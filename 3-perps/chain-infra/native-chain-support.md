# 第九部分：为 perps 新增链原生支持 —— 设计空间与三个机制空白

> **研究日期**：2026-09-07
> **定位**：本部分是第八部分（资产发行原生链设计）的**姊妹章节**。委托方的原话是"其次我认为给 perps 新增一些链原生支持也很重要，也可以考虑进来"——因此本部分回答两个问题：**① 链还能为 perps 做什么（现状之外的设计空间）；② 这些零件能否与资产发行共用一套 infra。**
> **底稿**：`research/M-perps-native-chain-support.md`（设计空间主体）、`research/J-appchain-comparables.md`（横向对标）、`research/I-risex-app-coupling.md`（RISEx 实况）、`research/N-opstack-mantle-surface.md`（OP Stack 改动量）
> **版式约定**：`[已实现]` = 有生产先例 ｜ `[本研究提案]` = 本研究提出、未见先例 ｜ 二者严格区分，不混淆

---

## 一页纸结论

**① perps 的链级痛点里，只有一类是"必须动链"的：与「顺序」有关的那些。**
oracle 延迟套利窗口、清算被拥堵挤出、cancel 被 taker 抢先、撮合热点争用 —— 这四项的本质都是**区块内相对顺序**，而顺序是 sequencer 的专属权力，应用层合约在定义上无法自救。

**② 而 gas 摩擦、失败成本、跨保证金原子性、sub-account 这些，全部可以在应用层解决。**
RISEx 就是活证据：它没有任何链级排序特权，靠 **operator 代付 gas + 人为 latency bump + TX 额度门禁** 三件应用层工具，做出了"链原生"的体感（见第七部分 §3）。

**③ 本研究识别出三个「高收益 + 中低成本 + 检索确认无先例」的机制空白：**

| # | 机制空白 | 为什么是空白 |
|---|---|---|
| **① 清算专用 lane（不可被挤占的区块空间配额）** | **没有任何链在协议层保留"普通交易不可借用"的清算配额。** Solana 优先费、Flashbots 私有通道都只是"加钱排前面"，不是"保留配额" |
| **② 协议强制的「模拟-免费拒绝」（revert protection）** | Flashbots Protect 是**应用层自愿服务**；Solana 失败仍收基础费；NEAR 是"按用量退款"而非"执行前拒绝"。**协议强制层面无先例** |
| **③ oracle 与清算的原子绑定（弱化版）** | 历史 Sei 靠**验证者投票**而非原子绑定；HyperEVM precompile 是**单向只读窗口**。**"同一状态转换内完成价格更新 + 清算判断"无先例** |

**④ 三者的共同点，也是它们值得做的核心理由**：
> **全部可以在不改变 OP Stack 共识模型（仍是单 sequencer）的前提下，只通过 sequencer / txpool / 交易验证层的规则调整实现。**
> 不需要并行执行引擎、不需要非 EVM 原生模块、不需要 TEE。

**⑤ 最重要的战略结论：perps 与资产发行确实能共用一套 infra，但共用的是"地基"不是"业务逻辑"。**

**高度共用的四件**：批量拍卖原语、优先车道/排序公平原语、原生费用路由、**交易类型标签（TransactionType）基础设施**。
**各自专用的**：撮合 precompile、保险基金/ADL（perps 专用）；转账钩子、上币额度拍卖（发行专用）。

**⑥ 但必须先说清一个前置条件**：**在 Mantle 今天的参数下，链上 CLOB 物理上跑不起来。**
【实测】纯 Solidity 撮合单笔烧 **240 万–420 万 gas**，Mantle 60M 区块只装 **14–24 笔**（RISE 的 1.5 Ggas 区块装 357–615 笔）。**任何 perps 链原生方案的第 0 步是改区块参数** —— 而这是配置，不是工程。

## 1. 先立靶子：perps 的十个链级痛点

| # | 痛点 | 本质 | 是否必须动链 |
|---|---|---|---|
| 1.1 | **oracle 延迟与可套利窗口** | "价格更新"与"依赖它的清算"之间存在两笔交易的间隙 ⇒ MEV 窗口。**Mango Markets 事件的根因就是缺原子性** | **是** |
| 1.2 | **清算的 MEV 与 keeper 竞争外部性** | 拥堵时清算交易与无关的 NFT mint 在同一个 gas 竞价池里竞争 | **是** |
| 1.3 | 下单撤单的 gas 摩擦 | 做市商每天数十万次撤单的成本 | 否（可代付） |
| 1.4 | **撮合的状态争用** | **单一市场 = 单一热点账户，并行 EVM 在此完全无用**（RISE 官方自己承认："dApps do need to innovate new parallel designs... like RISE's upcoming novel CLOB"） | 是（但收益有限） |
| 1.5 | 爆仓级联与 ADL | ADL 是"牺牲对手方盈利仓位"的零和转移，无法凭空消除穿仓亏损 | 部分 |
| 1.6 | funding 结算的 gas 成本 | 【实测】RISEx 的 `FundingRate` 合约**占全链交易的 10.5%** —— 每小时对全部持仓账户逐个结算 | 否 |
| 1.7 | 跨保证金的原子性 | 需要与借贷/AMM 同状态机 | 否（同链即可） |
| 1.8 | 提现延迟与桥风险 | 标准 OP Stack 挑战期（RISE ≈ 3 天） | 部分 |
| 1.9 | **做市商的 latency 不公平** | taker 用更快的基础设施在 maker 撤单前吃掉过期报价 | **是** |
| 1.10 | 失败交易成本 | EVM 中失败照样烧 gas；退款在博弈论上等价于免费 DoS 预算 | 部分 |

> **归纳：10 个痛点里，「必须动链」的是 1.1 / 1.2 / 1.9（以及有限的 1.4）—— 全部是「顺序」问题。**
> 这与第七部分的发现完全一致：**RISE 花大钱做的 Shreds/CBP 解决的是「延迟」，而 perps 真正的公平性问题是「顺序」，所以 RISEx 最后还得在应用层加 latency bump。**

## 2. 已有解法的能力上限（横向）

| 已有解法 | 解决的痛点 | 能力上限 |
|---|---|---|
| **自建应用专属 L1**（Hyperliquid HyperCore） | 1.3、1.9 | 牺牲通用可组合性与 EVM 生态网络效应换撮合性能；治理仍高度中心化（JELLY 事件中的验证者投票 + oracle override 即证据） |
| **Cosmos 原生 exchange 模块**（Injective） | 1.4（部分）、1.9 | 撮合下沉到共识层 Go 模块解决了"合约级"争用，但**热点账户问题在模块内部依然存在**，只是不再暴露给开发者 |
| **Cosmos 原生 oracle 模块**（vote extension，历史 Sei 模式） | 1.1 | 本质是"更快的多签"，不是"消除延迟"；**且 Sei 已放弃原生 oracle 模块转向第三方 DON** —— 这是一次"预期存在的特性其实被放弃"的发现 |
| **StarkEx 快速提现**（dYdX v3，已停用） | 1.8 | 上限＝LP 资金池容量；且已随 v3 sunset（2024-10-28）停止运营 |
| **Hyperliquid cancel 优先 + gas-free** | 1.3、1.9 | 只解决"同一链内"的排序公平，不解决跨 venue 套利者的延迟优势；优先规则由团队设定，**缺乏链下可验证的形式化保证** |
| **dYdX v4 保险基金 + ADL 协议模块** | 1.2、1.5 | ADL 仍是零和转移；极端尾部风险（JELLY 级别的低流动性资产被操纵）仍可超出保险基金厚度 |
| **HyperEVM 读 precompile**（`0x0800` 段） | 1.1（部分） | 只是给 EVM 开了一个**只读窗口**读 HyperCore 已处理好的 oracle/仓位状态。**方向是单向的** —— 是"链级状态暴露给 EVM"，不是"EVM 状态被链级消费" |
| **RISEx（应用层三件套）** | 1.3、1.9、反垃圾 | operator 代付 gas + latency bump + TX 额度门禁。**全部是中心化裁量权，且官方明写快速通道"may be revoked"** |

## 4. 三个机制空白（本部分的核心产出）

**筛选标准**：(a) 可感知收益 ≥4 或成本极低、(b) 实现成本 ≤3、(c) 底稿「是否有先例」字段**明确为"检索未找到先例"**。
已被 Hyperliquid / dYdX 生产验证的机制（3.3、3.7、3.8）即便分数达标也**不入选本清单** —— 它们是"高优先级移植候选"，但不是"机制空白"。

### 空白 ①：清算专用 lane

> **没有任何链在协议层面实现"清算专用、不可被普通交易挤占的区块空间保留"。**

- **为什么必须链级**：区块空间分配是 sequencer 的特权。应用层合约无法为自己保留空间 —— 一旦拥堵，清算交易与无关交易在同一 gas 竞价池竞争，清算方要么加价（推高清算成本并传导给交易者）要么等待（穿仓风险敞口扩大）。
- **与现有手段的区别**：Solana 优先费、Flashbots 私有通道都是**"让愿意加钱的人排前面"**，不是**"保留配额"**。差别在拥堵极端情况下是决定性的。
- **关键设计细节**：**即使该区块清算交易为零，这部分配额也不能被普通交易借用** —— 否则退化为先到先得，起不到保证作用。
- **攻击面**：若"打标签"验证有漏洞，攻击者可伪造清算交易骗取优先车道，等价于免费获得优先出块权。⇒ **预验证 precompile 必须极度保守：宁可漏放真清算，不可误放假清算。**
- **残留复杂度（诚实记录）**：全市场级联爆仓时（几千账户同时越阈值），lane 内部仍会拥堵，此时需要 lane 内的二级排序规则（按风险敞口大小），这本身是新的复杂度来源。

### 空白 ②：协议强制的「模拟-免费拒绝」

> **协议层面的"强制模拟 → 必然 revert 则免费拒绝"规则，检索未找到先例。**

- **最接近的先例是 Flashbots Protect**，但其性质是**应用层 / RPC 提供商的自愿服务**，不是协议强制。
- Solana 即使交易失败仍收基础费用（不属"免费"）；NEAR 对未使用 gas 有退款，但那是"部分执行后按用量计费"而非"执行前拒绝"。
- **为什么成本低**：OP Stack 是单 sequencer 架构，**"打包前可模拟"的能力本来就存在** —— 只是没被制度化为协议规则。不需要新增交易类型，不需要改共识。
- **为什么对 perps 有价值**：做市商的策略性挂单要为"失败"本身付费；对发行场景则直接降低狙击者的试错门槛（**⚠️ 注意这是双刃剑，见 §5**）。

### 空白 ③：oracle 与清算的原子绑定（弱化版）

> 完整版（免 gas 系统交易 + 强制插入区块首位）成本偏高（(b)=4）。**但抽出其中"清算判断与 oracle 更新在同一状态转换内完成"这一个子机制，成本可降至中等，且仍是机制空白。**

- **对照现有方案**：历史 Sei 的 vote extension 靠**验证者多签**在区块提交前达成价格共识（而非原子绑定），且已被放弃；HyperEVM 的 `0x0800` precompile 是**单向只读窗口**。
- **弱化版的实现形态**：不要求免 gas、不要求强制插首位，只要求"清算 precompile 内部直接触发 oracle 读取 + 立即执行清算判断"，把两笔独立交易压成一笔，**从而彻底消灭中间的抢跑窗口**。
- **这直接命中 Mango Markets 类事故的根因**。

### 4.1 三者的共同优势

> **全部可以在不改变 OP Stack 共识模型（仍是单 sequencer）的前提下，仅通过 sequencer / txpool / 交易验证层的规则调整实现。**
>
> 不需要引入原生并行执行引擎（3.6）、非 EVM 原生模块（3.4）或硬件 TEE（3.10）这类架构级前置依赖。**是"用最小改动换最集中收益"的组合。**

**结合第八部分的 N 轨道发现**，这三项的可行性还要再上调一档：

- Mantle 走 **OP Succinct（SP1）ZK validity proof**，因此**避开了 Cannon/MIPS「链上单指令仲裁必须认识新指令」的紧箍咒**；
- 代价转为「四层 fork 同步 + SP1 vkey 轮换 + 证明 cycle 成本」——**工程可控、商业可核算**；
- 且 Mantle 采用 OP Succinct 时**已经脱离 Optimism Standard Chain 序列**，"改 EVM 会失去 Superchain 认定"这个顾虑对它已不成立。

## 5. 共用零件 vs 专用零件 —— 「一套 infra 两个用途」能否成立

**这是委托方最关心的战略问题。答案是：能，但共用的是地基，不是业务逻辑。**

### 5.1 高度共用（四件）

| 链级零件 | perps 侧用途 | 发行侧用途 | 共用程度 |
|---|---|---|---|
| **批量拍卖 / batch auction 原语** | 消灭订单簿连续撮合的 MEV 窗口，统一出清价 | **ixo `x/bonds` 的 `BatchBlocks` 机制** —— 同批次内所有买卖单汇总后按统一价格结算、**忽略订单到达顺序**，是发行侧**抗狙击**的核心手段 | **最高**。底层都是"批次汇总 + 统一出清"这一个数据结构与状态转换规则；perps 订单簿与 bonding curve 认购只是把同一个批量拍卖引擎接到不同的定价函数上。**这是"一套 infra 两个用途"最强的证据。** |
| **优先车道 / 排序公平原语** | 清算不被挤占（3.2）、做市商撤单不被狙击（3.3） | 发行侧同样需要"保证撤销认购/取消挂单不被抢跑"；HIP-1 荷兰拍卖的"卡死不退款"、ixo 的 `MaxPrices` 价格保护都是同类需求的不同实现 | **中高**。都需要"交易类型标签 + 区块内排序规则"这套基础设施；标签定义不同，排序引擎复用同一套代码 |
| **原生费用路由** | 清算费自动进保险基金、maker/taker 费率结算 | **Solana Token-2022 `TransferFeeConfig`**（转账费自动暂扣到 `withdrawWithheldAuthority`）、**ixo `x/bonds` 的 `TxFeePercentage`/`ExitFeePercentage`** | **最高**。都是"状态转换里自动划转一定比例给指定地址"这个原语；字段语义不同，底层数据结构（费率参数 + 目标地址 + 自动触发点）相同 |
| **交易类型标签（TransactionType）基础设施** | 3.1/3.2/3.3/3.7/3.12 **五项提案共同依赖的技术地基** | 发行侧的"认购取消优先"、"KYC 前置检查"（Injective permissions 的 mint/receive 权限检查）直接复用 | **最高（基础设施层）**。一旦为 perps 建好，发行侧的抗狙击 / KYB 闸门可直接复用，**边际成本很低** |

### 5.2 中低度共用（两件）

| 零件 | 判断 |
|---|---|
| **原生 sub-account / 权限委托** | **中度共用**。perps 场景是"交易 vs 提现"二元区分；发行场景是 mint/burn/send/receive 多元位掩码（Injective permissions module）、`TreasuryCap`/`DenyCapV2` 分权（Sui Regulated Coin）。粒度不同，但**一个通用的"能力位掩码"账户模型能同时表达两种需求** |
| **原生 oracle 访问** | **低度共用**。perps 是 oracle 的重度刚需方；**发行侧多数场景（meme / bonding curve）是内生定价，完全不需要外部 oracle**，只有 RWA 发行需要参考汇率。复用价值主要在"链已有 oracle 系统交易底座"这一层 |

### 5.3 各自专用（无法复用）

| 零件 | 专用于 | 原因 |
|---|---|---|
| 撮合专用 precompile（定点数学 / skip-list / heap） | **perps** | 订单簿撮合的数据结构（价格-时间优先的堆/跳表）是 CLOB 特有；发行侧的拍卖/bonding curve 是"批量汇总求解"，不需要维护高频增删的持久订单簿 |
| 热点账户串行执行 lane | **perps**（弱专用） | 发行侧的热点（如 HIP-1 拍卖竞价）是**低频事件（31 小时一场）**，与 perps 撮合（每秒数千笔）不在一个量级。"perps 才有必要建，发行就算能用也用不着" |
| 链级保险基金 + ADL 协议化 | **perps** | 解决的是杠杆头寸穿仓这个 perps 特有风险模型；发行侧没有杠杆与强平概念 |
| **TransferHook / 转账钩子** | **发行** | 解决"发行方要不要在每次转账时校验/收税/限权"；perps 的仓位变化不是"转账"语义，无直接对应物 |
| **荷兰拍卖式上币额度分配**（HIP-1） | **发行** | 是"谁有资格发新币种"的准入机制。perps 的等价问题（谁有资格上新永续市场）理论上可借用同一套拍卖原语，但 **HIP-3 用的是质押门槛而非拍卖，未见拍卖制先例** ⇒ 暂不计入共用，列入存疑 |

### 5.4 战略结论

> **「一套 infra 两个用途」成立，但要用正确的方式理解它：**
>
> **共用的是四件地基**：批量拍卖原语、优先车道原语、原生费用路由、交易类型标签系统。
> **不共用的是业务逻辑**：撮合数据结构与风险引擎（perps）、转账钩子与上币准入（发行）。
>
> **⇒ 正确的工程顺序是：先建那四件地基（它们同时服务两个方向），再分别在其上叠加各自的业务模块。**
> **⇒ 反过来说，如果先为 perps 建撮合 precompile 和保险基金，对发行场景是零复用 —— 这是最容易犯的排序错误。**

## 6. 一个必须先解决的前置条件

**在 Mantle 今天的参数下，链上 CLOB 物理上跑不起来。**

| 项 | 数值 | 来源 |
|---|---|---|
| 纯 Solidity 链上 CLOB 单笔 gasUsed | **2,437,216 – 4,199,968** | 【实测】RISE 主网 |
| Mantle 区块 gasLimit | **60 M** | 【实测】 |
| **Mantle 单区块能装的撮合交易数** | **14 – 24 笔** | 计算 |
| RISE 区块 gasLimit | **1,500 M** | 【实测】 |
| **RISE 单区块能装的撮合交易数** | **357 – 615 笔** | 计算 |

> **⇒ 任何 perps 链原生方案的第 0 步不是加 precompile，是改区块参数（gasLimit + base fee 下限）。**
> **而这属于 L1（改 sequencer/配置），不破坏 EVM 等价性、不触发 SP1 vkey 轮换、不需要动 revm/kona 的四层 fork。**
>
> **好消息**：这一步同时也是"链上撮合能否存在"的唯一硬门槛，成本是**天级到周级的配置工作**，不是年级工程。
> **坏消息**：Mantle 填充率仅 0.224%，把区块放大 25 倍在短期内**没有任何可观测收益** —— 它是为一个尚不存在的应用预留容量。**因此这一步应该与 perps 应用的落地绑定，而不是提前空转。**

## 7. 执行建议

### 7.1 分阶段

| 阶段 | 动作 | 侵入性 | 前置条件 |
|---|---|---|---|
| **P0** | **区块参数**：提高 gasLimit、降低 base fee 下限 | L1（配置） | 与具体 perps 应用落地绑定，不提前空转 |
| **P0** | **原生 sub-account / session key**（3.8） | L0（可基于 4337 / 7702） | 无 —— 成本最低、去中心化代价最低，且**发行场景同样受益** |
| **P0** | **`eth_sendRawTransactionSync`（EIP-7966）** | L1（纯 RPC 层，周级） | 无 —— 第七部分已判定为全栈性价比最高项 |
| **P1** | **交易类型标签（TransactionType）基础设施** | L2（改 op-geth txpool + 区块构建） | **这是三个机制空白与四件共用地基的公共依赖，必须先建** |
| **P1** | **机制空白②：模拟-免费拒绝** | L1–L2（复用已有模拟能力） | 交易类型标签（可选） |
| **P2** | **机制空白①：清算专用 lane** | L2 | 交易类型标签 + 风控预验证 precompile |
| **P2** | **机制空白③：oracle-清算原子绑定（弱化版）** | L2 | 低延迟 oracle 推送通道 |
| **P2** | **批量拍卖原语**（3.4 退化版：系统合约 + 排序保证） | L1–L2 | **与发行侧共用，优先级因此上调** |
| **P3** | cancel 优先 + gas-free（3.3） | L2 | 交易类型标签 + 额度门禁防 DoS |
| **不建议** | 撮合 precompile（3.5）、热点串行 lane（3.6）、TEE mempool（3.10） | L2–L3 | 成本最高、去中心化代价最高、且**对发行场景零复用** |

### 7.2 三条硬提醒

**① gas-free 的任何东西都必须配额度门禁。**
免 gas 撤单本身是 DoS 面。Hyperliquid 的应对是按地址的挂单/撤单频率配额；**RISEx 的应对是"新地址 10,000 免费额度 + 每 $5 成交量 +1 + 撤单永久免费"**（第七部分 §3.2）。**两条独立路径都收敛到额度门禁 —— 这不是巧合，是"移除 gas 作为限速器"之后的必然结果。**

**② 「模拟-免费拒绝」对发行场景是双刃剑。**
它降低做市商的失败成本（好），但**同时降低狙击 bot 的试错门槛**（坏）。第一阶段研究识别的抗狙击范式之一恰恰是"用失败成本惩罚 bot"（Metaplex Candy Machine 的 bot tax）。**⇒ 若两个场景同链，该机制必须可按合约/交易类型选择性开关，不能全链一刀切。**

**③ 所有排序特权都会把 sequencer 变成新的信任焦点。**
3.1 的 oracle 系统交易要求 oracle 推送**本身带链下签名可验证性**（sequencer 只做转发者而非生成者），否则等价于 sequencer 自己操纵 oracle。**且 fraud proof 必须能覆盖"sequencer 是否正确插入了 oracle 签名数据"这一断言** —— 这是本部分所有提案里最容易被忽略、又最致命的一条。

## 存疑与未决

1. ⚠️ **Solana 拥堵导致清算失败**的证据为二手综合报道，**未找到官方一手事故报告**。这削弱了机制空白①的痛点论证强度（机制空白本身的判定不受影响）。
2. ⚠️ **Sei 放弃原生 oracle 模块**：仅能确认当前文档已不再列出该模块，**未定位到官方废弃公告一手 URL**。
3. ⚠️ **失败交易占比 / gas 浪费总量**无官方或学术级权威统计，仅有工程博客层面的定性描述。
4. ⚠️ **"新增永续市场"是否有拍卖制先例**：HIP-3 用质押门槛，本研究与 J/L 轨道均未发现拍卖制先例。若存在，§5.3 中"上币额度拍卖=发行专用"的判定需要改为共用。
5. ⚠️ **3.5 撮合 precompile 的 gas 收益量化估算**：底稿给出的是数量级推断（"低 1–2 个数量级"），**未做实际基准测试**。
6. ⚠️ **自定义逻辑与 SP1 证明 cycle 成本的线性关系**为本研究推断，非官方逐字结论。SP1 官方只确认 built-in precompile 能显著降本、缺补丁会造成 cycle regression。

**完整存疑清单见 `research/M-perps-native-chain-support.md` §存疑清单。**
