# 轨道 M：为 perps 新增链原生支持的设计空间

**目标文件**：`/Users/whisker/Work/research/work/launchpad-on-mantle/research/M-perps-native-chain-support.md`

主题：**为 perps 新增链原生支持的设计空间** —— 不只是盘点现状（现状对标交给 J 轨道），而是**系统性推导「链还能为 perps 做什么、以及每一项的可行性与代价」**。

这是一份**设计空间探索 + 可行性论证**底稿。允许提出**未被实现**的方案，但必须严格区分「已有实现」与「本研究提出的设计」，并对后者做**工程可行性论证与失败模式分析**。

## Change

### 1. perps 的链级痛点解剖（先立靶子）
每条都要有证据 / 事故案例支撑：
- oracle 延迟与可套利窗口
- 清算的 MEV 与 keeper 竞争外部性
- 下单撤单的 gas 摩擦（做市商每天几十万次撤单的成本）
- **撮合的状态争用**（单一市场 = 单一热点账户，并行 EVM 在此完全无用 —— 这一点要论证清楚）
- 爆仓级联与 ADL
- funding 结算的 gas 成本（N 个持仓账户的批量结算）
- 跨保证金的原子性
- 提现延迟与桥风险
- 做市商的 latency 不公平
- 失败交易成本

引用真实事故：Hyperliquid JELLY 事件、Solana 拥堵导致清算失败、各链 oracle 操纵案例（如 Mango Markets）。

### 2. 已有链级解法的能力上限
简表 + 交叉引用其他轨道（`→ 见 J 轨道`），**不重复深挖**。

### 3. 设计空间：逐项提出并论证
每项统一模板：
- **机制描述**
- **为什么必须在链级**（如果应用层能做，就要说明为什么还值得进链级）
- **实现形态**：precompile？系统合约？sequencer 策略？共识层？新交易类型？
- **在 OP Stack 上的改动量**
- **攻击面与失败模式**
- **是否有先例**（有则给 URL）

必须覆盖（≥10 项）：
1. **oracle 进入区块构建**：区块头 / 系统交易内嵌 oracle 更新，保证「价格先于撮合」的确定性顺序；价格更新免 gas；oracle 更新与清算的原子绑定
2. **清算专用 lane / 优先区块空间**：拥堵时清算交易永不被挤出
3. **cancel 优先于 fill 的排序语义** + gas-free cancel 的链级表达（做市商最关心的公平性）
4. **批量撮合 / frequent batch auction 作为链级原语**，消灭 latency 竞赛
5. **撮合专用 precompile**（定点数学、订单簿 skip-list / heap 操作、批量匹配）—— 给出 gas 收益的**量化估算**
6. **热点账户的确定性串行执行 lane**（承认撮合无法并行，给它一条独占执行流水线）
7. **链级 margin / 风控**：pre-trade risk check 进入状态转换、保证金账本作为原生状态
8. **原生 sub-account 与权限委托**（API-key 式交易权限、session key）
9. **链级保险基金与 ADL 的协议化**
10. **TEE / 加密 mempool 用于订单隐私**（防抢跑做市商报价）
11. **快速提现 / 结算通道**（含 native USD、L1 结算延迟的缓解）
12. **失败交易免费 / revert protection 的链级实现**

### 4. 优先级排序
用三轴给出优先级矩阵：
- (a) 对交易者 / 做市商的**可感知收益**
- (b) **实现成本**
- (c) **去中心化代价**

并挑出 **3 条「高收益 + 中低成本 + 无先例」的机会点** —— 第一阶段研究的最高价值产出之一就是识别「无人实现的机制空白」，请沿用这个标准。

### 5. 与「资产发行原生」的共用零件
明确指出哪些链级零件**同时服务 perps 与发行**（如优先 lane、gas 抽象、原生 oracle、批量拍卖、原生费用路由、原生 sub-account），哪些是各自专用。

**这决定最终方案能否"一套 infra 两个用途"，是委托方最关心的战略问题之一。**
