# 落盘协议（所有轨道强制遵守）

上一轮 7 个 research agent **全部在"研究完成、准备写文件"的那一刻进程退出**，15 分钟的研究成果全部丢失。原因是**一次性写入超大文件**。

## 因此本轮强制采用「先落盘骨架、再分段填充」

1. **第一个动作**就用 `write` 创建目标文件，只写：文件头（见共享上下文的 Contract）+ 全部章节标题 + 每节一行 `<!-- TODO -->`。**立刻落盘。**
2. 然后**逐节**用 `edit` 或 `write` 补内容，**每次调用只写 1–2 节**，单次写入**不要超过 400 行**。
3. 每完成 2–3 节就确认一次文件仍在磁盘上（`wc -l` 或 `read` 首尾）。
4. **绝对禁止**把整份 500–1200 行的文件攒在上下文里最后一次性 `write`。
5. 研究与写作**交替进行**：查完一节就写一节，不要先查完全部再写。
6. 若感觉上下文将要耗尽：**立即停止研究，把已有材料写进文件**，未完成的节留 `⚠️ 本轮未完成` 标记。**残缺但落盘的文件远胜于完美但丢失的文件。**

## 取数纪律（上一轮的教训）

- RPC / API 采样**串行 + 每次 sleep 150–300ms**，样本 20–30 个足够，禁止几百个并发请求。
- 十六进制→十进制换算务必核对（上一轮有 agent 把 `0x5faa79d` 算错导致采样未来区块）。
- 单次 shell / eval 调用**不超过 30 秒**，拆成多次小调用。
- 实测拿不到就标 `⚠️ 未取到`，**不要为了实测而卡死**。一手文档研究的优先级高于实测。
