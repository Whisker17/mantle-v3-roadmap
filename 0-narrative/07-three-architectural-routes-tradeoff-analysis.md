# Mantle 三条执行架构路线比较：保持现有状态、MantleCore 与 App-specific L3

> **文档状态**：供架构选型使用的比较材料，不代表最终决策。  
> **比较目标**：为 Perps、Launchpad 等产品选择执行与结算方式，评价产品能力、可组合性、安全、开发量和长期维护成本。  
> **路线三详细方案**：[Mantle App-specific L3 路线方案](09-native-l3-architecture-and-errata.md)。  
> **版本说明**：本稿替代原先预设 L3 为最终选择的横评，路线一按“保持现有执行层”重新定义。

## 1. 比较基线

三条路线服务于同一组产品目标：可验证的订单与资产处理、可持续的交易体验、可控的清算与坏账、可用的充提及可维护的系统。不以“采用某种架构”本身作为成果。

| 路线 | 明确定义 | 不应混入的能力或假设 |
|---|---|---|
| ① 保持现有状态 | 不改变 Mantle 当前执行层、排序规则或证明程序，以合约与应用服务实现产品 | 不把新增 Flashblocks、协议级撤单优先、precompile 等算成已有能力 |
| ② 引入 MantleCore | 在同一 Mantle 执行域内加入原生状态机，与 EVM 共同定义规范状态转换、提交和恢复 | 不把同进程直接等同于任意同步调用、零风险或零证明成本 |
| ③ App-specific L3 | 应用独立执行，在 Mantle L2 上托管资产、验证状态和执行结算 | 不把异步跨层交互视为同链原子组合，不默认需要 Solver 或远程授信 |

“保持现有状态”仍允许开发或集成产品合约、索引、前端、做市接口与 Gas 代付。它表示底层架构不变，不表示没有产品开发。

本文不采用此前对市场份额、国库规模、固定性能倍数或“零穿仓”的表述来决定技术路线。吞吐、费用和延迟均应以相同工作负载验证。

## 2. 路线一：保持现有 Mantle 执行层

### 2.1 Overview 与实现方式

应用部署为 Mantle L2 合约，使用现有资产和 DeFi 环境。交易接入、订单传播、报价和索引可以由链下服务承担，资产变化按照合约规则在 L2 执行。若采用链下撮合，必须明确最终由合约检查哪些授权、价格和资金约束，不能把链下回执写成链上最终成交。

```text
Mantle L2
+--------------------------------------------------------+
| Existing EVM execution / sequencing / proving           |
|                                                        |
| Lending <-> Product contracts <-> Existing token / DEX   |
+--------------------------------------------------------+
                    ^                 |
                    | Orders / calls  | Receipts / events
                    |                 v
              Application services / UI / SDK
```

### 2.2 优势

资产与应用处于同链，能在合约接口和 Gas 限制允许的范围内原子组合；现有钱包、RPC、代币与合约代码较容易复用。无需新增 Rollup 桥、子链 DA 或独立子链退出协议，新增基础设施较少。

### 2.3 局限

应用接受现有区块空间、执行语义和排序能力。高撤单比订单簿的持续吞吐、费用与风险处理可能受限，需要基准确认。通过链下服务改善回执，不等于获得协议级排序保证或更快最终性。

链上 Perps 在 EVM 上可以实现，需进一步区分 AMM、Oracle 报价、RFQ 和全订单簿等产品形态。某一种高频 CLOB 不满足目标，不代表所有 Perps 都不适合路线一。

### 2.4 适用条件

目标产品能在现有执行能力内成立；同链流动性与组合价值较高；希望较快验证产品需求；团队不准备承担新执行系统的长期责任。若测试显示不可接受的延迟、费用或风控调度限制，再比较两条定制执行路线。

## 3. 路线二：同一执行域引入 MantleCore

### 3.1 Overview 与实现方式

在 Mantle 的规范执行中加入原生业务状态机，EVM 与 Core 共享一个协议定义的提交、重放和重组边界。通过读接口及动作提交接口交互，业务状态进入总体状态承诺和证明程序。

```text
Mantle L2: one canonical execution domain
+--------------------------------------------------------+
| EVM                  <->  MantleCore                    |
| Contracts / assets        Orders / margin / liquidation |
|                                                        |
| Deterministic scheduling / action queues                |
| Shared state commitment / replay / proof program        |
+--------------------------------------------------------+
```

物理同机部署可以降低内部通信成本，但决定正确性的是规范执行规则。需要指定：EVM 读取的是哪个阶段的 Core 快照、写动作何时生效、失败如何处理、动作队列是否进入状态承诺，以及跨版本如何恢复。

[08 MantleCore 推演](08-route-2-hypercore-dual-engine-deep-dive.md)可提供机制草图，但其中“完美原子性”“必须手写 SP1 电路”和固定性能倍数不作为本轮比较依据。HyperCore 官方文档展示了读预编译与延后写动作的组合，支持这种区分。[S3]

### 3.2 优势

可按业务优化交易与状态布局，同时保持紧密的 EVM / Core 状态交互。应用资产无需再跨一条 Rollup 边界，统一风险与保证金较容易在一个规范执行域内实现。

### 3.3 局限

需要修改或扩展核心执行、状态持久化、重放与证明路径。业务升级可能涉及 Mantle 核心发布、验证密钥和治理；业务负载和缺陷也可能影响共享节点与证明资源。

采用 SP1 并不意味着必须手写每个业务电路。它能够证明编译到 RISC-V 的程序，工作集中于业务语义、状态认证、跨模块一致性、证明性能和升级管理。[S4] 不能仅凭“非 EVM”就判定工程不可行。

### 3.4 适用条件

产品确实需要专用执行，同时又频繁读取或更新 EVM 侧资产和风控状态；原子性与资本复用的收益较大；团队愿意长期维护核心客户端及证明集成，并能安排全链发布与治理。

## 4. 路线三：L2 结算、App-specific L3 执行

### 4.1 Overview 与实现方式

Mantle L2 保持通用执行环境，新增资产托管、Inbox / Outbox、L3 状态注册、证明验证、强制请求和退出合约。每条 L3 独立执行应用逻辑，异步发布数据及证明。

```text
Mantle L2: settlement
+--------------------------------------------------------+
| Escrow | Inbox / Outbox | L3 Registry / Verifier | Exit  |
+--------------------------------------------------------+
                 | Deposits              ^ Proofs / exits
                 v                       |
          Authenticated cross-layer protocol
                 |                       ^
                 v                       |
App-specific L3: execution
+--------------------------------------------------------+
| Orders / positions / margin / liquidation               |
| Own sequencing / state / data publication / proving     |
+--------------------------------------------------------+
```

参考基础方案为按 L3 隔离托管额度、预存保证金、原生充提和公开 DA。跨层统一授信、意图垫资、快速提现和隐私链作为可选扩展单独计价。完整设计、消息生命周期与失败处理见 [09 文档](09-native-l3-architecture-and-errata.md)。

**具体架构参照为 Lighter**：将其 Ethereum 父链托管 / 结算角色移至 Mantle L2，将其专用交易执行角色移至 L3。借鉴优先请求队列、公共账户差分、Commit / Verify / Execute 与待领余额；需适配父链确认、DA 与验证环境。参考数据发布采用 Mantle calldata，不假设支持原生 Blob 交易。架构参考不要求 L3 使用 SP1，详见 [11 Lighter 专题](11-lighter-reference-for-mantle-l3.md)。

### 4.2 优势

产品能够定制执行与状态，获得独立资源预算和发布节奏；通常无需把每个应用的业务规则加入 Mantle 通用执行程序。产品内部可以高频运行，再按批次向 L2 结算。

### 4.3 局限

新增跨层异步一致性、充值重组恢复、提现证明、DA、独立退出与运维工作。资产虽然托管在 L2，使用权仍分配给不同执行域，流动性不会自动统一。

L3 没有免除业务逻辑证明成本，而是将其放到独立管线。L2 故障、结算拥堵和升级仍会影响 L3；共享担保或错误的支付权限也可能让应用风险传播到父层资产。

### 4.4 适用条件

产品大部分操作能在预分配资金范围内闭环；跨层结算频率低于本地交易频率；专用执行和独立发布带来的收益能够覆盖多一条链的固定成本。

## 5. 同口径优劣势矩阵

| 维度 | ① 保持现有状态 | ② MantleCore | ③ App-specific L3 |
|---|---|---|---|
| 通用合约复用 | 较高 | EVM 侧保留，Core 需专门接口 | 原生非 EVM 部分需移植或适配 |
| 业务执行自由度 | 受现有 EVM 和排序能力约束 | 高，但纳入 Mantle 核心规则 | 高，可按应用独立定义 |
| 与 L2 DeFi 的原子组合 | 在合约接口和 Gas 限制内可实现 | 取决于阶段调度和动作语义，可做紧密集成 | 默认不能跨层原子完成 |
| 资金分配 | 同链，不新增子链充值 | 同一执行域内划拨，仍需内部账务 | 按 L3 分配余额 / 额度，需充提或再平衡 |
| 产品升级 | 合约及应用服务升级 | 可能涉及全链执行和证明升级 | L3 独立发布，但结算与验证版本要协调 |
| 资源隔离 | 共享区块空间 | 可分配资源，但仍共享规范执行和证明 | 执行可独立，父层结算与共享服务仍有依赖 |
| 新增安全面 | 应用合约、Oracle、权限和风控 | Core、跨模块一致性、核心升级和证明适配 | 业务、跨层协议、DA、Verifier、退出和治理 |
| 最终性 | 沿用 Mantle | 沿用 Mantle，并验证新状态规则 | 分别说明 L3 暂定执行、L2 接受证明与父层最终性 |
| 性能与成本 | 实测现有链上的应用负载 | 实测原生执行及总体证明成本 | 实测执行、证明、DA、桥与固定运营摊销 |
| 初始开发负担 | 通常较低，仍含完整交易产品 | 核心客户端集成较重 | 跨层协议和独立基础设施较重 |
| 长期维护 | 应用维护为主 | 应用加核心客户端 / 证明维护 | 应用加每链运行 / 跨层协议维护 |

不提供未经测量的“几毫秒对几秒”总分排名。原生撮合回执、区块时间、证明时间和可提现时间分别比较。

## 6. 开发工作量的对照口径

### 6.1 估算假设

本节为低至中置信度的 ROM 工程估算，不是报价。三条路线以同一参考产品计量：一个公开 Perps 应用、单一稳定币保证金、有限市场、订单与风控闭环、基础 API / SDK、审计配合和限额发布。没有假设可直接获得一套满足全部需求的已审计交易引擎。

Lighter 提供具体参考实现，但公开代码的许可、运行服务完整性及 Mantle 适配尚不足以形成直接复用报价。本表仍按自建业务程序与通用框架估计；若获得适用授权和完整交付，需要重新计算，不能把“架构已有参照”自动等同于“只需更换部署链”。

路线一如果无法在现有协议下满足必需的排序或性能需求，应标记“需求不满足”，不能通过低开发报价自动胜出。反过来，也不能将所有产品开发费用只归给路线一，而把已有业务引擎免费分配给路线二和三。

### 6.2 工作分解（直接人月，不含规划缓冲）

| 工作包 | ① 现有状态 | ② MantleCore | ③ L3 |
|---|---:|---:|---:|
| 协议 / 产品风险规格 | 1–2 | 3–5 | 2–3 |
| 原生节点 / 执行框架集成 | 0 | 6–9 | 6–9 |
| Perps 业务逻辑 | 6–9 | 6–9 | 6–9 |
| 资产接入与一致性接口 | 1–2 | 4–6 | 5–8 |
| 数据、状态承诺与恢复新增适配 | 0 | 2–4 | 3–5 |
| 证明程序新增适配 | 0 | 5–9 | 5–9 |
| 退出 / 升级 / 业务故障处理 | 1–2 | 3–5 | 4–7 |
| API / SDK / 索引 | 3–5 | 2–4 | 3–5 |
| 集成、性能与运维 | 2–4 | 3–5 | 5–8 |
| 审计配合、修复与限额发布 | 2–4 | 2–4 | 3–5 |
| **合计** | **16–28** | **36–60** | **42–68** |

零表示不新增该类协议工程，不表示应用没有相应运行成本。业务逻辑采用同一工作量区间只是比较控制假设，语言、成熟实现和实际团队能力都可能使它变化。Core API 估算较低的前提是保留既有 EVM 接入；若要求完整的新交易终端或大量独立钱包适配，需要另计。

采用 25%–35% 规划缓冲，预算工作量分别约 **20–38、45–81、53–92 人月**。外部审计采购、基础设施费用、流动性本金、合规和商业分销不在表内。L3 模块定义和增量范围见 [09 第 11 节](09-native-l3-architecture-and-errata.md#11-开发工作量周期与运营成本)。

### 6.3 排期与团队假设

| 项目 | ① 现有状态 | ② MantleCore | ③ L3 |
|---|---|---|---|
| 参考工程团队 | 4–6 人 | 8–10 人，含核心客户端与证明工程 | 8–10 人，含协议、桥、证明与 SRE |
| 规划窗口 | 5–15 个月 | 8–16 个月 | 9–18 个月 |
| 窗口终点 | 满足所选产品范围的限额生产 | 核心升级获准且新引擎限额生产 | 首条 L3 全闭环限额生产 |
| 主要关键路径 | 产品风控、合约审计与真实流动性验证 | 规范执行、证明集成、全链回归、治理与升级 | 跨层协议、DA / 证明、退出、故障演练与审计 |

周期按上述预算人月、约 65%–80% 有效产能及顺序依赖规划，各端点不是相同人数条件下的精确预测。路线一的宽区间包含从现有模块集成到定制产品的差异；采购成熟产品可能显著减少工期，但必须三条路线一起调整复用假设。路线二的治理排期和路线三的证明 / 退出风险都可能造成超出窗口的延后。

人月估算与日历排期应随代码盘点、团队确认和第一轮基准重估，不沿用早期材料中的固定美元总价。

### 6.4 长期成本

三条路线都承担产品风控、Oracle、用户接口、值班和安全维护。路线一主要支付既有链的使用成本；路线二增加 Mantle 核心客户端和证明的持续维护；路线三增加独立链的节点、证明、DA、跨层结算与资产再平衡。

比较预算时分别列建设投入、年度固定成本、业务量相关成本和营运资本。用户不付 Gas 不代表系统免费，同链可组合也不代表无需支付交易执行成本。

## 7. 哪些证据会改变路线选择

| 观察结果 | 对判断的影响 |
|---|---|
| 现有 L2 合约已满足交易与风控指标 | 路线一的较小改造面更有吸引力，定制执行需证明额外收益 |
| 高频原生执行必要，且大量操作需要同步访问 EVM 状态 | 路线二更值得推进详细验证 |
| 高频原生执行必要，大部分交易可在预分配资金内独立完成 | 路线三更值得推进详细验证 |
| L3 单位证明或固定运营成本高于收益 | 缩小负载、调整实现或重新评估路线一 / 二 |
| Core 改动难以与 Mantle 升级和证明管线长期维护 | 路线三的发布隔离价值上升 |
| 用户必须随时跨产品共享全部抵押，不能接受额度分配 | 路线三需要额外风险协议，基础 L3 报价不再适用 |
| 某产品只是要求免 Gas、发行曲线或现成 AMM | 不能据此直接决定新建 L3，先验证应用层方案 |

当前决策状态是保留三条路线，先把路线三说明完整。下一轮决策材料需要包含：固定产品负载、三条路线的能力差距、原型测量、真实代码复用清单、人员与审计可用性，以及可接受的安全模型。没有这些证据，不给出“唯一正确路线”的结论。
