# Mantle App-specific L3 路线方案：Overview、详细设计、优劣势与开发工作量

> **文档状态**：供路线比较的设计提案，不代表已选型或已部署。  
> **用途**：说明以 Mantle L2 为结算空间、以 L3 为应用专用执行状态机的完整方案，与「保持现有执行层」「同一执行层引入 MantleCore」比较。  
> **范围**：架构、资产与消息流、证明与数据可用性、安全边界、产品适配、建设和运维工作量。不包含 Bybit、国库配置、代币回购与市场增长预测。  
> **阅读入口**：[三条路线比较](07-three-architectural-routes-tradeoff-analysis.md)。本稿重写原 09 文档，文件名保持不变以保留引用。

## 0. Overview

### 0.1 这条路线做什么

Mantle L2 保持通用 EVM 执行环境，并通过部署结算合约接纳应用专用 L3。每条 L3 拥有独立的执行规则、状态、排序服务和证明管线；资产托管、充值入口、状态承诺及提现执行落在 Mantle L2。

用户把资金分配给一条 L3 后，可以连续在该 L3 内交易。订单撮合、保证金检查、仓位变更和清算不需要逐笔调用 L2。L3 异步向 L2 提交数据和证明，L2 验证后接受状态更新并允许相应提现。

设计目的有三个：

1. 允许产品采用通用 EVM 合约较难高效表达的执行规则与数据结构。
2. 让不同应用拥有独立的资源预算和发布节奏，减少应用迭代对 Mantle L2 核心执行规则的影响。
3. 继续使用 Mantle 作为资产入口和结算空间，同时明确承担跨层异步通信、独立运维和流动性分配的成本。

App-specific 的收益来自业务语义、状态组织、排序和证明工作负载的协同设计。使用 Rust 或增加一个 L3 标签，本身不能证明性能更高、成本更低。[S4][S5]

**主要架构参照采用 Lighter**：将其「Ethereum 托管与批次结算 + 专用交易执行层」映射为「Mantle L2 托管与批次结算 + App-specific L3」。日常撮合与风控在 L3 内闭环，跨层协议集中处理充值、优先请求、批次证明和退出。具体源码依据、状态模型与适配清单见 [11 Lighter 参考设计](11-lighter-reference-for-mantle-l3.md)。这是架构映射，不代表可以直接复制部署或沿用其性能数字。

### 0.2 在三条路线中的位置

| 路线 | 定义 | 主要获得什么 | 主要承担什么 |
|---|---|---|---|
| ① 保持现有状态 | 不改变 Mantle 执行层、排序规则和证明程序，在现有 L2 上构建应用合约与配套服务 | 合约复用、同链组合、较小的新增运维面 | 接受现有共享区块空间与协议级调度能力 |
| ② 引入 MantleCore | 在同一 Mantle 执行域内加入原生业务状态机，与 EVM 使用共同的规范状态转换和提交规则 | 专用执行，同时保留更紧密的状态交互 | 核心客户端、证明程序、升级和故障处理的耦合 |
| ③ App-specific L3 | Mantle L2 结算，应用在独立 L3 执行 | 专用执行、独立资源预算与发布节奏 | 跨层一致性、桥、DA、退出、独立节点与证明服务 |

路线一不包括新建 Flashblocks、修改 Sequencer 排序特权或新增协议级 precompile；这些会改变比较基线。路线二的 MantleCore 指本仓库提出的原生执行模块，不表示它是 Mantle 当前已部署能力。

### 0.3 什么条件下值得选 L3

适合 L3 的产品通常有以下特征：大量操作发生在应用内部；用户能够预先分配资金；核心业务不依赖逐笔跨层原子调用；专用执行带来的收益足以覆盖一条链的固定成本。

高频订单簿 Perps 是较明确的候选。Launchpad 是否需要独立链，取决于实际的状态增长、交易负载和排序需求。机构隐私市场有不同的数据披露和准入要求，可以单独讨论，但不能由“使用 ZK”直接推出隐私成立。

**方案成立的关键前提**：交易热路径可以在 L3 内闭环。如果产品要求实时、无额度分配地共享 L2 借贷抵押物，或每笔交易都原子调用 L2 DeFi，路线三的异步边界会成为主要障碍。

## 1. 设计边界与比较基准

### 1.1 基础方案与可选扩展

为使收益和成本可计算，本文选择一套参考设计。它用于估算和比较，不代表最终选型已经获批。

| 项目 | 基础方案 | 可选扩展，不计入首条 L3 基础闭环 |
|---|---|---|
| 结算 | 在 Mantle L2 上验证 L3 有效性证明 | 额外证明后端或递归聚合优化 |
| 执行 | 确定性的原生业务状态机，独立 Sequencer | 多排序者、based sequencing、额外预确认机制 |
| 资产 | 每条 L3 独立托管额度，预存保证金 | 远程信用分配、跨 L3 组合保证金、生息抵押 |
| 充提 | 原生 Inbox / Outbox 与证明结算 | Solver 垫资、ERC-7683 集成、快速提现池 |
| DA | 可恢复状态的数据发布到 L2，并核验其父层可用性路径 | 外部 DA 或 validium 模式 |
| 产品 | 一个公开交易应用；工作量以单一稳定币保证金 Perps 为参照 | 多资产抵押、股票公司行动、隐私暗池 |
| API | 应用 API、签名 SDK、余额与确认状态查询 | 完整 Ethereum JSON-RPC 兼容、任意 Solidity 合约部署 |

采用预存保证金是为了给出可闭环的比较基准，不否定远程授信的产品价值。后者的额外机制和工作量在第 7、11 节单列。

### 1.2 共用的产品口径

三条路线都需要订单与成交语义、预言机、初始及维持保证金、资金费、清算、保险或坏账分配、账户 API、审计和运营系统。这些不能只算在 L3 的成本中，也不能假设现有 EVM 路线无需开发交易产品。

对比时使用同一组订单流、市场数、账户数、撤单比例、极端行情和故障场景。若路线一达不到某项需求，应记录测试差距；不能为了形成统一报价而默认为三条路线都能达到相同结果。

## 2. 分层架构与组件职责

### 2.1 拓扑

图中最上层为 Mantle L2，最下层为候选 L3。三类 L3 表示可扩展方向，不意味着必须同时建设三条链。

```text
Mantle L2  |  Settlement space
+------------------------------------------------------------------------+
| Per-L3 Escrow | Inbox / Outbox | L3 State Registry                     |
| Asset allocation | Message authentication | Verifier / version         |
| Withdrawal limits | Forced requests | Upgrade / exit controls          |
+------------------------------------------------------------------------+
               |                                       ^
               | Deposits / allocated credit           | Proofs / data
               | Authenticated parent-chain messages   | Withdrawal claims
               v                                       |
+------------------------------------------------------------------------+
| L2 <-> L3 protocol                                                     |
| Parent references | Replay protection | Reorg recovery                 |
| Data availability | Proof binding | Failure / exit handling            |
+------------------------------------------------------------------------+
               |                       |                       |
               v                       v                       v
Mantle L3s | App-specific execution
+----------------------+ +----------------------+ +----------------------+
| Launchpad L3         | | Perps L3             | | Private L3           |
| Issuance / curve     | | Orders / positions   | | Permissioned trading |
| Embedded AMM         | | Margin / liquidation | | Privacy / disclosure |
| Own state + proving  | | Own state + proving  | | Own state + proving  |
+----------------------+ +----------------------+ +----------------------+
```

Solver、快速提现池和跨层授信可以接入这套结构，但基础结算不依赖它们。

### 2.2 L2 上的结算合约

| 组件 | 职责 | 必须明确的边界 |
|---|---|---|
| Per-L3 Escrow | 托管实际资产，记录充值与兑付 | 一条 L3 不得凭自身证明提取另一条 L3 的资金 |
| Inbox | 接收充值和强制请求，分配稳定的消息标识与顺序 | 事件必须来自指定合约、链和已认可的父链历史 |
| State Registry | 保存每条 L3 最近接受的状态根、批次序号与程序版本 | 新证明只能从已接受前态连续推进 |
| Verifier | 验证业务状态转换证明及其公开输入 | 合约地址、验证密钥、程序和消息承诺必须绑定 |
| Outbox / Withdrawal | 认证批次父链操作，累加并兑付待领余额 | L3 先扣账；仅执行已验证批次，防止重复执行和重复兑付 |
| Exit / Upgrade Controls | 强制请求、异常冻结、退出和版本迁移 | 升级不能绕过资产归属，暂停不能成为无限冻结的唯一方案 |

L2 合约保存的是 **L3 的状态承诺**。L3 不能直接覆盖 Mantle L2 的全局状态根；L2 自身仍按照原有协议执行这些合约调用。

### 2.3 L3 与链下服务

| 组件 | 工作内容 | 可复用部分与新增工作 |
|---|---|---|
| Sequencer / Executor | 接单、验签、排序、确定性执行、生成暂定回执 | 网络与存储库可复用；业务调度与状态转换需实现 |
| Parent-chain Observer | 跟踪 L2 区块、日志、确认级别及重组 | 可借鉴 Rollup 推导模式；不能默认现成客户端支持自定义非 EVM 子链 |
| State Store / Replay | 状态承诺、持久化、快照、崩溃恢复、确定性重放 | 通用数据库可复用；状态 schema、迁移与恢复规则需实现 |
| Batcher / DA Publisher | 编码并发布可恢复状态的数据 | 压缩库可复用；数据充分性和承诺绑定需验证 |
| Witness / Prover | 为执行准备见证，运行证明程序并提交证明 | 可选 zkVM 或专用电路；Lighter 使用 Plonky2 / PLONK 路线，不能直接按 SP1 复用 |
| API / Indexer / SDK | 订单、余额、仓位、充值、提现和确认状态 | 前端基础组件可复用；原生状态机需要专用数据模型 |
| Operations | 监控、备份、密钥管理、故障切换和告警 | 可共享运维工具；每条链增加独立的运行责任 |

“链”不要求每个组件都是独立微服务。可在首版合并部署；确定性执行、独立重放和安全边界必须保留。

### 2.4 按 Lighter 模式收敛结算接口

父链输入优先使用交易应用专用队列：充值、强制提现和其他必要优先操作均有唯一身份、消费顺序和超时规则。无需为了首个 Perps 产品先实现任意跨链合约调用。

L2 结算分别记录 **Commit、Verify、Execute、Claim**：Commit 保存数据与状态承诺，Verify 检查证明，Execute 执行经验证的批次父链操作，Claim 支付待领资产。实现可以合并部分调用，但这四种状态不能在 API 或账务上混为一谈。Lighter 的公开合约用批次操作哈希和待领余额实现这一模式。[S9]

这些接口借鉴协议结构，不要求照搬 Lighter 的合约、权限或超时参数。每条 Mantle L3 独立命名空间、托管权益和证明版本。

## 3. 专用执行状态机设计

### 3.1 哪些状态必须在一起

Perps 的订单、成交、持仓、保证金、资金费和清算由同一 L3 状态机管理。每次成交在同一状态转换中更新相关账户，不向 L2 请求逐笔风控授权。预言机输入、有效时间与过期处理也进入确定性执行规则。

Launchpad 的发行曲线、募集余额、毕业状态与 AMM 储备放在同一执行域。毕业可以是一次原子状态转换，不要求资产先退出到 L2。

不同产品采用不同状态机，并不自动要求不同链。需要紧密共享实时保证金的市场，应优先放在共同执行域；愿意按额度分配资金、接受异步结算的产品，更适合分开为 L3。

### 3.2 非 EVM 的范围

原生执行可以按产品定义交易类型、账户权限、Nonce、费率、状态树和整数精度，减少通用虚拟机语义的负担。代价是现有 Solidity AMM、ERC-20/ERC-721 工具与 Ethereum RPC 不一定可以原样运行。

参考设计采用应用级 API 和原生资产账本。若要复用已有 AMM，需要移植并验证其业务语义；若选择嵌入 EVM，则应计入双运行时、跨模块一致性和证明成本。不能同时按“纯非 EVM”估性能，又按“原样部署 Solidity”估开发工作量。

Perps 的状态组织参考 Lighter：完整交易状态、可公开恢复的账户 / 市场退出状态、每批聚合的账户差分分别建模，并由证明约束它们一致。订单索引应同时考虑运行时撮合和证明路径成本；一笔 taker 订单可能展开成多个内部执行周期，基准不能把订单数、成交数和电路周期数混用。[S9]

### 3.3 排序、收费与状态管理

- **排序**：定义接收、入队、撮合和撤单的生效点。FIFO 可以约束已接受交易的执行顺序，不能单凭私有 mempool 证明 Sequencer 未隐瞒或插入订单。
- **撤单与清算资源**：可设置保留配额和明确优先级，但必须防止其他交易长期饥饿。避免使用“0ms”表达无法兑现的网络和执行保证。
- **用户免 Gas**：由业务收费或运营预算承担执行、证明与 DA 成本。必须提供准入限流、配额或其他防滥用机制。
- **状态裁剪**：过期订单可按规则删除；失败发行应先完成退款或保留可领取承诺。不能以不活跃为由直接删除用户余额。历史归档、活跃状态压缩和 DA 保留分别设计。
- **确定性**：业务规则不得直接依赖节点本地时钟、浮点差异或网络读取结果。外部数据需要先成为规范输入。

## 4. L2 与 L3 的通信和资产生命周期

### 4.1 四类时间必须分别度量

| 时间口径 | 表示什么 | 不代表什么 |
|---|---|---|
| 订单回执 / 预确认 | Sequencer 接受或暂定执行了操作 | 不代表已被 L2 验证或继承最终性 |
| L3 执行确认 | 操作进入当前 L3 历史 | 不自动排除父链重组的影响 |
| L2 接受 L3 证明 | L2 合约验证并记录该状态更新 | 不等于包含该调用的 L2 区块已经最终确定 |
| 父层最终性 | 相应父链历史达到所选最终性条件 | 不替代 L3 合约、DA 和升级安全检查 |

在 OP Stack 术语中，unsafe、safe、finalized 是与父链推导进度相关的状态。safe 通常表示可从当前规范父链数据推导，finalized 对应最终确定的父链输入。[S1] Mantle 具体 RPC 标记、批次发布和证明接受延迟需要按实际部署测量，本文不指定固定秒数。

### 4.2 L2 → L3 原生充值

1. 用户在 L2 Escrow 锁定资产，Inbox 记录目标 L3、资产、数量、接收账户和唯一消息标识。
2. L3 Observer 验证事件来源与父链区块，按确认策略纳入执行。
3. L3 消费充值消息一次，增加相应账户权益，记录父链依赖和 Inbox 消费位置。
4. 数据发布与证明把该充值绑定到规范父链输入，推进 L2 上的 L3 状态承诺。

参考策略允许 L3 跟踪经本地验证的 L2 最新块并返回暂定余额，但对外明确其确认级别。任何依赖尚未稳定父链输入的状态，必须能回滚；其退出不得绕过父链认证直接转为不可撤回支付。若该恢复机制未通过验证，限额试运行前应使用更保守的充值确认策略。

单 Sequencer 可以减少协调过程，但不能单凭其签名把任意状态视为不可逆。原生充值是否足够快，应按用户从提交 L2 交易到 L3 可交易的完整延迟判断；L3 出块周期本身不能决定充值必须采用垫资。

### 4.3 L3 内交易

充值之后，交易、撤单、保证金占用、平仓及清算在 L3 本地执行。盈利必须对应其他账户、做市池或协议明确承担的负债变化，不能仅凭一笔 PnL 数值在 L2 增发可提现资产。

批量结算可以减少 L2 调用，但实时保证金检查持续在 L3 内进行。结算节奏由证明吞吐、DA 成本、提现需求和允许的未结算敞口决定，不统一写死为“日终”。

### 4.4 L3 → L2 原生提现

1. L3 按账户保证金规则检查可提金额，扣减可用余额，并产生唯一提现操作。
2. 操作进入该批次的父链操作承诺，与同一状态转换的扣账绑定。
3. L2 验证批次后按顺序执行父链操作，检查操作数据与承诺一致，再增加对应用户的待领余额。
4. 用户或中继者调用领取接口，将资产支付至授权的资产所有者并减少待领余额；重复执行批次或超额领取均应失败。付款失败必须原子回退或保留可重试领取权。

这采用 Lighter 的「批次操作哈希 + 待领余额」作为参考，不要求每个提现者额外提交独立的 Merkle 消息证明。限流导致延后时，保留待领权益和队列，不再次扣减 L3 余额。[S9]

这条流程的等待时间由证明、提交、父链确认和限流共同决定。ZK 路线没有必然固定为 15 分钟或一小时的证明等待期；不能拿别的系统的延迟替代本方案测量。

### 4.5 消息协议的必要字段与约束

| 内容 | 作用 |
|---|---|
| 源链、目标链、消息协议版本 | 防止跨链和跨版本重放 |
| 源合约、发送者、接收者、动作类型 | 限定调用权限和目标语义 |
| 消息序号 / 唯一 ID | 重复投递时只生效一次 |
| 父链区块标识、批次和消费位置 | 追踪历史依赖、顺序与重组 |
| 资产、数量、计量精度 | 避免单位混淆和跨资产误记账 |
| 状态版本、失败与重试规则 | 防止升级或重试改变原始语义 |

不用网络层保证“只送一次”。采用可重试投递、目标侧去重和可验证的消费记录。超时不等于消息未执行；退款或额度撤回必须排除目标链已经消费的情形。

## 5. 证明、数据可用性与安全继承

### 5.1 证明验证什么

参考证明公开输入包含 L3 身份、业务程序版本、前后状态根、批次号、父链输入承诺、Inbox 消费范围、Outbox 承诺和 DA 承诺。证明与 L2 合约共同检查：

- 前态与已接受历史一致，不能回退或跳接状态；
- 充值确实来自认证的父链输入，而非 Sequencer 伪造的见证；
- 用户授权、交易规则、资产记账和保证金约束被执行；
- 提现与扣账一致，消息只被消费一次；
- 发布的数据与被证明的状态转换一致。

L3 不必在每个批次重跑整个 Mantle L2。可以消费由父链 Inbox 等机制认证的输入承诺；认证路径本身属于结算协议和审计范围。

SP1 可证明编译到 RISC-V 的业务程序，不要求每个应用手写密码学电路。[S4] 工程重点是确定性程序、见证认证、公开输入绑定、状态恢复和证明吞吐。原生执行很快，并不保证在 zkVM 中证明同样便宜。

架构参考 Lighter 与使用其证明后端是两个决策。Lighter 的公开实现采用专用 Plonky2 电路、递归聚合和 gnark BN254 PLONK 包装。Mantle L3 可以采用该类专用电路，也可以按相同业务不变量构建 zkVM 程序；父链使用 SP1 不强制子链使用 SP1。第 11 节 ROM 仍按自建业务程序和通用证明框架估计，直接适配 Lighter 代码需要另行确认许可、代码范围和测量结果。[S9]

### 5.2 选择什么 DA

参考方案将聚合账户差分与必要市场数据作为 Mantle L2 交易 calldata 发布，在合约中计算数据承诺，由证明绑定解码内容与公共退出状态更新。数据超过单笔限制时采用有顺序、完整性和批次绑定的分块发布。需要验证父层 DA 路径、压缩、历史保存以及用户独立恢复退出权益的能力，不能只发布无法下载内容的哈希。

这个具体路径是对 Lighter Ethereum Blob 模式的适配：所读 Lighter 合约使用 `blobhash` 与 point-evaluation precompile，而标准 OP Stack 禁用 L2 Blob 交易。Mantle 将批次发布到 Ethereum Blob，不表示 L3 可以在 Mantle 上原样使用本地 Blob 交易；本方案不预设这一能力。calldata 的实际费用与容量需要测量。[S9]

外部 DA 是可选设计分支。只在外部保存退出所需数据，会引入额外可用性和退出假设；有效性证明并不能保证这些数据一定可得。若采用 validium，应在比较表中按该安全模型计价，不能仍把它描述为与父链上 DA 完全相同。

Lighter 的公共差分支持恢复账户权益与退出，但不应据此承诺从父链恢复所有订单历史和完整实时订单簿。Mantle 基础保障采用“可独立退出”；运行节点仍需备份、快照与确定性重放。若要求任意第三方在运营方失联后接管完整撮合，需要补充全部执行数据的可用性和接管协议，并重新计算 DA 成本。[S5][S9]

### 5.3 L2 结算的收益与代价

L3 批次在 Mantle L2 上验证，可以使用其合约环境和资产入口，避免应用逐笔在 Ethereum L1 执行。与此同时，L3 需要支付 L2 上的 DA、验证和结算费用，并承担 L2 的可用性、升级和最终性依赖。

如果 Mantle 自身采用 ZK 证明，L3 Verifier 的执行还会成为 L2 证明工作负载的一部分。复用同一证明体系不等于自动具备廉价递归聚合；必须测量验证交易的 L2 Gas 和父层证明影响。

本方案不宣称 L3 安全性与 Ethereum 完全等同。L3 在父链依赖之外增加自身程序、验证合约、消息协议、DA 配置、运营密钥和治理风险。[S6]

## 6. 故障、退出与升级

### 6.1 失败时系统如何运行

| 故障 | 预期处理 | 上线前必须验证的结果 |
|---|---|---|
| L2 重组撤销充值 | L3 回退至共同有效父链历史，重放依赖交易 | 不保留无担保充值，不产生外部不可撤回坏账 |
| L3 Sequencer 停机或审查 | 用户向 L2 提交强制请求；超时进入受控退出流程 | 恢复不依赖失联运营方签名 |
| Prover 落后或停止 | 限制未证明敞口，按阈值降低接单或暂停新增风险 | 不能无限提供“已最终确认”的错误回执 |
| 数据发布失败 | 不接受依赖不可用数据的正式结算 | 从公开数据能重建可退出状态 |
| Mantle L2 停机 | 暂停新跨层消息和提现；本地交易按预设敞口上限运行或停机 | 不把 L3 独立进程误当成独立父链结算能力 |
| Oracle 失效 | 禁止新增风险，按预设规则处理挂单、清算与恢复 | 不使用不明价格随意划扣保证金 |
| 业务规则缺陷 | 停止新风险，执行已定义的版本恢复或退出流程 | 不能依靠事后任意回滚抹去已结算资产 |

### 6.2 Perps 退出不同于简单转账链

持有未平仓头寸的用户不能仅证明旧保证金余额就提走全部资产。需要定义停止撮合的状态点、未结资金费、统一结算价格或其他关闭头寸机制，以及坏账分担顺序。

参考基础范围包括可公开触发的强制请求与超时退出机制。具体借鉴 Lighter 的冻结状态退出：通过公开账户、市场价格和资金费信息计算权益，验证后计入 L2 待领余额；尚未被消费的充值另有认证退款路径，不能与已消费充值双重兑付。[S9]

Lighter 白皮书以冻结时的最新 mark price 说明头寸估值，这可以作为设计参照，但股票休市、价格过期和坏账如何处理仍需专门规则。具体价格源、最长等待期、可接受未证明敞口和保险额度由产品风控与协议负责人共同签定，并通过第 12 节故障验收后才能开放真实资金。L3 可退出到 Mantle，不等于 Mantle 停机时可绕过它直接退出 Ethereum。

### 6.3 升级与回退

业务程序、状态 schema、证明验证密钥和接口版本一起管理。新版本必须证明或验证旧状态向新状态的迁移，明确切换批次和未完成消息归属。治理延时、预告和退出机会需覆盖 L3 及其 L2 结算合约。

上线真实资金后的回退通常是停接新单、结算未完成操作、按证明释放资产；不能简单恢复数据库快照。共享组件升级要测试旧版本 L3 能否继续结算，避免一次平台升级同时中断全部应用。

### 6.4 风险隔离与限流

每条 L3 配置独立的托管资产和保险上限。可以共享合约代码，但账户记账、取款权限和额度需要隔离；共享管理密钥仍是共同风险。

速率限制按时间窗口累计流出计算，并定义储备分母、绝对金额上限、窗口边界与合法提现排队规则。它争取发现异常和响应的时间，不能替代正确性证明或保证损失永远不超过某个比例。过于严格的限流也会降低资本效率，需要压力测试。

## 7. 可选扩展及其额外成本

### 7.1 远程保证金与统一授信

远程授信可让用户保留 L2 资产持仓，同时向 L3 分配交易额度。但父链锁资产、子链记权益也是普通桥常见的机制，“资产物理不离 L2”本身不是安全或资本效率保证。

授信必须具备可验证的生命周期：锁定与分配、L3 激活、占用、撤销请求、L3 停止使用、结算剩余负债、L2 解锁。通信超时不能直接返还可能已在 L3 被使用的额度。

对同一抵押物，跨产品承诺的风险预算不得超过扣除既有债务、折价和缓冲后的可用担保能力。若它同时参与 Lending，需要指定清算优先权；若保证金跨多条 L3 实时净额抵销，则需要专门的跨域风险与消息协议。

该扩展提升资金分配灵活性，也削弱了“每条 L3 独立承担损失”的简单边界。不能只计入一个信用签名接口的开发量。

### 7.2 ERC-7683 与快速充值

基础方案不要求 ERC-7683。只有在用户必须直接用 L2 资金执行 L3 动作、且原生充值延迟无法满足体验时，才需要评估 Solver 垫资。

Solver 需验证用户资金可收取、意图未取消、目标动作已完成，并处理重放、履约失败和父链重组。ERC-7683 提供意图互操作接口，不能代替底层履约认证和风险承担规则；其草案接口有版本变化，实现时需锁定版本。[S2]

### 7.3 快速提现

垫资方可在原生提现完成前向用户支付 L2 资产，再领取已分配给自己的提现债权。必须避免用户与垫资方重复领取，并限定原生结算失败时的损失承担。

若使用 TEE 或 Sequencer 签名辅助垫资决策，应限制风险在出资方额度内。直接用这种确认释放原生托管资金，会把提现安全模型改成对该确认机制的信任；后续 ZK 无法追回已经错误支付的资金。[S7]

### 7.4 多条 L3 与隐私执行

新增 L3 可以复用桥接口、节点框架、监控、SDK 和部分证明设施，仍需实现并审计业务状态转换，评估新增 DA、证明、流动性和运维负担。

Private L3 还需定义：谁能看到订单和仓位、见证由谁生成、哪些输入公开、如何进行合规披露、用户如何在运营方失联时退出。TEE 与零知识证明可以参与设计，但不自动解决整个隐私生命周期。

## 8. 三类产品的适配分析

| 产品 | 专用执行的潜在价值 | 必须本地闭环的状态 | 主要新增问题 | 比较时的处理 |
|---|---|---|---|---|
| 高频 Perps | 订单簿、批量验签、撤单与清算调度、状态布局 | 订单、持仓、保证金、资金费和清算 | Oracle、极端行情、保险与证明成本 | 用作详细工作量参考负载 |
| Launchpad + 毕业 AMM | 发行生命周期管理、状态压缩、资源与准入规则 | 曲线、储备、毕业、AMM 和用户权益 | AMM 移植、钱包兼容、失败发行退款 | 先与现有 L2 合约方案同负载对比，不能仅凭免 Gas 决定建链 |
| 机构隐私交易 | 特定准入、数据披露和执行规则 | 订单权限、隐私状态、成交与结算授权 | 密钥、DA、隐私泄露与合规退出 | 单独技术方案，不包含在普通公开 L3 的基础报价中 |

股票 Perps 增加市场日历、休市风险、价格源、公司行动、资产冻结与赎回差异等要求。跨层现货和 Perps 两腿不是原子执行，仍有基差、资金费、流动性和清算风险。链上交易全天开放不代表底层股票市场全天可对冲。

## 9. 优势、劣势与适用边界

### 9.1 优势及成立条件

| 优势 | 机制 | 成立条件 |
|---|---|---|
| 业务执行可定制 | 原生交易类型、状态布局、排序和费用规则 | 这些规则能确定性重放并进入证明程序 |
| 应用资源可隔离 | 独立执行节点、队列与预算 | L2 结算拥堵、共享证明器和共享运维仍需管理 |
| 降低 L2 核心改造面 | 主要在 L2 部署结算合约 | 特殊 verifier 所需能力已受支持，否则要重新计算 L2 改造成本 |
| 应用升级节奏更独立 | L3 程序版本与业务发布单独管理 | L2 验证密钥、状态迁移和用户退出同步安排 |
| 可能降低单位证明成本 | 更紧凑的业务语义和数据结构 | 同安全等级、同负载实测优于通用执行 |
| 保留 Mantle 资产入口 | 在 Mantle 托管和结算 | 跨层资金分配对用户及做市商可接受 |

### 9.2 劣势及缓解成本

| 劣势 | 具体后果 | 缓解手段与代价 |
|---|---|---|
| 跨层非原子 | 充值、额度释放和提现具有中间状态 | 重组依赖、去重、补偿及明确的确认策略 |
| 流动性与保证金分配 | 可用资金分散在不同执行域 | 预存资金、异步再平衡；统一授信另计开发和风险 |
| 多一套基础设施 | 节点、证明、索引、RPC、监控与值班 | 共享平台可降低重复工作，不能消除每链责任 |
| 父链依赖仍存在 | L2 故障或升级影响 L3 结算 | 限制未结算敞口、设计暂停和恢复 |
| 新增安全边界 | 桥、Verifier、DA、升级、退出都可能出错 | 多轮审计、故障演练、限额上线 |
| 非 EVM 生态成本 | 现成合约和工具不能完全复用 | 专用 SDK / 索引，或承担嵌入 EVM 的成本 |
| 低负载固定成本高 | 业务量少时每笔摊销可能更贵 | 先验证单条链的单位经济，再扩多链 |

L3 更适合高频内部操作、低频跨层结算。实时跨层组合频繁时，MantleCore 或现有 L2 合约路线应保留在比较中。

## 10. 开发范围与复用边界

### 10.1 需要交付的成果

基础方案交付一个产品的执行程序、可重放节点、证明程序、L2 结算合约、DA 发布与恢复工具、强制请求和退出机制、API / SDK / 索引、监控与运行手册，以及审计和限额上线所需的测试材料。

现有 SP1、密码学库、数据库、网络库和 Mantle 合约环境可以复用。现成 EVM Rollup 框架与 RaaS 是否支持任意原生状态机，需要逐项确认；不能将“一键部署 EVM 链”的报价作为本方案的实现成本。

Lighter 的公开 prover 与 contracts 仓库提供了更具体的参考，但固定版本采用 BSL 1.1、无额外生产使用授权，且本轮未取得完整生产运行服务包。第 11 节估计不因“代码公开”自动下调。获得适用授权与完整实现后，再按工作包扣除可复用部分并计入父链、DA、证明和审计适配量，详见 [11 第 10 节](11-lighter-reference-for-mantle-l3.md#10-代码复用与开发工作量的影响)。

### 10.2 不计入基础开发量的范围

- 三条 L3 同时上线，或任意第三方自助部署平台；
- 完整股票资产生命周期与发行人系统集成；
- 跨 L3 实时统一保证金、生息抵押和信用扩张；
- Solver 网络、快速提现营运资本和第三方桥接；
- 隐私暗池、KYC/KYB 服务采购与法务合规；
- 做市策略、流动性激励、机构分销和完整交易终端。

基础范围包含最小可交易界面 / SDK 集成所需的接口验证，不包含重新开发一个完整商业交易终端。

## 11. 开发工作量、周期与运营成本

### 11.1 估算性质与假设

以下为**用于路线比较的 ROM（数量级）工程估算**，由工作包拆解得出，不是供应商报价、已完成代码盘点或交付承诺，置信度为低至中。没有部署或压测本方案，时间和成本不能视为实测结果。

假设：从现有通用库和证明框架出发；没有一套已审计、可直接移植的同等原生 Perps；首条链采用单一稳定币保证金、有限市场、集中排序、公开 DA 和 ZK 结算；团队拥有 Rollup、合约、证明和交易风控经验。

“1 人月”指 1 名全职工程人员约 1 个月工作量。表中不含外部审计报价、基础设施账单、流动性本金与营销费用；含团队配合审计及修复的工作。

| 审计配合、修复与限额发布 | 修复记录、部署与回退演练、发布材料 | 3–5 | 规格冻结及外部审计结果 |
| **合计** | **单条公开 Perps L3 基础闭环** | **42–68** | **工作包可部分并行** |

按 25%–35% 的规划缓冲计算，预算工作量约 **53–92 人月**。缓冲用于跨模块返工、招聘磨合和审计修复，不代表故障一定可以在该范围内解决。

### 11.3 团队配置与日历周期

参考团队为 8–10 名全职工程人员：协议 / 执行 2–3 人，证明 1–2 人，合约 / 桥 2 人，API / SDK 1 人，QA / SRE 2 人；此外需要产品风控、安全评审和外部审计参与。

若按 8–10 人、65%–80% 的可用于上述交付的有效产能折算，53–92 人月约对应 7–18 个月的容量区间。考虑证明、结算和退出闭环的顺序依赖，**规划窗口暂取 9–18 个月达到首条链限额生产条件**。这是容量与关键路径估计，不是只靠加人就能压缩的排期；审计档期和关键岗位空缺可能继续拉长周期。

交付门槛按成果划分，不用固定日期代替验收：

| 门槛 | 独立可用的成果 | 不允许提前宣称 |
|---|---|---|
| G1 执行与证明基准 | 可重放的业务模型、代表性负载和初步证明成本报告，可用于选型 | 生产安全、正式 TPS 或资金接入 |
| G2 完整测试网 | 充值、交易、证明、提现、重组和退出在无真实资金环境闭环 | 可以省略退出与故障演练上线 |
| G3 限额生产 | 审计、修复、运行手册及风险参数签定，限定资产和敞口 | 已支持全部股票市场、多链授信和隐私交易 |
| G4 扩容或扩产品 | 在实际负载和事故演练结果支持下提高限额或部署第二应用 | 第二条链无需重新审计业务状态机 |

### 11.4 可选扩展的增量工作量

| 扩展 | 增量直接人月估计 | 估算边界 |
|---|---:|---|
| 第二个公开应用 L3，如 Launchpad + AMM | 12–24 | 复用已稳定框架，包含新业务、状态和证明适配；不复制整个首链成本 |
| 有限的跨层授信 | 8–16 | 按 L3 分配锁定额度、撤回握手和风险接口；不含实时跨域组合保证金 |
| Solver 意图 / 快速充提 | 4–8 | 集成一个履约与结算模型；不含流动性本金和开放网络建设 |
| 股票市场专项风控 | 6–12 | 市场日历、价格源、公司行动与冻结 / 赎回处理；不含许可与发行集成 |
| Private L3 | 需独立 ROM | 隐私模型、DA、证明与退出尚未定义，不能按公开链复制成本承诺 |

这些工作包存在重叠，不能机械相加；若要组合上线，需要按最终 scope 重新排期。跨域实时组合保证金与完全去中心化排序没有包含在本估算内。

### 11.5 预算与持续运营

人员预算按「预算人月 × 全成本人月单价」计算。比如，仅作敏感性示例，若取人民币 10 万元 / 人月，53–92 人月对应约 **530–920 万元人员成本**；该单价不是招聘报价，外部审计、硬件 / 云、DA 和运营本金另列。

持续成本至少包含：Sequencer 与备机、Prover、DA、L2 结算交易、RPC / 索引、存储和流量、监控值班、安全更新与定期演练。比较单位成本时记录：

> 每单位业务成本 = 执行、证明、DA 与结算的可变成本 + 固定运行成本按实际业务量分摊。

不要只按“成交笔数”摊销：高撤单比订单簿需要同时统计订单操作数、成交数、状态读写和已证明工作量。低负载时 L3 的固定成本可能高于在现有 L2 部署合约。

快速充提池所需本金应依据流量、结算滞后和极端挤兑计算，不能先指定固定金额。参考量为“高分位待结算净支付敞口 + 风险缓冲”，而非日均交易量的任意比例。

## 12. 选型前需要取得的证据

### 12.1 性能和成本测量

| 测量 | 统一口径 |
|---|---|
| 订单性能 | 提交、接收、执行、回执的 p50 / p95 / p99；附网络位置、负载和拒单率 |
| 持续吞吐 | 给定市场与账户规模、撤单比下，可持续执行且证明不持续积压的操作数 |
| 证明成本 | 硬件、程序版本、批次大小、交易组合、时间、内存、费用和失败重试 |
| 充提延迟 | L2 提交至 L3 可交易，以及 L3 申请至 L2 可用；明确确认级别 |
| DA 和结算 | 每批字节、状态增长、L2 Gas，以及对父层证明工作负载的影响 |
| 资本占用 | 托管额度、闲置保证金、待结算权益和垫资本金 |

50ms 等数字只能作为指定条件下的产品目标，必须明确指回执、执行还是最终结算，不能把不同时间口径横向比较。

### 12.2 正确性与故障验收

必须覆盖：重复或乱序充值、父链重组、交易与提现竞争、授信撤回竞争（若启用）、预言机失效、证明积压、Sequencer 停机、DA 不可用、版本升级和用户独立退出。对资产冻结型代币还应覆盖付款失败及重试，避免领取标记与实际支付失配。

通过条件包括：资金记账守恒，授权不可绕过，消息只生效一次，独立重放结果一致，单条 L3 无权动用其他托管资产，退出与升级不依赖临时人工发明的规则。

### 12.3 影响立项判断的开放决策

| 决策 | 负责角色 | 需要的证据 | 未解决时的影响 |
|---|---|---|---|
| 首个产品与目标负载 | 产品 + 交易工程 | 同负载下现有 L2、Core、L3 的能力差距 | 不能判断专用执行收益是否足够 |
| 证明实现和硬件 | 证明工程 | 代表性 Guest 基准和 Verifier 兼容性 | 人月与运营费用无法收敛 |
| DA 模式 | 协议 + 安全 | 数据恢复演示和成本曲线 | 无法确定退出保障和安全模型 |
| 确认与敞口策略 | 协议 + 风控 | 重组恢复测试、资金暴露分析 | 不能承诺充提体验或开放真实资金 |
| 退出与治理参数 | 安全 + 风控 + 治理 | 故障演练、升级与退出安排 | 阻断生产上线 |
| 实际复用资产与团队 | 工程负责人 | 代码盘点、人员可用性和审计档期 | ROM 不能转成承诺排期 |

这些开放项是比较阶段需要展示的决策成本。本文是路线说明与评估材料，不把它们包装成已完成的工程设计。

## 13. 对早期文档的修正说明

[06 跨层草案](06-cross-layer-interop-and-composability.md)、[08 MantleCore 推演](08-route-2-hypercore-dual-engine-deep-dive.md)和 [10 Base 报告](10-base-l3-and-appchain-research.md)保留作为早期材料。以下结论在本轮比较中不再采用：

| 早期说法 | 本轮采用的边界 |
|---|---|
| L3 是唯一正确路线 | 三条路线按同一产品负载、资本效率、成本和风险比较 |
| FCR 把 finalized 改成约 13 秒 | FCR 是带同步性假设的快速确认规则，不改变 FFG finalized 的含义；也不能直接套到无该共识结构的 L2 [S8] |
| Based 排序绝不可能提供快速用户反馈 | 父链排序与预确认是不同层次；如选该分支，须另计机制和安全假设 |
| 资产留 L2 就安全且可重复生息 | 安全取决于取款权限、负债归属和额度约束；同一抵押物不能被无约束重复承诺 |
| Sequencer 签名等于 ZK 结算 | 原生兑付必须服从选定证明模型；签名可供独立出资方作风险判断 |
| 2% 熔断永久封死风险 | 需要累计检查和响应流程，只能减缓损失；06 示例的比例条件实际检查单笔金额 |
| FIFO、撤单优先保证零 MEV、零穿仓 | 分别需要可执行的排序约束和完整风险机制，不能作绝对保证 |
| 自定义 SP1 程序必须手写电路 | zkVM 可运行可证明的业务程序；只有特定优化可能需要定制密码学组件 |
| 同进程意味着任意跨模块原子调用 | 原子性由执行与提交规则定义，排队动作仍可能跨块 [S3] |
| Base 存在 Appchain 实现证明 Mantle 必须选择 L3 | 实现提供可参考机制，不能替代 Mantle 自身的成本和产品适配验证 |
