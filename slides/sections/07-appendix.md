### A01｜账户方案怎样放在同一组场景里比较

**本页要讲什么**

建议让候选账户方案完成同一组正常、失败和撤销操作，再比较成本、交易能否及时被纳入，以及接入和维护负担。方案是否支持某项标准，不能直接代替这些场景的验证结果。

**对应原文**

- [2.2.2 低延迟执行与状态反馈：让交易者知道操作何时真正生效](../references/chain-infra.mdx)
- [3.1 目前已支持的 AA 方案综述](../references/chain-infra.mdx)
- [3.2 评估 Native AA 的增量价值](../references/chain-infra.mdx)

以下场景与记录方式是据原文需求整理的验证建议，原文未给出完整测试清单或通过阈值。

**需要的图文及原因**

用一张“场景与检查项”短表，列出正常操作、失败重试、撤销权限和滥用请求。每个场景对应可观察的执行结果，避免用“支持授权”“支持代付”等功能名称判定方案可用。表后列出各方案共同记录的成本和维护项，便于回答原生账户方案究竟改善了什么。

**上屏文案**

标题：账户方案怎样放在同一组场景里比较

建议：候选方案使用同一组操作与负载。

| 场景 | 检查项 |
| :-- | :-- |
| 正常操作 | 限权交易、独立队列、费用代付 |
| 失败重试 | 越权被拒；多次重试只执行一次 |
| 撤销权限 | 撤销生效后，旧授权无法再执行 |
| 滥用请求 | 超预算停付；无效请求受限 |

共同记录：请求进入区块的时间、执行成本、工具兼容与长期维护工作。

**讲述补充（不上屏）**

候选方案包括 ERC-4337，即通过合约与配套服务实现账户抽象；EIP-7702，即让普通账户委托代码执行；以及待评估的原生账户抽象，即把部分账户规则纳入协议。比较的是各自的完整实现，7702 本身不提供完整的限权与撤销机制。撤销试验还应记录撤销操作与待执行请求的先后关系，避免把“已提交撤销”当成“撤销已生效”。原生方案若能改善成本或纳入路径，还需评估无效请求耗尽资源的风险，以及客户端、验证系统和工具适配的新增工作。

### A02｜Agent 配套和状态剪枝做到什么范围

**本页要讲什么**

Agent 是代用户执行操作的程序。开发工具、事件订阅、审计和故障恢复可按产品需要补齐；状态剪枝要单独确认数据边界。原文仅将剪枝列为可选项，没有指定删除对象，不能据此推导出可以删除用户余额或有效权限。

**对应原文**

- [1.1.4 抽象出的 chain infra 需求](../references/chain-infra.mdx)，其中“其余 infra（Optional）”列出可选配套与状态剪枝。
- [2.2.1 账户模型：为自动化参与提供受约束的执行能力](../references/chain-infra.mdx)
- [2.2.2 低延迟执行与状态反馈：让交易者知道操作何时真正生效](../references/chain-infra.mdx)

剪枝的数据保留与恢复边界是补充建议，原文没有给出具体方案。

**需要的图文及原因**

用短表说明三组配套各自帮助 Agent 完成什么：开发工具负责调用，订阅与审计负责追踪，恢复机制负责故障后继续操作。另列剪枝的定义与建议边界，让听众区分节点减少数据保留和账户资产状态被删除，避免把四项工作视为一个必须整体建设的系统。

**上屏文案**

标题：Agent 配套和状态剪枝做到什么范围

配套按产品需要补齐。

| 配套 | 用途 |
| :-- | :-- |
| SDK（开发工具包） | 接入授权与交易调用 |
| 订阅与审计 | 接收状态变化，追踪谁授权、谁执行 |
| 故障恢复 | 断线后补查状态，重试不重复执行 |

状态剪枝：清理无需继续保留的数据。

边界建议：保留当前余额与有效权限，确保恢复所需数据可得。

**讲述补充（不上屏）**

实施剪枝前，建议明确哪些数据从节点清理、哪里仍可取得恢复所需数据，以及怎样验证恢复结果。原文没有指定保留周期或存储方案，本页不作选择。具体配套仍需满足已选产品流程的可靠性要求，不能因原文标为可选就省去必要的失败处理。

### A03｜验证结果怎样才可比较

**本页要讲什么**

产品是否带来持续交易，与基础设施能否稳定执行，需要分别记录再对照。报价应在相同订单规模下比较；时延要说明起止状态；故障试验要覆盖恢复与退出。新增采样方式属于建议，不代表已有数据或验收标准。

**上屏文案**

标题：验证结果怎样才可比较

| 对象 | 记录口径 |
| :-- | :-- |
| 产品 | 同规模订单的报价偏离、滑点、可成交量；成交用户与再次交易用户 |
| 时延 | 分别记录接收、执行反馈、结算确认的时间；提前反馈不等于最终确认 |
| 拥堵与故障 | 关键操作能否执行，积压能否消退，状态能否恢复、用户能否退出 |

采样建议：统一负载和窗口，同时报告典型与最慢一批请求的表现。

**讲述补充（不上屏）**

报价偏离指报价与选定参考价格的差距，滑点指实际成交价与提交时预期价格的差距；建议固定参考价格来源、订单规模和采样时点。再次交易用户也应约定观察窗口和统计方式。时延需注明采用哪一级确认，混合撮合还要单列链下成交到链上结算的等待。故障试验按方案检查节点断线、结算停滞，以及适用时的数据发布或验证积压；退出检查需遵循该方案的实际安全条件。原文没有给出通过阈值，应由首批验证任务另行确定。

### CA｜可用性要在失败与恢复中验证

**本页要讲什么**

附录给出的共同判断是：正常交易成功只是可用性的一部分，授权、费用和资金边界在失败、重试与恢复时也要成立。可比较的结果必须使用一致业务口径；配套工具或存储优化也不能牺牲资产权益与恢复能力。

**对应原文**

[2.2.1 账户模型：为自动化参与提供受约束的执行能力](../references/chain-infra.mdx)、[2.2.2 低延迟执行与状态反馈：让交易者知道操作何时真正生效](../references/chain-infra.mdx)、[3.2 评估 Native AA 的增量价值](../references/chain-infra.mdx) 及第 4 章的恢复与退出要求。本章依据：A01 的正反向账户场景、A02 的恢复与剪枝边界、A03 的比较口径。

**需要的图文及原因**

用三条验收结论收束，不再罗列所有测试用例。将正常可执行、异常仍守约束、结果可比较这三件事讲清楚，末尾明确验收门槛的来源。本页可在附录问答结束时展示，不要求每次跳看一个附录页后都重复播放。

**上屏文案**

标题：可用性要在失败与恢复中验证

- 正常能成交，越权要被拒绝，重试不能重复执行，撤权要真正生效。
- 比较使用同一资产、订单规模、费用和确认口径，也记录失败与最慢请求。
- 故障后能恢复并处理退出，优化与剪枝不能丢失有效权益。

验收门槛根据产品目标与基线预先约定，不能用一次成功演示代替。

**讲述补充（不上屏）**

本页总结验证方法，不声称测试已经通过。正常、失败和恢复路径由具体产品选取，不能把不同风险模型的结果混为统一性能排名。
