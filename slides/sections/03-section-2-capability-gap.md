### P23｜低延迟执行与状态反馈：让交易者知道操作何时真正生效

**本页要讲什么**

原文关注的是完整执行路径，而不仅是缩短区块。Launchpad 要知道创建、买入、毕业迁移是否完成；Perps 要知道撤单、新订单、仓位和保证金是否已生效。围绕这些结果，分别优化执行反馈、可靠接口和拥堵信息。

**对应原文**

[2.2.2 低延迟执行与状态反馈：让交易者知道操作何时真正生效](../references/chain-infra.mdx)。

**需要的图文及原因**

用“交易接收—执行—回执输出—状态读取”的路径图承接原文。Launchpad 与 Perps 各给一个结果标签，说明它们关心的生效状态。路径下保留原文三个优化组：更短区块或区块内增量反馈；可靠提交、查询与订阅；拥堵、费用分位和等待区间。不要再次用一张确认级别百科表替代本页的优化方向。

**上屏文案**

标题：低延迟执行与状态反馈：让交易者知道操作何时真正生效

Launchpad：创建、买入、迁移完成了吗？
Perps：撤单、新单、仓位与保证金更新生效了吗？

执行路径：接收 → 执行 → 回执 → 状态读取。

优化方向：

- 更短区块，或区块内增量反馈。
- 可靠提交与订阅：去重、查询、断线恢复、失败原因。
- 提供拥堵程度、费用分位和预计等待区间。

**讲述补充（不上屏）**

“去重”指幂等请求，多次提交同一业务动作不重复生效；“费用分位”让 Agent 了解近期不同费用水平对应的拥堵情况。配合预计等待区间，Agent 才能判断继续等待、调整策略或放弃操作。提前输出回执不等于最终性，缩短区块也不自动提高持续处理能力；这些是实现时的边界，不改变本页三组优化的主线。

**本页要讲什么**

从原文的两种突发负载出发：Launchpad 发行抢购与 Agent 重试，Perps 剧烈行情下集中撤单、调价、补保证金和清算。按干预程度归纳三层优化，目的是让其他应用仍有可预测的执行能力。

**对应原文**

**上屏文案**

标题：资源与费用隔离：避免热点业务挤占整个生态

| 层次 | 优化方向 |
| :-- | :-- |
| 入口与服务 | 限流、防滥用、代付预算、队列与背压 |

**上屏文案**

| :-- | :-- |
