## 1.1 Meme Launchpad

### P09｜曲线决定初始报价，毕业接续二级交易

**本页要讲什么**

先把 Bonding Curve 解释为合约采用的报价规则，再用不同曲线说明“价格怎样随买卖变化”。重点不是曲线长得像上涨行情，而是用户直接与合约按规则交换代币。达到毕业门槛后，需要把真实募集资产和预留代币配置成二级市场流动性；分笔迁移会暴露中间状态。

**对应原文**

本轮用户对曲线示例和非原子迁移的要求；[1.1.3 展示完整 workflow](../references/chain-infra.mdx)；[Launchpad 基础机制材料](../../2-meme-launchpad/outputs/02-meme-launchpad-fundamentals.md) §2–3。公式和迁移边界统一按 [曲线与 v4 核对笔记](../references/bonding-curve-v4-graduation.md) 表达。

**需要的图文及原因**

需要一张发行生命周期图，标出创建代币、曲线买卖、毕业条件、真实储备迁移、二级交易。曲线买卖处给三个教学示例：线性、指数、虚拟储备恒定乘积。横轴统一为净售出量，纵轴为下一单位的报价，说明持续买入与卖回的方向；不能画成价格随时间自动上涨，也不把恒定乘积称为指数公式。

- 线性示例 `p(s)=a+b·s`：每增加相同净售出量，下一单位的报价按固定幅度提高。
- 指数示例 `p(s)=a·exp(b·s)`：报价提高的幅度随净售出量增大。
- 虚拟储备 CPMM：`(x+v_x)(y+v_y)=k`，`x/y` 为真实计价资产与 Meme 库存，`v_x/v_y` 为虚拟偏移。买卖改变储备比，后续报价随之改变。

本页毕业分支必须画出“转真实储备、建池/加流动性”，并标注非原子迁移的空窗与中途失败风险，不能只用一个“毕业”箭头跳过。下一页专门解释这个缺口，为后面的 v4 做铺垫。

**上屏文案**

标题：曲线决定初始报价，毕业接续二级交易

Bonding Curve：合约按净售出量或储备变化计算报价。

发行：创建代币，设定曲线与毕业门槛。

- 线性：按固定斜率加价。
- 指数：越往后，加价越快。
- 虚拟储备 CPMM：`(x+vₓ)(y+vᵧ)=k`，买卖改变储备比。

x/y 是真实储备，v 为虚拟偏移。

曲线坐标：净售出量 / 下一单位报价。

毕业：停曲线 → 转真实储备 → 建池加流动性 → 二级交易。

分笔迁移会留下交易空窗、抢先操作和中途失败的风险。

**讲述补充（不上屏）**

Bonding Curve 是定价规则的统称，上面列的是教学形状，不代表每个 Launchpad 都采用同一套公式。卖出是否开放、如何反向计算及什么时候停止交易，由产品规则决定。线性和指数中的 `s` 为净售出量，`p(s)` 是边际价格；大额订单要按整段曲线或储备变化计算，不能直接用买前单价乘数量。

虚拟储备可以降低创作者先配齐双边 LP 的需求，但它不是真实可提取资金。一个忽略费用的例子：真实计价储备为 0，Meme 库存为 1000，虚拟计价储备为 10；第一笔投入 1 单位可以买约 90.91 个 Meme，第二笔同样投入 1 单位只能买约 75.76 个。两笔之间报价变化来自买卖状态，不来自经过了多少时间。具体算式见核对笔记。

直接在普通 AMM 建池要有实际流动性与初始化价格。曲线提供一套启动与定价过程，但不能天然消除抢跑 Bot、排序优势或夹子；这些仍需交易条件与排序机制处理。

### P09A｜毕业迁移需要把资金、价格和交易状态一起交接

**本页要讲什么**

讲清毕业到底迁移什么，以及非原子操作为什么会产生空窗。发行曲线停止后，真实计价资产与预留 Meme 需要形成二级池，价格、LP 权益和开放状态必须同时正确。跨合约可以做成原子交易，真正的问题是把这些变更拆开提交并暴露可被其他交易改变的中间状态。

**对应原文**

[1.1.3 展示完整 workflow](../references/chain-infra.mdx) 的流动性迁移；[2.2.5 交易可组合性：让完整业务动作共同成功或失败](../references/chain-infra.mdx)；本轮用户提出的非原子迁移问题。细节见 [曲线与 v4 核对笔记](../references/bonding-curve-v4-graduation.md) §2。

**需要的图文及原因**

需要“分笔迁移”和“原子接续”两条对照流程。分笔流程依次为停止旧曲线、确定/转出真实储备、初始化目标池、添加流动性并开放交易；在提交间隔标出用户不能交易、目标池被抢先初始化或价格改变、后续失败留下中间状态的可能性。

原子流程把目标池和价格校验、真实 LP 配置、阶段切换纳入同一组提交条件，任一步失败共同回滚。把“虚拟储备不能迁入”“原子性不能修复错误初始价格”写清楚，避免将 v4 的优势建立在“旧协议都无法原子迁移”的错误前提上。

**上屏文案**

标题：毕业迁移需要把资金、价格和交易状态一起交接

迁移资产：真实募集资金 + 预留 Meme，虚拟储备不在其中。

分笔执行：停曲线 → 转储备 → 初始化池 → 加流动性。

中间窗口可能出现：无法交易、抢先初始化或调价、后续失败卡住资金。

目标：校验价格、配置 LP、切换阶段一起生效，失败一起回滚。

跨合约也能原子化；原子性仍不能替代正确的价格与资产校验。

**讲述补充（不上屏）**

抢先初始化是否可利用取决于目标池的权限和验证。即使迁移本身在一笔交易内，未验证已有池身份、价格或储备比例，仍可能把资产加入错误状态。非原子窗口是额外风险，不是所有迁移攻击的唯一原因。

v2/v3 的同链合约可通过正确的 Router/迁移器编排在同一交易内完成多步操作。v4 的优势是更容易把两个阶段纳入同一池的可编程生命周期与结算路径，而不是它发明了原子性。下面先完成产品复盘与 Agent 设计，再在 P12A/P12B 解释 v4 的具体适配。

### P11A｜同一条打新流程，底层实现发生了什么变化

**本页要讲什么**

沿用 P11 的六步，把用户看到的自动化体验拆到账户、任务服务、提交路径、社区接口和合约事件。对照基线是普通 EOA 钱包与手工操作；新方案将权限、并发、代付与恢复做成可持续执行的能力。合约仍负责曲线定价与毕业，Agent 负责在规则内编排任务。

**对应原文**

本轮用户要求的开发者对比；[1.1.3 展示完整 workflow](../references/chain-infra.mdx)、[1.1.4 抽象出的 chain infra 需求](../references/chain-infra.mdx)、[2.2.1 账户模型：为自动化参与提供受约束的执行能力](../references/chain-infra.mdx)。候选实现依据见 [方案核对笔记](../references/agent-launchpad-implementation-notes.md)。

**需要的图文及原因**

复用 P11 的节点和顺序，每一步增加“普通 EOA 接入”和“Agent 产品”两种实现。资金路径、Moltbook 和毕业去向均不变，减去对话气泡与用户操作细节，把重点转到能力分工：

- 下指令：从用户手工填写订单，变为意图解析、策略参数与稳定任务 ID。
- 钱包接单：从逐笔签名，变为 AA 账户通过 Session keys 强制校验合约、函数、预算、期限与撤销。
- 买入：从准备原生 gas、按账户顺序发单，变为独立 nonce 通道与受预算约束的 Gas Sponsor，调用兑换和曲线合约；并发任务共享同一总预算。
- 社区传播：从人工发帖，变为 Agent 调用社区 API 并关联任务和身份；这是链下服务，不在钱包合约中运行社交推理。
- 毕业：两边都由合约判断条件；Agent 系统订阅事件，切换二级交易路径。
- 卖出汇报：从手动卖出和查看结果，变为按策略退出、业务去重、回执确认与事件恢复。

图中资金仍经过 USDC、mStocks、Meme，并在卖出时反向返回。候选 EIP 与费用隔离的细节放到 P13，避免同一页同时展开完整协议规范。

**讲述补充（不上屏）**

### P12A｜为什么优先用 Uniswap v4 承接发行与毕业

**本页要讲什么**

回应前面曲线与迁移问题，把 v4 作为本方案优先评估的发行和毕业底座。Singleton 降低大量新池的部署负担，Flash Accounting 改善多步资金操作，Hooks 让一个池承载不同阶段的交易规则。这三项组合更贴近 Meme 从启动到二级市场的完整生命周期。

**对应原文**

本轮用户对 Uniswap v4 特性的说明；[1.1.3 展示完整 workflow](../references/chain-infra.mdx)、[2.2.5 交易可组合性：让完整业务动作共同成功或失败](../references/chain-infra.mdx)。机制依据为 [Uniswap v4 Flash Accounting](https://docs.uniswap.org/contracts/v4/concepts/flash-accounting)、[Hooks](https://docs.uniswap.org/contracts/v4/concepts/hooks) 与 [固定版本源码核对](../references/bonding-curve-v4-graduation.md)。

**需要的图文及原因**

需要一张三项功能与 Launchpad 用途的对应图，不只列技术名词。

- Singleton：v2 每个 Pair、v3 每个 Pool 有独立池合约；v4 由 PoolManager 管理不同 PoolId。对应大量新 Meme 建池时减少独立池合约部署。Meme 代币合约与 Hook 的部署不能画成消失。
- Flash Accounting：同一次 unlock 中，多跳兑换和流动性调整先记 delta，最后按账户和币种结清。用 mStocks/Meme 与另一个兑换池示意减少中间转账，不写每跳固定两次 transfer 的普遍结论。
- Hooks：在初始化、增减流动性、swap 等回调加入产品规则，使发行曲线与毕业后交易可以使用不同逻辑。鉴权或 KYB 是可实现的策略，不是 v4 自动提供的服务。

页面需要说明为何偏向 v4，但不宣称行业所有 Launchpad 已选择它，也不填未经基准验证的 gas 降幅。

**上屏文案**

标题：为什么优先用 Uniswap v4 承接发行与毕业

| v4 能力 | 对 Launchpad 的作用 |
| :-- | :-- |
| Singleton | 一个 PoolManager 管理多个池，减少逐池部署 |

**讲述补充（不上屏）**

本次源码版本有 10 个生命周期回调，另有 4 个返回 delta 权限；不沿用“8 个节点”的概括。Transient storage 是交易内有效的瞬态存储，不是普通内存。

单例并不免除创建 Meme 代币、配置 PoolKey、初始化价格和准备真实资产。v4 减少的部署与转账成本需要连同 Hook 开销、账户路径和目标链环境一起实测，不能直接承诺从几十万 gas 降到几万。该选择首先适用于本方案的合约产品路径，不能据此锁定后续所有专用执行域都采用同一实现。

### P12B｜同一个 v4 池，发行期走曲线，毕业后走真实 LP

**本页要讲什么**

讲清 Hooks 怎样把两阶段产品放进同一池：发行期在 beforeSwap 中按虚拟储备公式计算收付，借助 BeforeSwapDelta 接管原生定价；毕业时用真实储备配置 LP 和价格，再让原生集中流动性交易接续。PoolManager 始终负责相应账户与资产账务，Hook 不会凭空创造资金。

**对应原文**

本轮用户提出的 Hook 自定义曲线与 NoOp 思路；[1.1.3 展示完整 workflow](../references/chain-infra.mdx)、[2.2.5 交易可组合性：让完整业务动作共同成功或失败](../references/chain-infra.mdx)；[Uniswap Custom Accounting](https://docs.uniswap.org/contracts/v4/guides/custom-accounting)。精确调用与符号见 [核对笔记](../references/bonding-curve-v4-graduation.md) §5–7。

**需要的图文及原因**

需要同一个 mStocks/Meme PoolId 的三阶段图，PoolManager 与 Hook 分开画。

1. 发行期：用户/Router 提交 swap，PoolManager 调用 Hook 的 beforeSwap，Hook 用 `(x+v_x)(y+v_y)=k` 算出真实应收和应付数量。开启 beforeSwapReturnDelta 权限后返回 BeforeSwapDelta，将原生 swap 的剩余数量抵消为零；Hook 与调用者仍须完成真实收付结算。
2. 毕业转换：验证门槛，检查真实 mStocks 与 Meme 库存、扣费和剩余资产，衔接原生池价格、LP 区间与权益，并将阶段标志一起提交。任何必要条件失败，不能只保留一个已经毕业的标志。
3. 公开交易期：同一个 Hook 的分支不再抵消正常 swap 数量，由真实 LP 支持原生 AMM 交易。可保留产品确需的权限和费用规则，不能假定 PoolKey 中的 Hook 地址可以随意替换。

“beforeSwapReturnDelta”必须画成 beforeSwap 的返回权限标记，不画成独立回调节点。NoOp 标在“原生 swap 剩余数量为零”这一步，不画成整个 PoolManager 停止运行。

**上屏文案**

标题：同一个 v4 池，发行期走曲线，毕业后走真实 LP

发行期：beforeSwap 按虚拟储备曲线计算收付，返回 BeforeSwapDelta。

NoOp 效果：抵消原生 swap 的剩余数量；真实资产仍须结清。

毕业：用真实储备配置价格与 LP，和阶段切换一起生效。

公开交易：停止曲线接管，由原生 AMM 与真实 LP 继续报价。

同一 PoolId 接续，不等于只切换一个布尔值。

**讲述补充（不上屏）**

固定输入为 q 时，调用参数的 amountSpecified 为 -q。Hook 的 specified delta 取 +q，则原生 amountToSwap 为零；另一币种的 delta 表达 Hook 应支付的 Meme。Pool.swap 对零剩余量返回零原生 delta，但外部 swap 输入本身不能是零。余额仍由真实资产或适用的合法 claim 结清，每次 unlock 返回时不能残留未结 delta。

beforeSwapReturnDelta 是权限；实际回调为 beforeSwap。此处不是新增一个叫 NoOp 的操作码，也不是无条件关闭原生引擎。对卖出、exact-output、费用、取整和跨毕业阈值的大单仍需分别设计。

发行曲线期间原生池价格未必同步变化，毕业时要正确衔接 sqrtPrice 与 LP 配置，不能重复 initialize 同一 PoolId 或直接改 PoolManager 存储。是否能在同池完成安全转换需实现验证；若必须改变 PoolKey，要明确新池与原子接续流程。v4 不自动防止 MEV、错误定价或未经授权的资产操作。

- **自动重试**：任务服务持久化 `requestId → txHash/userOpHash + nonce`，重复请求复用同一任务；通过交易/UserOperation 回执判断实际执行结果，订阅事件并在断线后补查。应用允许不同交易重试同一动作时，需在链上检查已处理的 operationId。遇过期报价、失败或重组重新核对预算与状态，不因 API 超时直接再买一笔。

### P16A｜RFQ 型 Perps：先询价，再接受有效报价

**本页要讲什么**

将原大纲中的 Variational 单独解释，避免把 RFQ 当作 Oracle 资金池。用户先向报价方询价，报价方结合市场与库存返回价格、数量和期限，用户接受后按规则执行与记账。谁报价、谁承担风险、在哪里结算要分别确认。

**对应原文**

[1.2.2 解析不同模式 perps 的运作模式](../references/chain-infra.mdx) 对 Variational RFQ 的说明；[2.2.3 可定制的交易排序：让排序规则服务于具体市场（Optional）](../references/chain-infra.mdx) 的 RFQ 场景。

**需要的图文及原因**

需要“用户询价—做市商报价—用户接受—验证报价—更新仓位”的流程，报价包含价格、数量、有效期。用一条失效分支说明报价已过期或已被撤销时不可继续按旧条件执行。RFQ 可以与不同结算结构结合，不用一条流程强行断言某项目全部逻辑的位置。

**上屏文案**

标题：RFQ 型 Perps：先询价，再接受有效报价

RFQ（询价交易）：

用户提出方向与数量 → 做市商返回价格与期限 → 用户接受 → 检查报价有效性 → 更新仓位。

核心问题：接受、撤销、过期谁先生效？同一报价能否被重复使用？

参考：Variational 的询价模式。它不等同于按 Oracle 价格直接与资金池成交。

**讲述补充（不上屏）**

做市商可能使用 Oracle、库存模型或其他市场来计算报价，背后也可能有池子承担风险；RFQ 描述的是取得与接受报价的方式。报价签名、适用账户、数量、有效期、部分成交和重复执行规则需由产品明确。实际报价与结算架构按所选实现核验，不因叫 RFQ 就假定所有状态已上链可验证。

### P17｜混合订单簿：链下匹配订单，链上结算成交

**本页要讲什么**

解释订单簿如何匹配买卖双方，以及混合模式把哪些工作放在链下。用户的资金由合约托管，高频挂单、撤单和匹配可以在链下完成，成交结果再批量提交链上校验与落账。产品需要管理已成交但尚未结算的状态差距。

**对应原文**

[1.2.2 解析不同模式 perps 的运作模式](../references/chain-infra.mdx) 的混合撮合部分；[4.2.2 混合撮合、链上结算型](../references/chain-infra.mdx)。

**需要的图文及原因**

需要买单、卖单进入同一链下撮合引擎，再把成交批次提交链上的流程。链下部分标“挂单、撤单、匹配”，链上部分标“资金、仓位与结算”。两者之间标“未结算窗口”，说明成交回报不等于链上账本已经更新。这样可直接引出后面的批量结算、保证金预留和故障恢复需求。

**上屏文案**

标题：混合订单簿：链下匹配订单，链上结算成交

用户入金并签署订单。

- 链下：挂单、撤单，按规则匹配买卖。
- 链上：校验成交批次，更新资金与仓位。

两者之间存在未结算窗口，需要预留保证金并限制风险。

参考：Aevo、Aster Pro。

图注：结算通过，不等于已证明撮合没有遗漏更优订单或延迟撤单。

**讲述补充（不上屏）**

资金费如何计算和记账依具体实现而定；原文 4.2.2 中 Aevo 的资金、仓位及资金费支付由合约记录和处理，不能统称为链下账本。普通链上校验可以检查签名、保证金和有效成交，不自动知道所有未提交订单。若要验证完整撮合过程，需要把相应输入和规则也纳入验证范围。

### P18｜可验证订单簿：把撮合与风险规则纳入验证

**本页要讲什么**

第三类路线希望验证给定订单输入是否按规则撮合、仓位和保证金是否正确变化。RISEx、Hyperliquid、Lighter 分别代表通用 EVM 合约、共识执行的专用交易状态机、专用执行加证明三种组织方式。它们解决相似业务问题，但建设工作不同。

**对应原文**

[1.2.2 解析不同模式 perps 的运作模式](../references/chain-infra.mdx) 的可验证订单簿部分；[4.3 面向 Fully Onchain Perps，Chain infra 要求发生了什么变化](../references/chain-infra.mdx)。

**需要的图文及原因**

需要三条相同输入、不同执行与验证位置的路径。输入均为订单与风险操作，输出均为仓位和资金状态。分别标明 EVM 合约、HyperCore 共识执行、专用引擎及结算层验证证明。三者同维度解释，不做未经测试的性能排行，也不把不同链的公开机制当成已可直接部署到 Mantle 的代码包。

**上屏文案**

标题：可验证订单簿：把撮合与风险规则纳入验证

| 参考 | 执行与验证方式 |
| :-- | :-- |
| RISEx | EVM 合约执行撮合和风控，由链验证 |
| Hyperliquid | HyperCore 专门处理交易，由链共识执行 |
| Lighter | 专用引擎执行，向结算层提交状态与计算证明 |

共同目标：给定订单输入，撮合、保证金和清算按规则发生。

图注：公开架构参照；订单纳入与遗漏还需相应规则。

**讲述补充（不上屏）**

通用 EVM 是运行智能合约的执行环境；专用状态机是按固定规则处理订单、仓位和风险的程序。证明用于检查状态变化是否合规，不自动保证交易输入没有被审查或遗漏，也不替代恢复数据和退出机制。资金池同样可以在链上运行；本页的重点是订单簿过程的验证，而非把“链上”作为只有订单簿才具备的属性。

### P19｜资金池、RFQ 与混合撮合，各自需要补什么

**本页要讲什么**

从前三种成交路径分别提炼 Infra 需求。资金池的重点是价格与执行服务及时可靠，RFQ 的重点是报价生命周期，混合模式的重点是成交与结算的状态一致性。应用规则、提交服务与链侧优化要配合，不能把所有问题都归为缩短区块。

**对应原文**

[1.2.3 将不同模式 perps 所需的 chain infra 总结出来](../references/chain-infra.mdx)、[2.2.3 可定制的交易排序：让排序规则服务于具体市场（Optional）](../references/chain-infra.mdx)、[4.2 过渡方案中的工作量分析](../references/chain-infra.mdx)。

**需要的图文及原因**

需要按模型逐行写“最怕什么—需要什么”的简表。价格过期、报价已撤销、重复落账是不同问题，要用不同规则解决。上屏只列关键约束；Oracle 版本、Keeper 预算、报价去重、成交序号、重放与风险上限等细项放在备注，避免一页出现三个完整架构。

**上屏文案**

标题：资金池、RFQ 与混合撮合，各自需要补什么

| 模型 | 核心问题 | 优化方向 |
| :-- | :-- | :-- |
| 资金池 | 价格失效、执行或清算积压 | 价格校验、可靠 Keeper、受限资源保障 |
| RFQ | 旧报价仍被接受、重复成交 | 有效期与撤销顺序、只执行有效数量 |
| 混合撮合 | 成交快于链上落账 | 批量结算、风险预留、去重与恢复 |

先明确产品规则，再优化提交与执行路径。

**讲述补充（不上屏）**

资金池：Keeper 自动提交执行或清算请求，需可靠价格输入、状态查询、费用预算和拥堵处理；资源保障必须有资格检查与反滥用约束。Oracle 价格有效性与清算条件属于产品风控，链不能替产品决定公允价格。

RFQ：签名报价的期限、撤销版本和累计成交数量由合约/协议规则约束，入口限流与快速反馈由服务提供；是否需要特殊排序再依据失效窗口评估。

混合撮合：采用唯一成交标识与序号，重复提交只记一次；限制未结算敞口和积压，明确撤单与部分成交的版本，支持事件重放、对账、暂停恢复与独立退出。链下 API 返回更快，不等于链上结算能力已经提高。

### P20｜共同目标：让用户及时调整风险，并能安全退出

**本页要讲什么**

把产品价值与共用要求收束起来：要让持有人、做市商和策略资金愿意使用 mStocks，报价调整、现货对冲、权限和异常处置都必须可靠。具体优化随模型变化，但验收要回到用户的完整交易与风险处理过程。

**对应原文**

[1.2.4 Perps 这个产品通用的 chain infra 需求](../references/chain-infra.mdx)、[2.1 从产品业务角度统一整理需求](../references/chain-infra.mdx)；[X2](https://x.com/agintender/status/2097276244341792817) 的休市价格风险、[X3](https://x.com/agintender/status/2099324702439407702) 的策略成本与执行条件。

**需要的图文及原因**

用四项用户操作与所需保证对照：报价过期后怎样失效，组合交易怎样避免只成交一腿，不同策略怎样隔离，价格或系统异常时怎样恢复与退出。结尾将这些要求交给 Section 2 的共用能力分析，不在本页预选账户标准或链架构。

**上屏文案**

标题：共同目标：让用户及时调整风险，并能安全退出

- 报价与仓位：知道旧报价何时失效、新仓位何时生效。
- 组合交易：明确现货与对冲的成交条件和回滚范围。
- 账户权限：隔离策略，分开交易与提现授权。
- 异常处理：价格失效或拥堵时按规则降险，保留恢复与退出路径。

这些能力，决定 mStocks 能否被持续交易和用于对冲。

**讲述补充（不上屏）**

订单簿可研究公开的 Cancel Priority（撤单优先）规则；RFQ 处理报价失效，资金池处理订单与价格更新时序，三者不是同一个接口。组合执行必须有同步成交和结果检查，批量发请求不等于原子成交；跨域异步需要另一套风险处理。

价格失效时不能为了保证吞吐强行用旧价清算，应按产品规则限制新增风险、暂停不安全操作并进入恢复流程。除成功路径，还要检验拒单、重复请求、断线、结算停滞与用户退出。这样才能回到本章的产品主张：让资产拥有持续使用的理由，并具备可靠执行这些用途的条件。
