### 2.3 同开销推算

将 RISE 截图的操作预算原样映射到 Mantle，仅作为容量推算：

```text
RISE 截图：1,000 MGas/s
Mantle 样本：60 MGas / 2s = 30 MGas/s
容量比：30 / 1000 = 3%

placeOrder：300 × 3% = 9 次/秒，约 18 次/块
cancelOrder：900 × 3% = 27 次/秒，约 54 次/块

截图反推的预算等效开销：
placeOrder ≈ 1e9 / 300 = 3.333M Gas
cancelOrder ≈ 1e9 / 900 = 1.111M Gas
```

9 与 27 是两种**独占全部 Gas 预算**的情形，不能相加。若每次挂单伴随三次撤单，同口径约为 `30M / (3.333M + 3 × 1.111M) = 4.5` 组/秒，即约 4.5 次挂单加 13.5 次撤单/秒；这些数字还没有给其他应用、Oracle、清算、失败、DA 或证明留下余量。也没有处理持续打满硬上限可能带来的费用变化。

因此能支持的结论是：**Mantle 当前参数不足以直接照搬该开销、该高频目标的订单簿；路线一需要大量链级性能工程。** 不能据此证明“任何规模、任何实现的链上订单簿都不可能”，也不能把这当成 Mantle 已部署 RISEx 的结果。

## 3. Vault 为什么可能被单边行情侵蚀

这里指**作为交易者对手方的池式/预言机 Perps**，不是所有名叫 Vault 的做市策略、保证金账户或理财产品。

[GMX 官方流动性文档](https://docs.gmx.io/docs/providing-liquidity/) 明确讨论 LP 与交易者 PnL、每侧持仓上限、储备比例、PnL 上限和自动减仓。Fully backed 与 synthetic 市场须区分：持有对应标的并限制持仓的池子，可以用资产覆盖相应盈利；不能把单边上涨必然掏空所有池子当成事实。

对稳定币池、无对冲且承接净多头客户的简化模型：

```text
LP 初始权益 C = 1,000,000 USDC
交易者净多头入场名义本金 N = 5,000,000 USDC
价格上涨 r = 20%
交易者净盈利 ≈ N × r = 1,000,000 USDC
LP 剩余权益 ≈ C − N × r = 0
```

假定固定线性头寸、期间不减仓、不对冲、不追加 LP 权益，忽略费用、资金费及其他头寸；客户自有保证金不是额外免费给 LP 的吸收损失资本。净空头客户遇到下跌也有对应风险。上述是风险教学算例，不是 GMX 实际参数或事故复盘。

控制手段会改变过程和极限：按侧 OI/净敞口上限、持仓与抵押资产匹配、外部对冲、动态费率/价格影响、ADL 或利润兑现约束。它们保护池子，也可能降低可开仓规模、强制减仓或影响退出体验，不能一边假设所有控制失效，一边声称成熟协议必然被掏空。

其他需要说明的风险：

| 风险 | 传导 | 交付要求 |
| :-- | :-- | :-- |
| Oracle 过期、被操纵、休市跳空 | 错价成交或不连续的风险估值 | 价格版本/有效期、时段规则、偏离熔断 |
| 清算/Keeper 停顿 | 亏损穿过保证金，形成坏账 | 有界执行预算、减仓通道、保险和损失分摊 |
| LP 提现与已承诺赔付争用流动性 | 先退出者消耗剩余可用资金 | 储备、利用率和赎回规则 |
| 方向敞口积累 | 盈利客户持续侵蚀池权益 | 限仓、动态费用、对冲与减仓 |
| 合约或费用服务故障 | 请求遗漏、重复执行、无法退出 | 可重放事件、幂等执行、暂停与恢复 |

在本项目中，Vault 作为低基础设施门槛的过渡产品，用来验证需求与风控；它没有交付终态要求的可验证订单簿撮合。这个路线判断来自本次产品目标，不能扩大为“所有 Vault Perps 都只能短期存在”。

## 4. 混合模式的收益与风险

链下挂撤/撮合减少链上订单流和 Gas，用户体验可较快上线。链上合约可以验证成交授权、累计成交量和资金变化，但仅有成交结果不足以证明未遗漏更优订单、未延迟撤单或未违反公布的优先规则。

风险与设计要求：撮合服务的审查/停机需链上取消和故障退出；未结算窗口需保证金预留、积压与风险上限；撤单回执与最终失效需版本和截止语义；重放/乱序需唯一成交 ID 与累计量检查；恢复需事件重放、对账与明确确认状态。若要达到本次终态，订单输入承诺、撮合规则及其状态转换都须进入验证范围。

## 6. 路线二的关键：证明复合状态转换

设计目标是 **EVM 与 MantleCore 都在同一个 Mantle L2 内，复合状态由 Mantle 向 Ethereum 提交结算证明**。不能把图画成 Core 结算给 EVM 所在的另一条链，也不能把 HyperBFT 当成 Mantle 的 L1 验证方案。

建议以原稿的阶段模型为首轮 PoC：Core 消费此前已承诺动作并执行本轮原生操作 → EVM 读取这一阶段的确定快照、将成功写动作入队 → 提交本轮 EVM/Core/队列承诺。写动作的生效阶段、拒绝、退款与重试有确定语义；同块读不代表同笔写后读，更不承诺同步成交。

需要证明的内容包括：

1. EVM 执行与状态根更新符合链规则。
2. Core 的订单、撮合、保证金、资金费、清算及状态更新符合确定性规则。
3. CoreReader 返回值来自所承诺的正确快照；宿主机内存返回值不能未经认证进入证明。
4. CoreWriter 只接受成功调用，来源、权限和动作唯一标识正确；队列入队、消费、失败退款均在承诺与证明内。
5. EVM 锁定、Core 记账、跨引擎待处理额度与最终释放保持资产守恒；父链输入、前后态、批次与程序版本绑定。

不能直接把两个根哈希后塞进 Ethereum 兼容的 `stateRoot` 字段并假设账户证明不受影响。应保留 EVM 根语义，在 Mantle 扩展结算输出中认证 Core 根、队列根、版本等，再调整 Guest、聚合和 L1 接受规则。

### zkVM 与专用电路的准确边界

[SP1 官方介绍](https://docs.succinct.xyz/docs/sp1/introduction) 明确：可证明编译到 RISC-V 的 Rust/C/C++ 程序，**不要求为每个应用手写专用电路**。原稿 §3.2.1 也要求比较联合 Guest 与分模块证明后聚合。

- **联合 Guest**：扩展可证明程序，重放 EVM、Core 与通信规则，输出联合承诺。新增业务证明逻辑、认证见证、跨模块约束和性能工程是必需工作。
- **拆分后聚合**：分别证明 EVM 与 Core，由聚合证明绑定相同批次、前后态及通信承诺，拒绝不匹配的证明。两份有效证明放在一起不自动证明它们交互正确。
- **专用电路/加速组件**：若通用 zkVM 的证明成本不达标，可评估 Core 专用电路、定制 precompile 或其他加速路线。这时需要额外电路设计、安全审计与证明组合；不是使用 SP1 的先决条件。

[Mantle 当前验证路径](https://l2beat.com/scaling/projects/mantle) 为 OP Succinct/SP1，存在程序密钥升级及其他治理条件；该项目页是补充审查来源。实施前须固定 Mantle 客户端与 Guest 版本，而非照抄旧材料的版本号。执行、重放、Guest 与 L1 验证密钥/配置必须一致升级，且测量证明吞吐、延迟与内存；本轮没有得出固定倍数。

## 7. 路线三的建设范围与退出

App-specific L3 是垂直扩展：业务执行在 L3，**直接结算层是 Mantle L2**，Mantle 再接受 Ethereum 的验证与最终性约束。重建的是应用状态机及其执行、数据、证明和运维闭环；现成 zkVM、密码学库、数据库和节点框架可以复用，不必从零发明证明系统。

L2 提供按 L3 隔离的 Escrow、Inbox、State Registry、Verifier、Outbox 与异常退出控制；L3 提供接单、验签、排序、风险、快照重放、父链观察、批次/DA、证明与 API。证明绑定父链历史、充值游标、前后态、批次、数据/提款承诺、应用与程序版本。

充值需认证来源与父链历史且只消费一次；提款先在 L3 扣账，再以已证明的 Outbox 操作建立 L2 待领余额，付款失败保留重试权。L3 运营方不能仅提交一个盈利数字让 L2 增发可提现资产。

首期可评估 Mantle calldata 发布可恢复数据，不默认 L2 提供 L1 式 Blob 交易。Alt DA 需独立定义数据不可得与恢复条件。父链确认状态、L3 暂定回执、L2 接受证明与 Ethereum 最终确认分别暴露给用户。

Perps 故障退出涉及开放仓位：冻结确定状态、撤掉未成交单、按预定规则定价结算、处理坏账与索赔，不能只拿余额 Merkle proof 抽走担保开放头寸的抵押品。独立执行不意味着共享托管、治理、DA 与父链风险全部隔离。

## 9. 二次优化：RISE 的执行、EVM 与 EigenDA

本节以本轮重新读取的一手文档为依据；文档中的实现描述、路线图和性能宣传分开引用，没有完成 RISE 全客户端源码审计或主网部署清单审计。

### 9.1 流水线中究竟优化了什么

| 环节 | 官方文档中的做法 | 对订单业务的含义 |
| :-- | :-- | :-- |
| CBP 连续执行 | 三线程分别预执行 mempool 交易、计算状态根、按 payload 属性封块 | 减少等待新块请求和算根造成的执行空窗 |
| 回执与 Shreds | pending block 正式归入链前返回回执；同步发送 RPC；逐 Shred 广播 | 接单后更快看到执行结果，区别于父链最终性 |
| RiseDB | 统一组织 world state 与 Merkle 树存储，减少重复层次；SSD 顺序/追加写、低内存设计 | 优化订单和仓位频繁更新时的状态读写，不能直接视为删除状态承诺 |
| DA | 正常路径 EigenDA；错误、缺失 ACK 或支付异常时回退 Ethereum blobs | 高负载数据发布不只依赖 Ethereum blob 容量，也引入外部 DA 的可用性假设 |
| 结算 | 文档描述 OP Succinct Lite 的 ZK fraud proof：先提交状态，发生挑战时生成证明 | 不能将其画成 Mantle 式每次更新都必须先有有效性证明的同一流程 |

来源：[CBP](https://docs.risechain.com/docs/rise-evm/cbp)、[Shreds](https://docs.risechain.com/docs/rise-evm/shreds)、[RiseDB](https://docs.risechain.com/docs/rise-evm/rise-db)、[DA](https://docs.risechain.com/docs/rise-evm/data-availability)、[ZK Fraud Proofs](https://docs.risechain.com/docs/rise-evm/zk-fraud-proofs)。

CBP 文档给出的 3–8 倍提升、ping + 1–3ms 回执等属于团队口径，不是对所有硬件、负载或 Mantle 的预测。DA 文档部分 Ethereum blob 参数带有旧版本背景，因此本轮采用其明确的 EigenDA 主路径/回退机制，不将旧的 blob 容量数字当作今日 Ethereum 参数。EigenDA 的可用性与 Ethereum 上的状态结算是不同保障，不能因为有回退就抹去 Alt DA 假设。

### 9.2 EVM 层有优化，但不能把路线图当成已上线

[PEVM 文档](https://docs.risechain.com/docs/rise-evm/pevm) 页首仍明确写着：

> Note the PEVM is not currently live on RISE & is a future improvement.

文档提出基于 Block-STM 的乐观并行、依赖检测、冲突重执行，以及延后处理 Gas beneficiary 余额等 lazy updates。目标是得到与规范顺序执行相同的结果，不是给撮合增加一个新 opcode。共享订单簿和保证金仍有冲突，不能把独立转账的并行倍数套到热门市场。

因此上屏按 **“公开文档仍标为后续改进”** 表达状态，不将 CBP 多线程算根说成已上线并行 EVM，也不因架构总览列了 PEVM 就推断全链已启用。

CBP 还明确存在快速执行路径的适配边界：预执行时父块根和哈希可能尚未算完，依赖相应 `BLOCKHASH`/EIP-2935 的请求需进入特殊调度路径；文档称观察到这类请求后最多每 12 秒安排一次即时执行块。L1 origin 变化也需额外 payload 属性以避免按旧 L1 输入执行。其含义是某些调用可能不能获得同样的快速回执，不宜简单宣称所有合约的时延和 RPC 行为完全不变。

### 9.3 Solidity 撮合是否需要 opcode，是否破坏兼容

**用 Solidity 实现订单索引、价格档、挂撤单、匹配、仓位和风险计算，本身不要求新增 opcode 或撮合专用 precompile。** 编译后的逻辑可由已有 EVM 指令执行。性能适配主要包括紧凑存储、位图或有序索引、批量调用、有界循环、最坏 Gas 预算，以及处理授权、滑点、重入和失败。

[RISE 架构文档](https://docs.risechain.com/docs/rise-evm) 描述 EVM-compatible 执行，[RISEx](https://docs.risechain.com/docs/risex/about/overview) 描述订单簿与 DeFi 共享状态。此次读取的公开资料未找到“必须新增撮合 opcode/precompile”的要求；**这不等于已经审计证明所有生产实现都没有自定义扩展**。旧研究以单笔 Gas 高为依据断言不存在 precompile，并不充分，本轮不采用这种反推。

需区分三种改动：

- **应用实现**：在既有 EVM 内优化 Solidity 数据结构、算法和存储，通常不新增协议语义；其代码能执行与实际吞吐足够仍是两回事。
- **客户端性能工程**：缓存、流水线、并行算根或等价并行执行，目标是保持状态转换结果；仍须检查回执、块上下文、Gas 与证明适配。
- **新增原生能力**：若把撮合搬进 precompile 或新增 opcode，节点与证明系统必须认识新规则，依赖它的合约也不再能不加适配地部署到不支持的链。扩展未必让所有旧合约失效，但已经增加了语义与可移植性边界。

P36A 因而改画 RISE 的实际公开优化设计，不能再把 EigenDA 和挑战式证明省略后标成一套普适的 Ethereum DA/有效性证明流水线。Mantle 借鉴哪些环节，是独立的方案选择，不隐含决定切换 DA 或证明安全模型。

## 10. L3 长期推荐的完整收益与范围

依据 [指定原稿 §2.3.3](execution-three-paths-source.mdx) 和本轮用户明确的方向，L3 pitch 要说明长期价值，而不止列出取舍：**Mantle 保留资产与结算平台，新增业务以专用执行域接入，减少每类业务都改 L2 核心的压力。** 这是本次路线建议，不是某项原生升级已获批或所有 L3 已存在的事实。

| 原稿中的收益 | 本轮归纳 | 保留的准确边界 |
| :-- | :-- | :-- |
| 独立升级 | L2 继续对齐 Ethereum，业务规则与发布尽量在 L3 演进 | 验证版本、消息协议与结算升级仍需协调 |
| 自定义执行 | 按业务选择状态机、数据结构、定点运算和状态承诺，省去不需要的通用开销 | 不必保留 EVM 解释器/MPT，但不能省去证明、恢复和资产权益 |
| 排序与准入 | 不同应用定义批量、优先级、风险通道和准入政策 | 原生排序不自动保证公平或消灭审查；政策需公开并有退出规则 |
| 账户和费用 | 原生 Agent 授权、nonce、赞助和费用资产可独立试验 | 仍需实现完整认证/预算，不等于某个 AA 提案可零成本启用 |
| 资源隔离 | 执行预算、状态增长和业务计费按 L3 分离 | 共享父链结算、DA 和治理依赖仍在，不直接等同 LFM 或绝对风险隔离 |
| 成本空间 | 精简执行、批量结算、压缩与 DA 选择提供降本路径 | 比较证明、DA、桥和固定运维总费；Alt DA 改变安全假设 |
| 实验和互操作 | 新功能先在 L3 验证；研究跨 L3 意图与更快协调 | 不能把 FCR/Based/7683 写成已有原子组合或统一余额 |
| Mantle 定位 | 从承载单个应用，扩展为多业务资产入口与结算平台 | 不由架构直接预测收入、流动性或用户增长 |

跨域部分还参考 [L3 勘误 §7](../../0-narrative/09-native-l3-architecture-and-errata.md)：FCR 是有共识与网络前提的确认规则，不直接改变 FFG finalized；Based 排序需定义父链/排序者角色；ERC-7683 提供意图互操作接口，Solver 仍需资本、履约认证和重组风险管理。这些均为研究选项，不是本次基础交付的强制组合。

### 10.1 后续业务扩展

| 候选业务 | 主要定制方向 | 与 Mantle L2 的联系 |
| :-- | :-- | :-- |
| Perps L3 | 订单簿、批量挂撤、保证金、清算和坏账 | 资产入口、保证金分配、验证与提款 |
| Meme Launchpad L3 | 发行、曲线、排序、状态过期剪枝与毕业生命周期 | 资产映射、发行资产用途、L2 DEX 毕业/交易 |
| Private L3 | 隐私支付或交易；Bonsai 提供紧凑状态与批量验证原型参照，见 §12 | 认证充提、公开承诺、证明与安全退出 |

三类业务可复用经过验证的结算接口、消息规范、SDK、监控和运维工具；每条仍需独立业务规则、程序版本与资金边界。Private L3 不因使用 ZK 就自然隐藏订单与余额；支付隐私和可编程交易隐私需要不同设计，须定义见证生成、数据恢复、密钥和披露规则。

Launchpad 的跨层毕业要处理冻结迁移状态、证明、资产映射、建池和失败恢复，不能照搬同层原子毕业。先验证需求最清楚的一条业务 L3，再扩展其他方向；不是要求同时建设三条链。

### 10.2 代价集中讲清，不吞掉推荐理由

保留跨层消息/桥接风险、流动性分配、异步组合、独立链运营、DA/证明和退出责任。跨 L3 快速资金调动需另计资本与履约风险。推荐 L3 的理由是其长期业务扩展和定制收益，落地前仍须用具体负载、成本和故障退出结果确认收益可兑现。

## 11. Vault 页面的流程补充

[GMX 架构文档](https://docs.gmx.io/docs/api/contracts/architecture/) 的 Execution model 提供一手实现参照：用户先通过 Router 提交包含规模、抵押、可接受价格与执行费的请求；Keeper 读取请求并带签名 Oracle 价格调用执行入口；合约校验价格和订单条件，再原子更新仓位与资金状态。此为两阶段请求/执行，不是链下 Keeper 直接决定账户余额。

P34 用上述流程解释池式 Perps，再接净敞口风险与过渡定位；数字压力算例保留在讲述备注，P34A 保留更完整的风控清单。不同 Vault 实现可以采用不同执行机制，本页以常见 Oracle/Keeper 方案教学，不泛化成所有协议必须相同。

## 12. P41B：状态过期与 Bonsai 隐私支付的具体收益

### 12.1 Commonware 已有公开原型，百万级指标是验证吞吐

完整读取用户指定的 [Private Payments / Bonsai 文章](https://commonware.xyz/blogs/private-payments)，并核对其链接的 [zk-pari PR #2：Adds zk and send/receive circuits](https://github.com/guruvamsi-policharla/zk-pari/pull/2)。PR 包含 send/receive 电路及批量验证基准文件；本次读取时为 OPEN。可以说有公开的隐私支付与证明原型，不能升级表述为已经交付完整 Private execution client 或可直接上线的 Mantle L3。

文章中的具体指标：

| 指标 | 原文口径 |
| :-- | :-- |
| 硬件 | M5 MacBook Pro，6 性能核 + 12 能效核，48GB RAM |
| 并行度 | 18 线程，每线程独立批量验证 |
| 报告吞吐 | **1,051,487 operations / second**，约 1.05M 次/秒 |
| 单位 | send 或 receive 各算一个操作；一次完整支付需两者，折算约 525,000 支付/秒的验证量 |
| 未计入 | 序列化、反序列化、subgroup checks；也不是含网络、共识、存储与结算的端到端压测 |
| 状态结构 | 验证者每账户一个 32-byte commitment，另有少量哈希；不维护按所有交易持续增长的全局 nullifier 集合 |
| 隐私效果 | 隐藏金额、对手方，在 operation-hiding 变体中也隐藏发送/接收类型；活动账户仍可见 |

文章先以 2^12 约束、一个公开输入的 squaring circuit 分离测量证明系统成本，再展示独立批次的并行验证扩展。钱包侧 send/receive 的证明生成另有更长耗时，不能将批量验证吞吐说成所有隐私支付步骤均达到同一速度，也不能直接推导隐私撮合/AMM 的 TPS。

其结尾明确指出下一步才是将吞吐贯穿 networking、consensus、storage，形成 complete private payment system。因此 P41B 保留 **“Bonsai 原型、18 核 M5、批量证明验证约 1.05M 操作/秒、非整链 TPS”** 四项关键信息，百万级数字不单独脱离口径展示。没有重新运行该基准。

对 Private L3 的实际价值在于：公开原型提供了隐私支付状态机与证明设计参照；验证者热状态主要随账户数增长；钱包可以长期离线后恢复。nullifier 负担部分移到用户，钱包冷归档仍随历史活动增长，不能写成全系统只需每账户 32B。适配 Mantle 仍要完成网络/共识、持久化、DA、充提与父链证明；隐私交易程序需要另行设计。

### 12.2 对应的状态过期提案是 EIP-7736

[EIP-7736：Leaf-level state expiry in verkle trees](https://eips.ethereum.org/EIPS/eip-7736) 与用户所说的冷状态过期最接近。本次读取正文状态为 **Stagnant**，依赖 EIP-6800，分叉和恢复交易类型仍列 TBD。提案给 Verkle extension 节点增加更新 epoch，将到期的 extension/suffix 数据移除，但保留 stem 与 commitment（keepsake），再通过恢复交易提供旧数据、校验承诺并重新激活。

提案主要借鉴点是 **冷状态移出活跃存储，同时保留可认证恢复能力**，不是没收或抹除用户权益。提案自身仍保留树的其他部分，因此不能据此承诺状态总量恒定。L3 可按原生业务状态设计相应生命周期，不需要照搬 Verkle 结构或其半年 epoch 参数。

“没有受到重视”不是本次能确认的事实。原文 Motivation 确实讨论早期状态过期方案因复杂度上升而停滞，本次可以准确标注该 EIP 的 Stagnant 状态，不由此推断整个 Ethereum 社区忽视状态增长。

### 12.3 EIP-4444 / 7927 是另一类过期

[EIP-4444](https://eips.ethereum.org/EIPS/eip-4444) 讨论执行客户端对旧区块头、区块体和回执的历史数据提供/保存边界；[EIP-7927](https://eips.ethereum.org/EIPS/eip-7927) 记录历史过期的协调与激活过程，并给出 pre-merge 数据归档与替代获取路径。两者不授权删除当前账户余额、合约存储或未兑付资产权益。

本轮搜索摘要与直接读取对 EIP-4444 状态、保留窗口存在版本差异，因此不从摘要写入“固定一年”或统一状态标签；这里仅采用两者与当前状态过期不同的职责定义。EIP-7736 的状态与机制以直接读取正文为准。

### 12.4 Meme Launchpad L3 怎样获得剪枝收益

L3 可以根据业务期限与状态机终态更积极地划分热数据、冷数据和可删数据，降低热点索引、缓存、同步与持久存储负担。这里是候选设计，尚无实测节省比例，也不宣称只有 L3 能做任何形式的剪枝。

| 状态类型 | 可采用的生命周期 | 必须保留的东西 |
| :-- | :-- | :-- |
| 已执行/过期请求、取消订单 | 完成终态处理后移出活跃索引 | 重放保护的紧凑状态、可审计结果与恢复数据 |
| 结束发行的过程记录 | 最终结算后归档中间数据 | 最终资产分配、费用及领取承诺 |
| 失败发行与退款 | 退款完成，或把未领取款项转为可证明领取权 | 未兑付权益、资金托管和防重复领取规则 |
| 冷账户/低活跃资产 | 研究保留承诺、按证明恢复的状态过期 | 余额、所有权、授权与退出权；不按时间归零 |
| 毕业迁移 | 迁移完成后清理临时过程数据 | 资产映射、LP 归属、未领取权益及跨层唯一标识 |

真正可以激进的是热状态保存策略与已完成业务的临时记录，不是任意删除代币、LP 或余额。用户长期不登录也必须能恢复合法权益；DA、归档、证明服务与退出窗口需要共同设计。不是固定“48 小时后全删”，也不能只做历史裁剪却声称已解决所有活跃状态增长。

P41B 因而把通用的工具复用文案换成两条具体价值：**Launchpad 按业务生命周期压缩热状态；Private L3 借鉴 Bonsai 的紧凑状态与百万级批量验证原型**。Perps 保留简短定位，页面数量不变。
