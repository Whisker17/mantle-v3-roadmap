## Section 0 — 回顾：我们已经解决了什么，下一阶段还缺什么

### 0.1 本次分享希望形成什么共识

- 对齐下一阶段重点验证的产品方向
- 从产品流程中识别可复用的基础设施需求
- 讨论架构选项，但不预先将某个选项作为结论
- 最终确定首批验证任务、责任边界和决策条件

### 0.2 当前三条工作线及其不同职责

- **Mantle v2 的 Glamsterdam 适配**
  - 这是必须完成的基础工作，不依赖新产品是否成功
  - 保障 L1 升级后的派生、批次提交和跨链消息正常运行，同时保留现有 L2 EVM 规则
- **mStocks 产品的开发**
  - 按当前产品设计，通过直连券商的方式引入美股相关资产到链上
  - 回答“用户可以在 Mantle 上持有和交易什么”
- **PropAMM、聚合器和链下做市实验：补充交易执行能力**
  - 回答“用户能否以合理价格成交”
  - 后续应作为产品之间的公共能力，成为所有产品中获取资产的最佳方式

### 0.3 为什么我们做这些事情：从资产供给与 TVL 积累，走向高质量交易

- **为什么做 mStocks：抓住“美股周期 + 资产上链”的机会**
  - 我们当前的市场判断是，“美股周期 + 资产上链”是值得投入的方向。
  - mStocks 是我们承接这一机会的产品：
    - 通过直连券商的方式，将美股相关资产引入 Mantle。
    - 为 Mantle 增加一类有明确链外市场基础的资产，而不只是增加链上原生资产。
  - 因此，mStocks 首先解决的是**资产供给问题：Mantle 上有什么值得用户持有和交易的资产。**
- **为什么不止于引入资产：Mantle 的优势在于 TVL 积累，但 TVL 不是充分的目标**
  - Mantle 已经积累了一定的 TVL，这是我们的基础优势。
  - 但我们不希望只围绕“有多少资金留在链上”来评价生态：
    - TVL 反映资产沉淀规模，不直接反映这些资产是否被有效使用。
    - 资产进入池子，不代表当前价格附近就有足够的有效交易深度。
    - 有资金、有资产，也不代表有持续的交易需求和良好的成交体验。
  - **我们下一阶段更关注的是：这些资产是否产生了真实、持续的交易，以及用户能否以合理的价格成交。**
  - 因此，我们的方向不是否定 TVL，而是希望将资产沉淀优势进一步转化为交易优势。

**一个具体例子：Fluxion 上的 xStocks 池子**

![Fluxion Lp](/images/fluxion-lp.png "Fluxion Lp")

- 根据我们此前对相关池子的调研，流动性是平铺的，而不是集中在当前交易价格附近。
  - 池子里虽然有资金，但这些资金并没有高效地转化为当前价格附近的可执行深度。
  - 从已有报价测试来看，用户实际得到的报价并不好。
  - 这体现了一个问题：**看起来有流动性，不等于用户交易时能获得好价格。**

- 分享时可以在这里展示两类证据：
  - 我希望你可以直接去看 [https://whisker-mantle.mintlify.io/knowledge-base/products/m-stocks#4-1-2-fluxion-%E4%B8%8A%E7%B3%9F%E7%B3%95%E7%9A%84%E5%81%9A%E5%B8%82%E7%AD%96%E7%95%A5](https://whisker-mantle.mintlify.io/knowledge-base/products/m-stocks#4-1-2-fluxion-%E4%B8%8A%E7%B3%9F%E7%B3%95%E7%9A%84%E5%81%9A%E5%B8%82%E7%AD%96%E7%95%A5)
- 这个例子要支持的结论不是“TVL 是假的”，而是：
  - **仅看 TVL，会高估资产的实际可交易性；我们需要同时关注有效深度、资金利用效率和成交质量。**

- **为什么做 PropAMM：补齐从“有资产、有资金”到“能高质量交易”的环节**
  - mStocks 解决资产供给，但不会自动解决这些资产进入链上之后的报价问题。
  - 因此，我们希望通过 PropAMM，以及配套的聚合器和链下做市能力，探索更好的报价与执行方式：
    - 根据市场价格和自身库存，更灵活地调整报价。
    - 提高用于报价的资金利用效率。
    - 通过聚合与路由，为用户寻找更好的可执行价格。
  - 这项工作的目标不是再增加一个沉淀 TVL 的池子，而是**提高用户实际交易时的成交质量**。
  - 对应的评价指标也应从单纯的资金规模，扩展到：
    - 相同订单规模下的报价偏离、滑点和可成交深度。
    - 报价与执行的稳定性。
    - 在此基础上，真实交易用户是否增加、是否持续回来交易。
- **小结：当前几项工作共同指向什么**
  - 资产供给和交易质量，是我们正在补齐的两个环节。
    - **mStocks：引入值得持有和交易的资产。**
    - **Mantle 的 TVL 积累：提供已有的资产与资金基础。**
    - **PropAMM：探索如何让这些资产获得更好的报价和交易体验。**
  - 我们希望从“链上有多少资产”，进一步走向“这些资产被怎样使用，以及产生了多少高质量交易”。

### 0.4 改变迭代方式：从基础设施供给驱动，转向核心应用牵引

> **先决定链要支持什么技术特性，再去寻找能够使用这些特性的项目，最后期待这些项目带来用户。**

- 问题不在于性能优化、协议适配没有价值，而在于：
  - 技术特性与明确的用户需求之间缺少验证。
  - 链团队交付了能力，却未必有产品团队把它转化为完整体验。
  - 即使引入了外部项目，也没有确保项目之间形成资产、订单流和用户的协同。
- 最终容易出现：
  - 功能越来越多，但用户为什么来仍然不清楚。
  - 项目越来越多，但交易深度和持续使用没有同步提升。
  - Roadmap 按“实现了哪些功能”验收，而不是按“做成了什么产品”验收。

> 在这里我们可以以 MegaETH 和 Rise 这两个高性能 evm 链作为例子，MegaETH 是以高性能链作为叙事，寄希望于项目方来完成其生态的构建；Rise 则首先确定了要做 fully onchain perps 来作为高性能 evm 链的核心产品，不断的基于这个产品去做链 infra 的迭代，两者的设计思路不同也导致了目前两者的走向不同。

- 因此我们认为比较健康的方式是：明确市场 → 核心产品假设 → 最小可用产品与必要 infra → 验证 PMF → 针对瓶颈优化 → 将成熟能力开放给生态。
- 因此我们在确定 mStocks 是核心资产之后就需要去寻找对应的核心产品，详细内容可以查看 [https://whisker-mantle.mintlify.io/knowledge-base/products/m-stocks](https://whisker-mantle.mintlify.io/knowledge-base/products/m-stocks)

### 0.4 下一阶段的核心叙事

- 从“引入更多资产”，走向“让资产进入可持续运转的交易市场”。
- 围绕两个产品方向验证：
  - **Meme Launchpad：** 验证新的发行、分发与参与方式。
  - **Perps：** 验证持续交易、风险表达和对冲需求。
- mStocks 和 PropAMM 不退出主线：
  - 前者提供资产供给。
  - 后者提供报价、路由和做市能力。
  - 新产品与它们的协同，通过具体资金和订单路径验证。

**本节结论：我们不是为了增加链上交易数量而增加场景，而是要找到能够产生持续需求、并由现有资产和执行能力承接的产品。**

## Section 1 — 产品拆解：两个产品究竟解决什么问题，需要什么能力

### 1.1 Agentic Meme Launchpad

#### 1.1.1 先复盘：为什么不值得再做一个普通 Launchpad

- 将此前两个项目的复盘放在方案介绍之前。
  - Funny Money 和 Printr
- 失败的原因？
  - Mantle 本身没有用户
  - 没有对应的 kol 资源
  - meme Launchpad 本身没有任何新意

#### 1.1.2 确定新的 meme Launchpad 的 PMF

- 最大的创新来源于对用户的转移
  - 如何解决用户的问题
    - 需要 agents 作为第一公民，对于 agents 来说他们不在乎链之前的数据和名声
    - Bybit AI 的推出意味着 Bybit 想要将 agents 的交易地位提升，但是他们依然被困在交易所内，而我们可以帮助他们扩展到链上
  - 如何解决 kol 等资源问题
    - agents 本身是中立且无状态的，因此我们可以给 agents 搭建交流平台（类似 Moltbook），这样就可以不需要 kol 喊单了
- 围绕 mStocks 的创新
  - 将 mStocks 作为 quote token，让 meme 成为 mStocks 生态的放大器

#### 1.1.3 展示完整 workflow

- 需要在这里展示 vanilla meme Launchpad 和我们本次的 Agentic meme Launchpad 的 workflow 对比，既做到了对内的教育（让同事们知道 meme Launchpad 的原理），也做到了对新的产品的解析，并可以在对比中强调新产品的优势
  - 入口与用户激活。
  - 钱包创建／接入及授权。
  - 资产创建或发现。
  - 初始发行与交易。
  - 二级市场接入，以及流动性迁移流程——如已有设计包含该环节。
  - 后续交易、权限管理和退出。

对每个步骤标注：**用户在做什么、Agent 在做什么、哪些约束必须由合约或协议强制执行。**

#### 1.1.4 抽象出的 chain infra 需求

- 根据新的交易主体（agents）提供新的账户模型
  - 安全、可撤销的自动化授权（Session keys）
  - 可控的代付成本与滥用防护（gas sponsor）
  - 发行高峰期的交易处理和明确的排序规则（2d nonce 等）
- 其余 infra（Optional）
  - 可靠的交易提交、状态查询和失败恢复
  - 面向 Agent 的 SDK、事件订阅与操作审计
  - 状态剪枝

**本节结论：Launchpad 对基础设施的核心要求，不是“支持某个 AA 提案”，而是让自动化参与安全、顺畅且成本可控。**

### 1.2 Perps

#### 1.2.1 先定义目标产品，而不是先讨论执行架构（确定 PMF）

Mantle Perps 的差异化，不是单独提供一个杠杆交易场所，而是围绕 mStocks 建立方向交易、库存对冲和组合策略市场，让不同风险偏好的资本都能参与 mStocks 生态

- 目标用户是谁：
  - 普通交易者
  - 做市商/对冲需求方
  - 策略工具
- 如何与 mStocks 进行结合
  - 让 mStocks 持有人可以做对冲，实现 Delta Neutral（这部分用户往往是专业套利者以及做市商）
  - mStocks 在 perps 中的使用途径（包括 HLP 类似的 Vault 以及作为保证金抵押资产）

- 选择什么交易模型：
  - 资金池／预言机模型。
  - 混合撮合与链上结算模型。
  - 撮合与风险状态转换可验证的订单簿模式

#### 1.2.2 解析不同模式 perps 的运作模式

- 资金池／预言机模型
  - GMX，Aster Simple，Variational 为首
  - 不需要双边订单簿，仅仅通过预言机报价然后去和 Vault/Pools 去做对手方，Variational 不太一样是一个 RFQ 的模式
  - 示例
    - 假设针对的市场是 ETH/USDC，那么该市场会有一个 Vault，里面包含的资产有 ETH 和 USDC，流动性可以由 LP 以及用户注入提供
    - Alice 在 \$2000 的价格 10x 开多 5ETH，假设你的保证金是 1000，那么当你开单后这部分保证金就会进入到 Vault 中
    - 需要注意的是你做的这部分保证金在 vault 是不断在变化的（包括手续费，borrow fee，funding fee 等）
    - 当你最后平仓的时候，你所获得资金最终都是由 Vault 提供的
- 混合撮合与链上结算模型
  - Aevo，Aster Pro 为首
  - 主要就是通过链下撮合 + 链上结算的方式来实现 perps
  - 示例
    - Alice 将资金 deposit 到合约中，然后同样的开单，但是此时不会立即成交，而是需要有链下撮合引擎帮助你去和当前的挂单进行撮合
    - 撮合完成后将双边的开单都上链，持单期间的 funding fee 等都是在链下记录的
    - 当最后结算的时候盈利都是从对手方的保证金中扣除
- 撮合与风险状态转换可验证的订单簿模式
  - Hyperliquid，Lighter，RiseX 为首
  - 解决的是链下撮合的黑箱问题，提供可验证的撮合
  - 分开讲述这三者的不同
    - RiseX 将撮合与风险逻辑运行于 EVM。RISE 将 RISEx／MarketCore 描述为 Solidity 合约系统，可在同一交易内与其他合约组合；
      - 保留同步可组合性，但承担通用执行、存储和计量成本
    - Hyperliquid 将订单簿、撮合和保证金状态纳入 HyperCore，通过链的共识执行
      - 可以围绕交易优化状态与排序，但不是可直接搬到 Mantle 的普通合约
    - Lighter 在专用引擎执行交易，生成证明，向结算层提交状态更新与恢复状态所需的数据
      - 可以优化交易与证明工作负载，但必须建设证明、数据可用性和退出机制

#### 1.2.3 将不同模式 perps 所需的 chain infra 总结出来

- 资金池／预言机模型
  - 主要的约束在于
    - 价格更新、订单执行和清算交易能否及时到达
    - 拥堵时 Keeper 是否继续工作
  - 所需要的 chain infra
    - 低延迟执行反馈
    - 可靠 Oracle 接入
    - 是否能给 Keeper 提供优待通道
- 混合撮合与链上结算模型
  - 主要的约束在于
    - 链下已成交状态与链上可结算状态之间的差距
    - 成交批量提交能力
  - 所需要的 chain infra
    - 批量结算、幂等提交、明确预确认语义、风险预留与结算滞后上限、重放与故障恢复
- 撮合与风险状态转换可验证的订单簿模式
  - 主要的约束在于
    - RiseX
      - 每次挂撤单与撮合均涉及状态执行
      - 单一热门市场的热点状态
    - Lighter
      - 证明生成、数据发布和结算验证是否跟得上业务
      - 故障时能否恢复和退出
    - Hyperliquid
      - 引入新状态机后如何纳入 Mantle 验证体系
  - 所需要的 chain infra
    - 更短执行反馈周期、订单专用批处理、优化订单簿存储与索引
    - 专用状态机与证明系统、证明积压管理、数据可用性、L2 验证合约、强制请求和退出路径

#### 1.2.4 Perps 这个产品通用的 chain infra 需求

- 不论什么模式的 perps，都存在一些通用的 chain infra 需求
  - 降低做市商的未对冲暴露时间
    - 这里强调的是做市商能够及时调整合约敞口，合约报价过期时，能够及时撤销，即 Cancel Prioirity 机制
  - 交易的可组合性能力
    - 对于大多数中性套利/对冲的用户来说，他们希望可以让他们的 spots 交易与 perps 交易可以组合提交，并实现原子同步可组合性
  - 账户模型的多层交易能力
    - 包括子账户的权限管理，以及针对 agents/bots 的权限管理，这部分可以做在产品层，也可以做在链 infra 层
  - 极端行情下的特殊操作仍然能执行
    - 这里主要是一些产品内的设计（包括外部价格失效，大规模清算等），但是对应的也有一些可优化的 chain infra 设计（但是需要考虑到状态机是专用的还是通用的）

## Section 2 — 从产品需求到能力差距：哪些事情真的需要改链

需要明确的是除非在合约层面无法实现，否则我们并不倾向于修改链本身。

**Agentic Launchpad 的首要要求，是让 Agents 能够在明确权限和成本边界内，安全、持续地完成发行、发现、交易及退出。**

**Perps 的首要要求，是让交易、报价调整和风险处理及时生效，并按照明确规则完成撮合、保证金更新和结算。**

因此我们的目前就是：为所有产品提供一致的账户、提交、状态反馈与资产接口；为确有需要的业务提供更深入的排序、执行和资源定制能力。

### 2.1 从产品业务角度统一整理需求

| 能力方向 | Agentic Launchpad 的需求 | Perps 的需求 | 可以共同建设的部分 |
| :-- | :-- | :-- | :-- |
| **账户与授权** | 自动发行、交易、预算控制、权限撤销 | 子账户、策略权限、下单与提现分权、风险限额 | 受限授权、多操作队列、代付与审计接口 |
| **交易提交与反馈** | 明确发行和交易是否成功，避免重复执行 | 明确订单是否接收、成交、撤销及结算 | 幂等提交、状态订阅、失败归因、恢复机制 |
| **排序与资源使用** | 热点发行时的排队、公平性和费用可控 | 报价刷新、撤单、风险操作的时效性 | 可观测拥堵、受约束调度、反滥用机制 |
| **组合执行** | 发行、初始交易和流动性迁移的状态连续性 | 现货与合约、保证金与交易的组合执行 | 条件执行、批量调用、明确回滚边界 |
| **极端情况处理** | 热点拥堵、赞助预算耗尽、交易失败 | 价格失效、清算高峰、撮合或结算停滞 | 降级模式、服务恢复、关键操作保障 |

### 2.2 从产品需求出发，归纳 Mantle 的链层优化方向

#### 2.2.2 低延迟执行与状态反馈：让交易者知道操作何时真正生效

##### **产品需求**

Launchpad 中，Agent 需要及时知道资产是否创建成功、买入是否执行、毕业迁移是否完成，避免因状态不明确而重复提交。

Perps 中，做市商需要及时知道旧报价是否已经撤销、新订单是否生效、仓位与保证金是否更新。对冲策略关注的是实际敞口何时发生变化，而不只是 API 多快返回“成功”。

##### **对应的链层优化**

重点应从单一的 **shorter blocktime** 扩展为 **低延迟交易执行路径**：

- 优化交易接收、执行、回执输出和状态读取，评估更短区块或区块内增量反馈等方式。
- 提供可靠的提交与订阅接口，支持幂等请求、执行状态查询、断线恢复和明确的失败原因。
- 提供拥堵程度、费用分位和预计等待区间等信息，帮助 Agents 决定继续等待、调整提交策略还是放弃操作。

## Section 4 — 以 Fully Onchain Perps 为终态进行的 chain infra 优化

### 4.1 先澄清比较维度

- 确定不同模式 perps 下的工作难度
  - 初始的版本我们可以提供一个 Vault 方式的 perps，但是最终形态依然是 fully onchain perps，所以我们要从最终形态开始审视 Mantle chain infra 的优化方向

- 实现 fully onchain perps 的方式
  - **现有 L2 通用执行环境。**
  - **Mantle 统一验证边界内的专用执行模块。**
  - **独立执行域、在 Mantle 结算的 App-specific L3。**

### 4.2 过渡方案中的工作量分析

#### 4.2.1 Vault／预言机型 Perps

这一模式的主要链上负载，不是持续维护大量双边挂单，而是执行用户请求、处理价格输入、更新仓位，以及执行清算：

| 能力缺口或待验收项 | 对产品的影响 | 对应的链级工作 |
| :-- | :-- | :-- |
| **请求到执行的延迟不够可预期** | 用户提交后，不清楚何时开仓、减仓或退出 | 优化交易接收、执行反馈与状态订阅，明确请求创建、执行、失败和过期状态 |
| **价格输入与订单执行之间缺少可靠协调** | 可能执行失败，或使用不符合产品规则的价格 | 提供可靠的 Oracle 提交与读取接口，支持价格版本、有效期及执行条件检查 |
| **Keeper 在拥堵时缺少执行保障** | 正常订单和清算积压，增加市场风险 | 建设有界的 Keeper 提交通道、资源预算、费用管理和反滥用机制 |
| **热点期间成本波动与重试成本不可控** | Keeper 或代付方难以维持服务 | 提供费用估计、提交队列、预算控制和失败归因 |
| **节点或索引服务故障后恢复不完整** | 重复执行、遗漏请求、状态追踪错误 | 提供可重放事件、幂等执行接口、断线恢复及重组处理 |

Mantle 优先需要补强的是低延迟执行、Oracle 接入、Keeper 可用性与成本控制，而不是先建设交易专用状态机，但是我们要明白的是这个产品形态只是一个最初始版本的 perps，并非最佳的 perps UX，但是他对于链 infra 的需求是最低的。

#### 4.2.2 混合撮合、链上结算型

这一模式将高频挂单、撤单和撮合放在线下，将资金与成交结果放到链上结算。以 Aevo 的公开架构为例，创建和取消订单不产生链上 gas，而成交结算需要链上执行；资金、仓位及资金费支付则由合约记录和处理

| 能力缺口或待验收项 | 对产品的影响 | 对应的链级工作 |
| :-- | :-- | :-- |
| **批量成交结算的容量与成本** | 链下成交速度超过链上落账速度 | 优化批量提交、执行与数据发布，压测每批成交数、gas、数据量和结算延迟 |
| **链下已成交与链上已确认之间的状态差距** | 保证金或可提现余额可能被错误使用 | 提供清晰的确认状态；配合产品建立保证金预留、未结算风险限额及积压上限 |
| **重复提交与乱序提交的处理** | 重复成交、累计成交量错误、错误拒单 | 统一交易标识、成交序号、幂等验证和可重放结算接口 |
| **撤单、部分成交和结算之间的边界** | 用户认为订单已取消，但旧订单仍可能被提交 | 明确撤单版本、订单有效性与累计成交量，支持必要的链上取消和失效机制 |
| **撮合方、提交方或节点故障后的恢复** | 资金被长期占用，或账本无法重新对齐 | 建设结算重放、状态对账、暂停与恢复流程，并定义用户独立退出能力 |

Mantle 首先需要增强成交结算与故障恢复，而不是把链下订单 API 的延迟问题误认为链的执行问题。它可以作为产品方案或对照基线，但不应被当成终态已经完成。

这个方案的问题在于无法检查撮合方是否遗漏了更优订单、延迟了撤单，或违反了公开的撮合顺序，若要进一步验证这些过程，就需要把对应订单输入与规则纳入验证范围——这正是最终 fully onchain 方案要解决的问题

### 4.3 面向 Fully Onchain Perps，Chain infra 要求发生了什么变化

#### 4.3.1 路线一：在现有 Mantle L2 通用执行环境中实现

在这种路线下如果我们想要实现 fully onchain perps，这是一个非常困难的设计，将订单簿、撮合、保证金、资金费和清算逻辑部署为 Mantle 上的合约。所有权威状态更新继续通过通用 EVM 执行，并沿用其对应的链级验证路径。目前看下来 RiseX 似乎是最接近的答案，而他们针对 perps 这个产品对他们链 infra 本身做了非常多的优化（问题是他们这部分逻辑并没有开源，无法验证）：

| 工作方向 | 具体内容 | 实现边界 |
| :-- | :-- | :-- |
| **连续执行与低延迟反馈** | 减少执行空窗；更早输出回执和状态变化；支持低延迟行情订阅 | 优化执行流水线、RPC 和节点服务，不将提前反馈误称为最终性 |
| **热点状态执行优化** | 优化状态缓存、数据库访问、状态根计算与执行之间的协调 | 优先保持 EVM 执行语义不变，通过性能工程降低开销 |
| **高频订单的提交与批处理** | 支持受约束的批量挂撤单、签名验证及操作队列 | 部分由账户和市场合约提供，链层优化对应执行与计量 |
| **市场相关排序与资源调度** | 评估撤单优先、风险操作保障和热点资源限制 | 区分排序器服务策略与协议强制规则，并明确操作分类与反滥用方式 |
| **数据发布与验证吞吐** | 压测订单负载增长后的数据量、状态增长和验证成本 | 不能只提高执行容量，却让数据发布或证明长期积压 |
| **可组合执行接口** | 让现货交易、合约成交和保证金变化可被同一交易检查 | 应用需要同步成交、结果返回及整体回滚能力 |

这个方向的主要约束：

1. **热点市场不能简单依靠并行执行解决。** 独立市场和独立账户可以寻找并行空间，但同一订单簿的顺序、共享保证金与成交依赖仍需要保持一致。应当用目标工作负载识别真正的串行部分，而不是通过增加不相关交易证明吞吐充足
2. **缩短区块不等于提高每秒处理能力（甚至可能会降低执行能力）。** 如果执行、存储或状态承诺已经饱和，仅提高出块频率可能增加调度负担。区块参数、执行流水线和状态处理需要一起评估

这个方向的主要优势：

1. 保留 mStocks、现货、借贷与 Perps 的同步组合空间

#### 4.3.3 路线三：独立执行域，在 Mantle 结算的 App-specific L3

这一方案将订单接收、排序、撮合和风险计算放到独立执行域，Mantle L2 承载相应的结算、验证、托管和退出接口，L3 可以采用 EVM，也可以采用交易专用状态机。

| 工作方向 | 独立执行域需要建设 | Mantle L2 侧需要提供或集成 |
| :-- | :-- | :-- |
| **订单排序与执行** | 交易网关、本地排序、预确认、撮合与风险状态机 | 接收满足结算条件的状态更新，不逐条承担快路径撮合 |
| **状态验证** | 状态承诺，以及有效性证明或其他具有明确安全边界的验证机制 | 验证器、状态更新约束、版本与升级管理 |
| **数据可用性与恢复** | 发布足够恢复状态和执行退出的数据，提供归档与恢复工具 | 验证相关数据承诺或可用性条件，处理发布失败的后果 |
| **资产与保证金出入金** | 处理入金消息、余额记账、保证金占用和提现请求 | 托管资产，校验消息与提现，防止重放和重复释放 |
| **跨域状态协调** | 跟踪父链状态、处理重组与确认级别变化 | 提供明确的消息和结算状态接口 |
| **强制请求与退出** | 响应强制减仓、取消、提现等请求，并支持故障状态恢复 | 提供绕过正常排序器的请求入口及相应退出约束 |
| **运行监控与风险降级** | 监控执行、数据发布及验证积压，限制新增风险 | 识别停滞状态，并执行预先定义的结算或暂停规则 |

这个方向最主要的约束：

1. 开发成本高，除了要做 Mantle L2 的验证和结算逻辑，还需要根据不同的业务逻辑去开发 L3 本身的状态机（包括执行、验证、数据与退出体系）
2. 损失了 DeFi 可组合性以及同步可组合性

这个方向的优势是：

1. 保留了 Mante L2 的独立升级，不受到业务逻辑的影响
2. 定制化能力强
   - 不同的 appchain 可以定制化自己的排序规则，甚至可以审查用户的交易
   - 不同的 appchain 可以做到极致精简的状态机设置，抛弃通用的  EVM bytecodes 解释器，放弃 MPT 状态树
   - 不同的 appchain 可以采用不同账户模型，不同的 gas token
   - 不同的 appchain 之间有天然的拥堵隔离，起到 LFM 的作用不同 appchain
   - Appchain 的手续费可以进一步下降
3. 实验性功能的快速落地
   1. 所有不确定的 L1 功能都可以在 L3 上进行实验，不需要担心 Mantle L2 的 evm 兼容问题
   2. L3s 之间的可组合性，类似于 Ethereum 想要解决的 L2s 之间的可组合性（FCR 等）
