# Mantle 产品账户需求：EIP-8130 与 EIP-8141 能力覆盖及适配评估

> **本次决策不是选一个“AA 功能最多”的提案，而是确定：怎样以可接受的安全、复杂度和维护成本，让 Agent 持续、受限、可撤销地参与交易。**
>
> 完整比较对象应当是 **8130＋Policy-aware 账户／产品＋Sponsor＋提交系统**，以及 **8141＋8250＋等价账户策略＋Sponsor＋提交系统**。同时保留现有合约层账户方案作为基线，验证原生协议改动是否具有必要的增量价值。

**系列导航：** 协议细节见 [8130 Deep Dive](01-eip-8130-deep-dive.md) 和 [8141 Deep Dive](02-eip-8141-deep-dive.md)。本篇聚焦产品覆盖、架构适配、缺口与选型条件。

**阅读建议：** 决策讨论可先看 §1、§4 和 §13；产品适配看 §6～§8；工程评审看 §5、§10～§12。矩阵中的“可实现”不等于已经由协议完整交付。

## 阅读口径与来源

本篇的需求依据是用户复制的《从资产供给走向可持续交易，以及产品驱动的 Chain Infra 演进》，重点为 **§1.1、§1.2、§2.2.1、§2.2.2～§2.2.5，以及 §4**。以该份材料为项目需求基线，不将文中的未来设计视为 Mantle 已上线能力。[^requirements]

比较框架沿用用户提供的《EIP-8141 与 EIP-8130 底层机制与虚拟机执行内核深度解析》§5；机制按 **2026 年 9 月 24 日访问的 EIP-8130、EIP-8141 和 EIP-8250 官方 Draft 文本**核对。两篇 deep dive 已逐项说明对原稿的保留、修正和补充。[^intro][^e8130][^e8141][^e8250]

全文中的“建议”“示例”“验收项”是根据需求作出的设计分析，不是 EIP 原生规定；没有运行 Mantle 客户端、账户合约或证明系统，也没有测得本文涉及的延迟、吞吐、Gas 或开发工期。

## 1. 先给出本阶段可以成立的结论

### 1.1 两条路线都可以承载受限 Agent，但原生标准化的位置不同

**8130 更偏向标准化账户身份与基础授权。**它提供 Actor、Authenticator、到期与撤销配置、基础 scope、Policy Manager 门禁、付款人，以及有序多通道和 nonce-free 机制。业务策略仍需 Manager、账户或产品实现。[^8130-account][^8130-nonce]

**8141 更偏向标准化交易处理流程。**它提供原生签名材料、验证 Frame、执行／付款批准、业务 Frame、原子组和结果内省。Session key 的存储与权限规则需要账户实现；多通道比较必须另列 8250，而不能归给 8141 本体。[^8141-frames][^8141-approval][^e8250]

因此，不能从“8130 内置更多账户语义”推导出“它已经更安全、更快”；也不能从“8141 本体是标量 nonce”推导出“完整 8141 路线只能串行”。

### 1.2 Mantle 当前最重要的不是批处理，而是完整的授权闭环

需求文档要求：Agent 有时效且可撤销；操作范围受限；不同策略减少串行阻塞；交易与提现分权；代付可控；操作与权限可审计。[^req-account]

要真正交付这些能力，必须回答：

```text
谁授权 Agent？
  → Agent 能签什么？
  → 验证器检查了哪些内容？
  → 谁真正能移动资产？
  → 多个 Agent 如何共享或隔离预算？
  → 失败时谁损失 Gas？
  → 撤权后旧交易、旧订单和持仓分别怎样处理？
  → SDK 如何判断最终业务状态？
```

两案都只覆盖其中一部分。**最大的工程风险不一定来自验签，而可能来自验签后未被约束的执行入口、费用权限、订单验证和失败恢复。**

### 1.3 可以优先验证 8130，但尚不能直接据此决定改链

原稿将 8130 定位为“优先工程验证方向”，不是确定的生产方案，这个限定应保留。[^intro]

建议将该假设进一步收紧为：

> 当目标工作负载包含同账户多 Agent、高频链上直发操作，并希望统一 Actor 与基础权限接口时，优先验证 8130 是否能降低账户、接入和准入复杂度；同时用 8141＋8250＋同等安全约束作为对照。

项目需求中“除非合约层无法实现，否则不倾向于修改链”的约束仍然成立。若现有合约层方案已经满足安全与目标体验，原生 AA 的立项依据必须来自被测量的新增价值，而不是 Native 标签。[^req-principle]

## 2. 当前已经明确什么，哪些前提还没有明确

### 2.1 已明确的产品方向

| 产品 | 需求文档已明确的方向 | 对账户评估的影响 |
|---|---|---|
| Agentic Meme Launchpad | Agent 作为参与主体；持续发行、发现、交易及权限管理；构想包括以 mStocks 为 quote token | 不能只研究一次“连接钱包＋买入”；需要覆盖授权、预算、并发、重试和退出 |
| Perps | 围绕 mStocks 的方向交易、对冲与组合策略，覆盖普通交易者、做市商和策略工具 | 需要分层权限、子账户、及时撤改单、订单与仓位状态反馈 |
| Perps 演进 | 初期可以采用 Vault 模型，但面向 fully onchain Perps 终态评估基础设施 | 不能只按初期入金／开仓流程决定长期账户接口 |
| 基础设施方法 | 产品驱动，共用账户、提交、状态与资产接口；必要时深入排序、执行与资源定制 | AA 账户层与交易执行层需要分别验收，不能互相替代 |

以上来自需求文档，不是对公开市场或 Mantle 现网的独立调研结论。[^req-products][^req-perps][^req-principle][^req-domains]

### 2.2 仍需在产品／工程方案中明确的前提

| 尚未确定的事项 | 为什么会改变比较结果 |
|---|---|
| 一个用户是否同时运行多个 Agent、是否共享同一资金账户 | 决定同账户多通道与策略隔离的重要性 |
| Perps 订单是原生链上交易，还是链下签单后批量结算 | 决定原生账户 nonce 是否处于每次报价的关键路径 |
| 账户采用哪一种受限执行实现，Manager 如何操作资产 | 决定 POLICY 是否形成完整授权闭环 |
| 预算以投入、净买入、成交名义金额、保证金还是风险敞口计量 | 决定检查应位于验证阶段、执行阶段还是产品风险账本 |
| Sponsor 是免费补贴，还是收取 ERC-20／mStocks 报销 | 决定费用权限、报价风险、偿付与失败处理 |
| 使用什么公共／专有提交路径 | 决定验证规则、待处理容量、Sponsor 预留与 DoS 防护 |
| Perps 终态位于通用 EVM、统一验证的专用模块，还是 L3 | 决定账户规则怎样进入验证系统，以及是否能同步组合 |
| 实际客户端、验证／证明体系、Gas 与数据费用规则 | 决定两案的链级工作量，不能预先代入 SP1 或其他具体栈 |

这些是**待确认的设计变量**，不是要求先停止研究。以下按不同情况给出适配结论与验收项。

两篇 deep dive 使用“100 USDC 买入”是教学示例，不改变本项目围绕 mStocks 的产品构想。实际 quote token 的合约行为、授权接口与可用性，需要单独接入验收。

## 3. 把账户需求转成可验收的能力清单

### 3.1 核心账户需求

以下 R1～R6 是对需求文档 §2.2.1 的拆解，其中“Session keys 与权限撤销”被拆为身份生命周期与细粒度权限两项；不是新增的项目范围。[^req-account]

| 编号 | 需求 | 交付标准，而非功能标签 |
|---|---|---|
| R1 | Session key：独立密钥、时效、撤销 | Owner 不交出根密钥；Agent 使用自己的凭证；过期与撤销有明确生效状态 |
| R2 | 受限操作与预算 | 对目标、函数、资产、接收人、金额和授权扩张建立不可绕过的检查 |
| R3 | 多 Agent／多策略独立操作流 | 不必要的账户级 nonce 依赖减少；恶意或故障 Agent 的影响范围可解释 |
| R4 | 子账户与分层权限 | 交易与提现分权；策略或子账户的资金、风险及管理权限有明确隔离边界 |
| R5 | 可控代付 | 按账户、应用、操作配置预算、速率和滥用限制；失败费用与资金预留可预测 |
| R6 | 签名与审计 | 能识别操作主体和授权来源，追踪权限版本、业务结果及失败原因 |

其中 R4 不是“有两个 Actor 就有两个子账户”，R5 也不是“交易格式允许 payer 字段就已经完成代付平台”。

### 3.2 与账户紧密相关、但不能归入 AA 的需求

需求文档还提出以下能力，应保留在评估中，但单列责任层。[^req-feedback][^req-ordering][^req-resources][^req-composition]

| 编号 | 需求 | 主要责任层 |
|---|---|---|
| R7 | 业务幂等、执行状态、重试与恢复 | 产品状态机、SDK、RPC、索引与恢复服务 |
| R8 | 多操作的成交条件与共同回滚 | AA 分组＋账户／产品执行接口；必要时包含跨模块执行规则 |
| R9 | 撤单、风险操作及时生效 | 订单状态机、排序与调度、准入及执行资源 |
| R10 | 热点费用与资源隔离 | 提交入口、费用机制、调度或独立执行域 |
| R11 | 极端行情与基础设施故障时的降级 | 风控、Keeper、Oracle、提交与恢复体系 |

**多维 nonce 主要回应 R3，不直接交付 R9；原子组回应 R8 的回滚机制，不直接保证业务已同步成交。**

## 4. 能力覆盖矩阵：原生支持到哪里，哪里仍需补齐

### 4.1 如何阅读这张表

本表使用以下口径：

- **原生机制**：激活相应协议后，交易处理规则直接提供。
- **账户／产品补齐**：协议允许实现，但需设计、部署和审计。
- **外围补齐**：依赖提交、排序、索引、费用服务或产品市场状态机。

“可实现”不能与“EIP 已经完整规定”混为一谈。下面机制分别来自官方规范；覆盖判断是将其映射到 R1～R11 后作出的分析。[^e8130][^e8141][^e8250]

### 4.2 核心账户能力

| 需求 | EIP-8130 | EIP-8141 本体 | 8141＋8250 的变化／共同缺口 |
|---|---|---|---|
| R1 独立 Agent 身份 | 原生 Actor 与认证器选择 | 签名／验证入口原生；Session 身份模型由账户定义 | 8250 不增加 Session 模型 |
| 认证方式／Passkey 接入 | canonical 集合区分 k1、P-256、WebAuthn passkey 与 delegate | 原生标准签名包括 secp256k1、P-256；完整 WebAuthn 数据与授权检查不能只由曲线验签替代 | 8250 不扩展签名方案；两案都要验证钱包、SDK 与授权展示 |
| R1 到期与撤销 | 原生 Actor expiry、撤销及配置版本机制；Lock 会限制配置修改 | 账户实现有效期、撤销版本与恢复入口；公共准入需遵守时间与状态依赖规则 | 均需处理在途交易、旧订单与 UI 生效反馈 |
| R2 调用范围 | POLICY 原生约束顶层目标为 Manager | 验证器可检查完整 Frame 序列 | 细粒度函数、参数、资产、接收人等仍由策略实现 |
| R2 预算与风险 | Manager／产品执行累计额度与风险逻辑 | 账户验证静态限制；动态累计与风险由执行逻辑实现 | 8250 不增加风险账本 |
| R3 有序独立队列 | 内置 `(account, key, sequence)` | 本体使用标量 nonce | 8250 提供 key 集合与 sequence；公共池待处理规则仍需单独解决 |
| R3 无序独立请求 | 有短有效期＋有界共识去重的 nonce-free 模式 | 没有对应的内置 nonce-free 模式 | 新 key＋初始 sequence 可构造某些无序操作，但会增加持久状态，不等于 8130 的环形去重 |

| R4 子账户与资金隔离 | Actor 是操作身份，不是余额或保证金子账本 | Frame 是执行单元，不是子账户 | 均由账户／产品实现资金、保证金与风险隔离 |
| R4 交易与提现分权 | POLICY＋安全 Manager／账户接口 | Session 验证＋安全执行接口 | 均需防范 allowance、任意调用、升级及间接资产转移 |
| R5 原生付款主体分离 | 显式 payer、付款认证与 payer scopes | APPROVE_PAYMENT 指定 payer | 8250 不改变付款权限模型 |
| R5 预算、速率与滥用控制 | 原生付款权限不自动提供业务预算；需要 Sponsor 策略及准入 | Paymaster／账户及服务实现业务预算，受公共准入约束 | 两案均需预留、限额、报价、失败归因和监控 |

## 5. 真正会影响 Mantle 选型的安全与体验差异

### 5.1 8130 的受限入口不等于完整业务授权

8130 对 POLICY-only Actor 的原生保证是顶层调用指向指定 Manager。它不自动判断 `buy` 是否合规，也不自动使 Manager 拥有移动账户资产的权限。[^8130-policy]

必须明确下列路径中的实际权限：

```text
方案 A：Account → 外部 Manager → 经授权的账户执行模块 → 产品
方案 B：Account → Policy-aware Account 自身 → 产品
方案 C：Account → 直接承载策略的产品入口
方案 D：Manager 使用账户已授予的有限 token allowance
```

这些是实现选项，不是等价且默认安全的替换件。

对 Mantle，建议首先选定一种可审计的最小模型，并验证所有旁路：Owner 执行入口、Agent 执行入口、模块安装、delegatecall、回调、代币授权和升级。

**特别是 `manager = account` 时，不能仅凭 `msg.sender == address(this)` 放行任意执行。**协议本身可以产生这种 self-call，上层仍须识别 Actor 和 Policy。[^8130-policy]

### 5.2 8141 必须授权完整 Frame 集合，而不是只认证 Agent 签名

8141 的执行批准是交易级：账户批准之后，后续 SENDER Frames 都能使用 sender 身份。[^8141-approval][^8141-security]

这要求验证器同时证明：

```text
这笔交易确实由某个有效 Agent 签署
                        且
这笔交易的全部受授权动作都在 Owner 给该 Agent 的权限内
```

Agent 即使签了整笔交易，也可能签署超越自身授权的动作。因此不能只确认某一 Frame 是允许的 `buy`，然后忽略后续提款、扩大 allowance 或修改权限的 Frame。

这是 8141 账户实现的关键安全工作，而不是可选增强。其优点在于验证器可以在批准前拒绝不合规的完整计划；其限制在于公共 Mempool 不允许任意读取第三方动态状态，复杂业务风险仍需要在执行阶段检查。[^8141-mempool]

### 5.3 多通道不等于权限隔离，两案的补齐位置不同

在 8130 中，NONCE scope 不规定某个 Actor 只拥有某些 key。即使 Manager 在执行阶段拒绝越界操作，也不能据此撤回已消耗的原生 nonce。[^8130-nonce][^8130-validation]

在 8141＋8250 中，账户可以在验证阶段要求：

```text
当前 Session 只可使用指定 key；
或者当前 key 集合的承诺必须匹配授权配置。
```

当前内省接口使这类约束具备实现基础，但复杂 key 集合的编码、检查方式及验证成本仍需设计。它不是 8250 自动建立的密钥所有权。[^e8250]

**产品结论：** 对“不同 Agent 相互不能干扰”的严格要求，仅有 8130 原生多通道还不足够。应评估不共享账户、使用 nonce-free、增加可验证的通道限制，或接受并明确剩余 DoS 边界。

这些选择都不自动隔离共享保证金、共享 Sponsor 余额和热点订单簿。

### 5.4 交易预算、风险预算和 Gas 预算必须分开

建议明确三个独立约束：

| 预算 | 示例问题 | 适合的检查位置 |
|---|---|---|
| 交易资金预算 | Agent 累计可以投入多少 quote token？ | 账户／产品执行状态 |
| 风险预算 | 可增加多少名义敞口、保证金占用或单腿风险？ | Perps／组合策略风险状态机 |
| Gas 预算 | 每笔最高费用、每日累计费用、失败重试次数？ | 账户授权、Sponsor、预留与提交服务 |

表中是设计建议，不是 EIP 统一定义。

对 8130，SELF_PAYER 不自动继承 Manager 的交易预算；POLICY 不会将付款权限变成“只有业务成功才能扣 Gas”。对 8141，批准付款同样意味着承担交易执行成本，业务 Frame 失败不等于付款免责。[^8130-account][^8130-gas][^8141-approval][^8141-gas]

另外，8130 的 payer-auth 成本与用户 `gas_limit` 采用分离预算，报价系统不能仅把 `gas_limit × max_fee` 当成所有付款模式的完整最大负债；8141 则需计入 Frame 预算、原生签名、数据 floor 和首次状态增长。具体费用公式分别见两篇 deep dive。[^8130-gas][^8141-gas]

### 5.5 撤权必须拆成配置、执行权限和订单三层

建议为产品定义以下撤权清单：

| 对象 | 8130 | 8141／8250 | 不能误认为 |
|---|---|---|---|
| 尚未落地的授权材料 | Local epoch 可退休相应本地配置签名；跨链通道另有规则 | 由账户授权版本／签名域设计 | 旧材料失效就等于现有权限被删除 |
| 已激活 Agent | RevokeActor；注意 Account Lock | 修改 Session／权限状态 | 已撤权就能倒转已经执行的交易 |
| 已签业务订单 | 产品再次验证 Actor／Policy 与订单版本 | 产品再次验证 Session 与订单版本 | AA nonce 已消费就等于订单已取消 |
| 未结算成交 | 按产品撮合与结算规则处理 | 同左 | 撤单可以无条件取消已经成交的义务 |
| 已持仓风险 | 需要另外减仓／平仓／调整保证金 | 同左 | 停止 Agent 就等于风险自动归零 |

8130 尤其要避免：撤销 live Actor 后，仍有效的 JIT 配置材料再次将其授权回来。应根据授权通道组合处理 RevokeActor 与旧配置签名退休。[^8130-epoch][^8130-changes]

对从 EOA 演进的账户，还应审查普通交易与代码委托路径；Keystore 或 Session 撤权不应被宣传为所有旧密钥路径都已经消失。[^e8130]

对长期锁定的账户，8130 原生配置修改受到限制，高额度准入与紧急撤权之间存在取舍。可以研究产品层紧急阻断、短时授权或隔离的 Sponsor 锁定，但不能宣称这些替代了原生账户撤权，也不能默认 Sponsor 锁定后完全不影响付款资金管理。[^8130-lock][^repo]

### 5.6 Sponsor 的高频准入需要作为独立系统设计

大量独立用户并不意味着 Sponsor 没有共享瓶颈：他们可能依赖同一个 payer、同一余额、同一报价签名服务和同一预留账本。

8130 通过标准认证、账户锁定及准入约束形成相应路径；8141 的公共池则包含 canonical Paymaster、代码限制、余额预留与相关防失效机制。两者不是“只换一个付款签名”的同等工程。[^8130-validation][^8130-lock][^8141-paymaster]

对 Mantle，应单独测量：

```text
每秒接受多少待付请求
  → 最大费用预留是否超卖
  → 同时有多少用户依赖同一 Sponsor
  → 撤单／替换／过期后如何释放预留
  → Sponsor 余额不足时如何降级
  → 失败请求消耗多少真实预算
```

原生币由 Sponsor 支付、用户用 ERC-20 报销，是两段不同的资金关系。报销转账成功并正确分组，才可能在后续业务失败后保留；代币返回 `false`、余额被提前转走或报销价格变化，仍可能造成损失。[^erc20][^8130-execution][^8141-examples]

### 5.7 统一 SDK 不能简单统一成“交易成功／失败”

8130 可以出现：账户配置和前面的 Phase 成功，后面的业务失败。

8141 可以出现：原子组整体状态回滚，但组内先执行成功的 Frame 仍保留成功执行 status；组外后续 Frame 继续运行。两案都需要业务事件与状态来解释结果。[^8130-receipt][^8141-receipt][^8141-behavior]

建议 SDK 输出独立字段，而不是一个布尔值：

```text
transport_status       请求是否接收／入块
authorization_result   授权是否安装、撤销或仍有效
fee_result             谁付费、预扣多少、结算多少、报销是否成功
execution_result       Phase／Frame 的执行与共同回滚结果
business_result        资产创建、成交、撤单、保证金等权威状态
confirmation_level     当前状态所对应的确认级别
```

这些是 Mantle 统一 SDK 的建议，不是 EIP 规定的字段名。确认级别必须采用 Mantle 实际定义，不能把排序器接收或提前反馈称为最终性。[^req-feedback]

## 6. 建议的共同账户抽象：先统一产品行为，再接不同原生协议

### 6.1 定义一套产品级授权，而不是让产品直接依赖某一个 EIP 的细节

下面是**示意数据模型**，不是建议照抄的生产 ABI：

```text
AgentGrant {
  account
  agentIdentity
  policyVersion
  validUntil
  permittedOperations
  allowedTargetsOrMarkets
  allowedAssets
  allowedRecipients
  subaccountScope
  spendingBudget
  riskLimitReference
  feePolicyReference
  noncePolicyReference
}

Operation {
  account
  grantReference
  operationId
  subaccountId
  action
  parameters
  validUntil
  expectedBusinessVersion
}
```

其中 `spendingBudget`、`riskLimitReference` 的具体意义必须由产品定义。没有统一可靠价格来源时，不能把不同资产金额直接相加成一个“美元预算”。

两条原生路线只是不同的承载方式：

```text
统一 AgentGrant / Operation
        │
        ├─ 8130 adapter
        │    Actor + scope + Manager commitment
        │    → Policy-aware execution
        │
        └─ 8141 / 8250 adapter
             Session storage + Frame verifier + nonce-key policy
             → guarded execution
```

共同实现的核心是：目标与参数检查、资金权限、累计预算、订单验证、业务幂等和审计，而不是强求两种协议内部状态完全相同。

### 6.2 权限角色应按产品动作分开

| 角色／能力 | 可以做什么 | 默认不应隐含什么 |
|---|---|---|
| Owner／授权管理者 | 安装、修改、撤销策略，管理恢复 | 不必参与每次策略交易 |
| 发行 Agent | 创建资产、提交允许的发行参数 | 任意移动现有账户全部资产 |
| 交易 Agent | 在指定市场交易、撤单或提交受限策略动作 | 提现、升级账户、任意扩大 allowance |
| 风险操作授权 | 执行明确定义的减风险操作 | 无条件任意平仓、任意改变受益人 |
| Sponsor 授权 | 在费用规则内支付 Gas | 获得用户交易、提现或修改策略的权限 |

这是建议的权限拆分，不是给“风控 Agent”无限权力。所谓 reduce-only 也必须由产品验证，不能仅相信调用方声明自己在减风险。

### 6.3 审计链路要同时保留原生身份与业务身份

建议索引关系为：

```text
transactionHash
  → 原生 sender / payer
  → Actor 或验证器识别的 Agent
  → grant / policyVersion
  → operationId
  → orderId / marketId / subaccountId
  → 实际执行与资金结果
```

对于链下订单批量结算，还要额外区分：

```text
本笔交易提交者／撮合者
        与
每一份订单所属的用户及其 Agent
```

该设计回应统一签名与审计需求。8130 的标准 Actor 接口可以减少一部分自定义字段；8141 则需要 Mantle 的账户与 SDK 约定，才能形成同样统一的可观测性。[^req-account][^8130-sign][^8141-approval]

## 7. Agentic Meme Launchpad：覆盖程度与推荐适配方式

### 7.1 不要再把它当成普通“首次买入”Launchpad

原稿认为 Launchpad 主要是大量不同 sender 同时入场，因此对 nonce 方案的判别力不大。这只覆盖一类负载。

本项目明确包含持续自动发行、发现、交易、权限管理与退出；需要同时保留两个工作负载：[^req-products]

| 负载 | 要验证什么 |
|---|---|
| 大量独立用户首次进入 | 创建／初始化、授权安装、Sponsor 接纳、热点产品合约、真实失败成本 |
| 同一用户多个 Agent 同时行动 | 独立队列、共享预算、策略隔离、通道干扰、撤权与恢复 |

因此应把原稿结论改为：

> 普通多用户抢购不必然体现多维 nonce 的优势；Agentic Launchpad 是否能从中获益，取决于同账户下的 Agent 数量、请求依赖和资金共享方式。

不能凭跨账户并发测试，证明同账户自动化已经具备目标体验。

### 7.2 同一业务意图的三条路径

**业务意图：Agent 在有效授权和预算内，用 quote token 买入资产，平台支付原生 Gas。**

| 阶段 | 普通 EOA 基线 | 8130 设计路径 | 8141＋8250 设计路径 |
|---|---|---|---|
| 初始授权 | 普通信封没有受限 Session 模型；需额外应用／账户机制 | Owner 配置 Actor、POLICY、Manager 和必要 nonce 权限 | Owner 安装 Session grant、Frame 规则与 key 策略 |
| 准备买入 | Owner 签名，或让 Agent 持有相应账户密钥 | Agent 构造受 Manager 门禁约束的 calls | Agent 构造完整允许的 Frame 序列 |
| Gas | 用户账户准备原生币 | Sponsor 提供 payer_auth | Sponsor 在验证 Frame 批准付款 |
| 并发 | 同一 EOA 标量 nonce | key／sequence 或 nonce-free | 8250 key／sequence；实际接纳仍看提交路径 |
| 业务检查 | 产品合约规则；额外策略需另建 | Policy-aware 账户／Manager 检查预算与动作 | 验证器检查静态权限；执行入口检查动态预算 |
| 原子执行 | 独立 approve 与 buy 不共同回滚 | 放入一个 Phase，或由受限入口内部原子执行 | 放入 Atomic Frame group，或由受限入口内部原子执行 |
| 失败反馈 | 普通回执＋业务状态 | Phase、授权配置、费用与业务结果分别解读 | Frame 与原子组回滚、费用与业务结果分别解读 |

这是方案组合的示例。初始账户部署、Owner 授权和 Agent 交易是否能一次提交，取决于具体账户和初始化路径，**不能无条件宣称所有步骤都只需一笔交易或一次签名**。详细逐步示例见前两篇。[^8130-execution][^8130-changes][^8141-examples][^e8250]

### 7.3 发行与首次交易应使用业务 operation ID

建议把“创建资产并初始化发行状态”作为一个明确业务操作；若产品允许首次买入与其同步完成，可以加入同一回滚边界。

```text
operationId = 用户在授权域内定义的唯一业务标识

执行：
  检查 operationId 未处理
  → 创建资产
  → 初始化发行状态
  → 可选的首次买入
  → 记录操作结果
```

这里不能只使用 8130 `replay_id`：更换 Sponsor、调整有效期等会改变该标识。8141／8250 的 nonce 也不能直接取代产品层幂等 ID。重试可能使用新的原生 nonce，却仍然对应同一个“发币”业务意图。[^8130-replay][^e8250]

业务应定义重复请求返回已有结果、拒绝重复，还是要求新的 operation ID；不能让 SDK 在未知状态时盲目重发。

### 7.4 预算检查必须抵御多 Agent 并发和回调

假设两个 Agent 共享 100 单位 quote token 预算，同时各请求花费 80：

```text
错误模型：
两个链下服务都看到“剩余 100”
    → 都签字放行
    → 实际累计花费 160

需要的模型：
权威执行时检查／占用预算
    → 第一个成功后，第二个按更新状态检查
    → 总额不能越界
```

这是并发安全设计要求，不是说 EVM 会失去顺序一致性。问题在于链下预检查或授权签名不能替代最终的链上累计预算检查；回调和重入也不应绕过占用规则。

若操作失败时回滚预算，应确保资产变化也在相同业务回滚范围内；若独立收取报销，其费用预算需要另记。

### 7.5 毕业迁移：AA 支持本次迁移的原子执行，不覆盖整个生命周期

需求文档要求毕业时储备处理、建池与流动性迁移的状态连续性。[^req-composition]

合理的回滚目标是：

```text
确认本次毕业条件
  → 冻结／结束相应发行状态
  → 处理储备
  → 创建或初始化目标池
  → 迁移流动性
  → 写入毕业完成状态
```

这些动作如果在同一执行域可同步调用，就可以研究放入同一 Phase／Atomic group，或产品合约内部一个原子入口。

但“数小时前发行，若干轮交易，之后毕业”不可能因采用 AA 就成为一笔长时间原子事务。迁移所需权限也未必属于普通买入 Agent，应单独设计调用者与条件。

### 7.6 报价资产与原生币调用是两个接入问题

本项目构想围绕 mStocks quote token，教学示例用 USDC 只是便于解释 allowance 与买入。实际代币的授权、转账返回值、金额单位及业务可用性，应当以所选资产合约为准。

若另行支持原生 MNT 买入，两案的顶层调用表达不同：

| 方式 | 原生币如何进入业务调用 |
|---|---|
| 8130 | 顶层 `call` 只有目标与 calldata，没有 value；由已授权的账户代码内部发起带 value 的调用 |
| 8141 | `SENDER` Frame 可显式携带 value；验证器必须将其纳入 Session 资金权限检查 |

这是 SDK 和受限执行入口的适配差异，不足以单独决定路线。用户的买入本金、用户对 Sponsor 的代币报销、Sponsor 支付的链级 Gas，必须分别记账，不能因为资产名称相同而混成一笔预算。[^8130-execution][^8141-frames]

### 7.7 对 Launchpad 的适配判断

**两案都有实现基础；当前最关键的补齐项是策略和 Sponsor，而不是 AA 格式本身。**

8130 值得验证的增量是：统一 Actor 与授权来源、较规整的受限入口、原生多通道／nonce-free。8141 值得验证的增量是：灵活组合验证、付款和执行，以及通过账户规则在批准前约束完整动作计划。

最终应以“相同授权边界下成功处理目标负载的成本与可靠性”比较，不能根据一次买入演示选型。

## 8. Perps：必须按订单进入系统的方式分别评估

### 8.1 初期 Vault／预言机型：AA 主要改善账户与请求体验

需求文档中，这一阶段的重点是请求执行、Oracle 协调、Keeper、拥堵费用和恢复。[^req-vault]

AA 可以帮助组织：

```text
授权 Agent
  → 注入保证金
  → 提交开仓／减仓请求
  → 由 Sponsor 支付费用
  → 追踪请求状态
```

但如果协议是两阶段 `request → execute`：

```text
现货买入成功 + Perps 开仓请求创建成功
```

不等于：

```text
现货实际成交 + Perps 实际对冲成交
```

共同原子成功。

无论 8130 还是 8141，都不能只靠交易包装把异步 Keeper 执行变成同步成交。此时账户层完成的是请求授权与提交，单腿敞口管理仍要由策略与产品解决。

**适配结论：** 以账户安全、代付和请求恢复为先；本阶段并不能充分证明原生多维 nonce 值得改链。

### 8.2 混合撮合、链上结算：用户订单与原生交易不是同一对象

典型流程是：

```text
用户入金
  → Agent 离线签署订单
  → 撮合系统接受／取消／匹配
  → 撮合者或提交者构造链上结算交易
  → 产品验证订单并更新资金与仓位
```

因此需要分别管理至少三类标识：

```text
用户订单 ID 与订单取消版本
撮合／成交 ID 与累计成交量
提交者原生交易 nonce／重放保护
```

需求文档已经强调取消、部分成交、结算滞后、幂等和恢复；这些不能由用户 AA nonce 代替。[^req-hybrid]

**8130 集成重点：** 默认 ERC-1271 不接受 POLICY-only Agent。应使用 Actor-aware 验证，识别用户订单的 Actor、scope 和 Policy，再校验具体订单权限。不能为了适配旧订单接口添加 OPERATOR，因为它会绕开原有 POLICY 门禁。[^8130-sign][^8130-account]

**8141 集成重点：** Frame 验证解决的是当前原生交易的授权。若 sender 是撮合者，它的验证结果不自动授权所有用户订单；用户订单仍需要独立的 Session／账户签名验证与取消规则。[^8141-approval]

**适配结论：** 这一模式下，两案对用户高频报价路径的差距可能小于原生直发模式。应优先评估订单权限接口与批量结算，而不是只测用户 nonce。

### 8.3 通用 EVM fully onchain Perps：多维 nonce 才直接进入挂撤改单路径

如果每次挂单、撤单或改单都是用户原生链上交易，需求变成：

```text
多个 Agent／策略持续提交
  → 尽量减少无关 nonce 依赖
  → 受限密钥验证
  → 快速接纳与排序
  → 更新订单簿／保证金
  → 返回权威状态
```

8130 的内置 2D nonce 和 nonce-free，8141＋8250 的 keyed nonces，都与这条路径直接相关；但公共池单 sender 待处理限制、Sponsor 共享预留和热点市场状态仍需独立解决。[^8130-nonce][^8141-mempool][^e8250]

这里应把延迟分解为：

```text
生成与签名
+ 网络与入口排队
+ 验证与 Sponsor 接纳
+ nonce／状态依赖等待
+ 排序等待
+ 市场执行
+ 状态与回执发布
```

AA 只影响其中部分环节。目标指标应当是“旧订单何时不可再成交／新报价何时在权威状态中生效”，不是仅报告 RPC 接收耗时。[^req-feedback][^req-ordering]

### 8.4 撤旧单＋挂新单有两种合理但不同的失败策略

| 产品意图 | 合理回滚语义 | 8130 | 8141 |
|---|---|---|---|
| 保持报价替换的全有或全无 | 新单失败则旧单恢复 | 同一 Phase | 同一 Atomic group |
| 优先消除旧报价风险 | 撤单成功应保留，即使新单失败 | 撤单放前一 Phase，新单放后一 Phase | 撤单与新单分组，显式处理后者是否依赖前者成功 |

两种策略没有普遍正确的一种，必须由订单状态机和做市接口指定。

还要处理反方向失败：

> 如果撤单失败，是否允许继续挂新单？

8130 前一 Phase 失败会跳过后续 Phase；8141 独立 Frame 失败后仍可能继续执行后续独立组。因此 8141 需要显式的业务条件、共享结果或账户执行入口，不能仅靠排列顺序表示依赖。[^8130-execution][^8141-behavior]

此外，8141 Frame 间的 transient storage 会清除，不能把普通同笔 EVM 交易内跨调用共享的 `TSTORE` 方案直接用于跨 Frame 条件传递。[^8141-crossframe]

### 8.5 多维 nonce 不交付 Cancel Priority

独立撤单通道可以减少被某个未完成序号阻塞的情况，但不保证撤单先于旧单成交。

需要产品和排序规则回答：

```text
订单接受和撤销的权威顺序在哪里确定？
同一批次内撤单与成交怎样比较？
已成交但未结算的订单还能否取消？
谁可使用风险／撤单优先路径？
如何防止把普通交易伪装成紧急撤单？
```

这些问题来自需求文档对快速撤单、RFQ 时序和风险操作保障的要求，不是任何一个 AA EIP 的默认行为。[^req-ordering]

### 8.6 子账户必须有真实账本和权限边界

建议至少将以下维度分开：

| 维度 | 负责解决的问题 |
|---|---|
| Actor／Session | 谁在提交操作 |
| nonce key | 哪些请求存在重放顺序依赖 |
| subaccount ID | 哪个资金或保证金账本承担结果 |
| policy version | 操作受到哪版授权限制 |
| market／order ID | 操作影响哪一个市场和订单 |
| risk group | 哪些仓位共享保证金或风险限额 |

给 Agent A 和 B 分配不同 Actor、不同 nonce key，不会自动阻止它们消耗同一 cross-margin 账户的保证金。

若产品要隔离损失，必须定义独立保证金、可转移范围、借用额度或共享风险限额；它们由产品状态机执行。[^req-account][^req-perps]

### 8.7 专用执行模块：账户规则必须进入统一验证边界

在 Mantle 统一验证边界内引入专用市场模块时，至少要决定：[^req-domains]

```text
专用操作是否仍封装在 8130／8141 交易内？
专用模块怎样读取 Actor／Session 及撤权？
nonce 是否与 EVM 账户共享，还是有单独的订单序号？
模块调用的费用、权限和失败怎样计量？
EVM 与模块的资产变化是否在共同回滚边界内？
实际验证程序怎样检查新增的认证与状态转换？
```

采用某个 AA EIP 不会自动使专用操作受到等价的权限保护。若另建一套绕过验证器的高速入口，必须证明它保留相同授权、费用与重放语义。

**适配结论：** 此路线下账户方案应与专用操作格式联合设计。不能先在 EVM 钱包演示成功，再认为市场快路径已经继承全部能力。

### 8.8 L3：父链 AA 不等于 L3 账户，也不等于跨域同步组合

若 Perps 在独立执行域，Mantle L2 负责结算、托管和退出，那么通常至少有两套状态：父链账户／资产状态，以及 L3 的订单／保证金状态。[^req-l3]

需要分别定义：

```text
L2 授权是否映射成 L3 权限？
L2 撤权如何传播，在哪个 L3 状态版本后生效？
跨域充值、提现和订单操作怎样防重放？
排序器故障时，用户如何独立取消、减仓或退出？
L3 与 L2 重组／确认级别变化如何协调？
```

8130 的配置可移植性或 8141 的 Frame 编排，都不自动解决这些问题。跨域现货与 Perps 对冲不能仅因两边都支持 AA 就被称为同步原子执行。

**适配结论：** 此时应分别评估 L2 资产入口账户与 L3 交易账户；不要把独立执行域的工作量记作某个 EIP 的小型适配项。

## 9. 哪些问题必须明确排除在“AA 已解决”的范围之外

| 不属于 AA 自动交付的能力 | 原因 |
|---|---|
| 更好的成交价格、流动性深度 | 由流动性、做市、路由与市场机制决定 |
| Oracle 正确与风险模型安全 | 需要价格输入与产品风控规则 |
| 热点订单簿真正并行 | 共享状态与确定性排序仍存在依赖 |
| 更短 blocktime 必然提高吞吐 | 执行、数据发布和验证可能仍是瓶颈 |
| 私密订单、隐藏仓位、抗 MEV | 两案均未单独提供交易加密或完整排序保护 |
| Agent 绝不会亏损 | 合规权限内仍可能作出损失性交易 |
| 用户“无需原生币”意味着系统无 Gas 成本 | 成本转移给 Sponsor，不是消失 |
| 原子请求就是原子成交 | 异步市场的请求与实际执行仍分离 |
| 多 nonce 就有资金隔离 | nonce 管理重放顺序，不管理保证金账本 |

以上是从规范范围和需求分层得出的边界判断，不是对两案的否定。尤其 8141／8250 可以作为某些隐私方案的交易基础，但不能据此宣传为当前产品已经拥有隐私或抗 MEV 保证。[^e8130][^e8141][^e8250][^req-resources][^req-domains]

## 10. 哪些工作在合约层，哪些会触及 Mantle 链本身

### 10.1 先建设两条路线都要用的产品能力

建议先明确并尽量共用：

```text
授权行为规范与权限版本
Policy-aware 执行入口
交易／风险／Gas 预算定义
订单签名验证与取消规则
业务 operation ID 和幂等
Sponsor 策略与预留
统一 SDK、事件与恢复模型
```

这些能力不会因为选择原生 AA 消失，也是与现有合约层账户方案公平比较的基础。

本篇不重做用户已经完成的其他 AA 调研，也不凭空断言现有方案在 Mantle 上的性能；应直接将其作为后续同负载测试的一组基线。[^req-principle][^req-aa]

### 10.2 8130 原生集成的工作包

| 工作包 | 主要内容 |
|---|---|
| 交易与状态转换 | 0x79 编解码、sender／payer 哈希、认证、费用、账户变更、回执 |
| 规范账户系统 | Keystore、canonical authenticators、默认／自定义账户的兼容与版本 |
| nonce 与上下文 | 有序状态、nonce-free 共识去重、上下文接口、重组恢复 |
| 执行与错误处理 | Manager 门禁、Phase 提交／回滚、配置变化与业务失败边界 |
| 准入与反滥用 | 认证器 Profile、Actor／账户失效依赖、锁定与 Sponsor 接纳 |
| 验证体系 | 将新增交易和原生认证／状态操作纳入实际执行验证路径 |
| 工具 | 签名 SDK、估价、浏览器、索引、钱包权限展示和错误归因 |

“No EVM changes”不能理解成“不需要改链”。即使不增加普通 EVM 操作码，原生交易处理、系统状态、计量、准入与验证仍需适配。[^e8130][^repo]

### 10.3 8141＋8250 原生集成的工作包

| 工作包 | 主要内容 |
|---|---|
| 交易与签名 | 0x06 编解码、签名方案、canonical hash、预验证 |
| VM 执行上下文 | DEFAULT／VERIFY／SENDER、APPROVE、内省指令及身份切换 |
| 原子与回执 | Atomic group、失败后继续、逐帧回执、日志与回滚、transient storage 语义 |
| 费用计量 | execution／state Gas、数据 floor、预扣、退款与状态回补 |
| keyed nonces | 8250 状态、key 集合、首次写入计费、内省、激活兼容 |
| 准入与 Sponsor | 验证前缀、状态依赖、canonical Paymaster、预留与替换 |
| 账户与工具 | 完整 Frame 策略验证、Session、签名展示、Gas 估计、索引恢复 |
| 验证体系 | 新操作码、Frame 执行和 nonce 状态的验证适配 |

不能只算 8141 信封支持，却忽略 8250、Session 实现或其 Gas 依赖的集成工作。若 Mantle 采用与官方依赖不同的 Gas 方案，应将差异版本化，而不是仍声称完全等同于原 Draft。[^e8141][^8141-gas][^e8250]

### 10.4 当前不能可靠给出人天估算

资料未提供目标客户端分支、现有账户实现、可复用的验证模块、团队分工与完成标准，因此无法从 EIP 篇幅推导开发人天。

可以先按以下交付物拆工作，再估算：

```text
规范差异清单
→ 最小参考实现
→ 一致性测试向量
→ 完整安全策略账户
→ 同负载基准
→ 验证系统集成
→ 工具与运维
→ 外部审计及升级方案
```

这里的不确定性是缺少项目实现输入，不是因为方案无法研究或比较。

## 11. 工程验证：先验证安全等价，再比较性能

### 11.1 比较组与控制变量

建议至少设置：

| 比较组 | 目的 |
|---|---|
| A：既有／拟采用的合约层账户方案 | 检验是否真的需要原生变更 |
| B：8130＋完整受限账户＋Sponsor | 评估账户与认证标准化的增量 |
| C：8141＋8250＋同等受限账户＋Sponsor | 评估 Frame 编排与 keyed nonces 的完整方案 |
| 可选 D：8141 本体 | 仅用于分离 8250 的增量，不作为多通道公平对照的唯一代表 |

须保持相同业务约束、资金分布、订单比例、Agent 数量、失败率、负载持续时间、硬件和验证范围。

如果 B 验证了滑点、接收人和累计预算，而 C 只做裸签名检查，其吞吐对比没有产品决策意义；反过来也一样。

### 11.2 先建立必须通过的安全验收

下面是**建议测试集，不是已发现的 Mantle 漏洞**：

| 测试 | 期望结果 |
|---|---|
| 受限键追加提现／扩大 allowance | 完整路径拒绝越权，不仅某一入口拒绝 |
| 8130 混入 OPERATOR 或账户 self-call 旁路 | 权限配置与执行入口不能悄悄扩大 Agent 权力 |
| 8141 在已检查 Frame 后追加未检查 SENDER Frame | 批准前拒绝越界计划 |
| 多 Agent 同时消耗共享预算 | 按权威执行状态计算，不发生额度超卖 |
| Agent 使用其他策略的 nonce key | 明确可拒绝的位置及剩余通道干扰边界 |
| 高费用／大量失败交易消耗 Gas | 独立费用预算、限速与责任边界生效 |
| 撤销 live Actor 后重放旧 JIT 授权 | 已退休配置不能恢复权限 |
| 锁定账户或 Sponsor 发起紧急停止／资金调整 | 行为与产品承诺一致，不把锁定限制隐藏在 SDK 后面 |
| 旧订单在撤权后结算 | 按明确业务规则验证，而非误用撮合者身份 |
| 改 Sponsor、改有效期或换 nonce 重试 | 业务操作不被重复执行 |
| ERC-20 返回 false、报销失败或被提前花光 | 不错误标记“已收到报销”，费用处理符合约定 |
| 原子组失败、配置或前序动作保留 | SDK 正确报告状态，不按单个布尔值判断 |
| 节点重组与订阅中断 | nonce／去重、业务结果、预留和索引可恢复 |

机制对应风险见两篇 deep dive；测试方式和期望安全属性属于本项目的建议验收标准。

### 11.3 六组必须覆盖的产品工作负载

| 负载 | 设计重点 | 主要指标 |
|---|---|---|
| W1 大量新用户进入 Launchpad | 首次创建、授权安装、Sponsor 共享、热点买入 | 每个完成用户的总成本、接纳失败率、状态增长、成功业务数 |
| W2 同账户多 Agent 并发 | 独立队列、共享预算、Actor／key 干扰 | 各操作流延迟、公平性、可接受并发、无效请求影响 |
| W3 Perps 连续挂撤改单 | 直发与链下订单两种模型分测；原子替换与风险优先分测 | 旧报价实际失效、有效新报价、仓位更新的 p50／p95／p99 |
| W4 密钥失陷与紧急停止 | 旧授权、live Agent、锁定、旧订单、备用管理路径 | 从紧急请求到目标权限／订单确实失效的时间及残余影响 |
| W5 付款与组合失败 | 报销失败、业务失败、post-op 失败、首次状态写入 | 付款负债、预留误差、残余 allowance／授权、业务正确性 |
| W6 长时运行与故障恢复 | nonce-free 容量、持久 key 增长、重组、Sponsor 枯竭、节点恢复 | 状态与数据量、验证积压、恢复完整性、重复操作和预算泄漏 |

不要只用持续成功的、彼此无状态冲突的转账来证明 Perps 账户方案可用。需求文档已经指出热点市场和共享保证金的串行部分，需要用实际工作负载识别。[^req-domains]

### 11.4 指标应指向“权威业务生效”，而非前端观感

建议分层记录：

```text
t0：Agent 决定提交
t1：本地签名和 Sponsor 报价完成
t2：入口接收
t3：通过准入／预留
t4：纳入权威执行顺序
t5：业务状态更新
t6：客户端观察到该状态
t7：达到产品声明的确认级别
```

其中排序器预确认、执行状态和最终性应按实际系统定义，不能混用。

报告应同时提供成功率、失败类型、费用、状态增长和验证开销。一个方案仅降低 `t2 - t0`，却让 `t5 - t0` 或失败成本恶化，不一定改善目标产品体验。[^req-feedback]

### 11.5 通过条件先定义，再测量

本篇不填未经确认的 TPS、毫秒或 Gas 优势数字。建议由产品和链团队共同确定：

```text
目标 Agent 数与并发模型
最大可接受的授权／撤权生效窗口
可接受的撤单与敞口更新时间分布
每用户／每策略 Sponsor 预算与失败比例
最大在途风险、结算滞后与恢复窗口
数据／状态／验证的持续增长上限
```

这些阈值确定后，才能判断原生 AA 改动是否值得，而不是测完后选择看起来最有利的指标。

## 12. 规范成熟度与维护：在立项前解决，而不是留到上线前

截至核对日期，8130、8141、8250 均为 Draft；8130 canonical 仓库明确提示未审计。原稿指定 commit 不等于它的所有依赖也已经固定。[^e8130][^e8141][^e8250][^repo]

建议为每一条 PoC 路线保存：

```text
EIP 文本版本
canonical 合约版本
客户端版本
Gas 与交易激活规则
公共／专有准入规则
账户策略版本
验证程序版本
测试向量与已知差异
```

两篇 deep dive 已标出应继续澄清的文字或组合问题，包括：

| 方向 | 需要澄清或通过测试固定的事项 |
|---|---|
| 8130 | payer-auth 上限、预扣与实际计量的完整一致口径；锁定下配置动作在不同入口的许可；canonical ABI／存储版本 |
| 8141 | 公共池对 non-canonical Paymaster 的不同段落表述；expiry 与部署前缀的组合；原子组回执与 SDK 解码 |
| 8141＋8250 | 组合后字段与 Gas 变量的版本一致性；首次非零 key 状态成本；交易激活及旧待处理交易行为 |
| 两案在 Mantle | L2 原生／数据费用映射、账户迁移、排序器服务策略、验证路径与工具兼容 |

这些事项不是证明提案不可用，而是防止“规范读起来能工作”被误认为“生产集成已经没有语义选择”。

## 13. 建议的决策路径

### 13.1 第一阶段：冻结共同业务安全模型

先明确授权、预算、子账户、撤权与订单语义，做出最小 Policy-aware 账户／产品适配器，并形成共同测试向量。

这个阶段无论最终采用哪种原生协议都不会浪费，因为它解决的是产品自己的权限和状态机问题。

### 13.2 第二阶段：并列验证原生增量，而不是提前锁定结论

在相同工作负载下比较：

```text
合约层基线
vs.
8130 完整实现
vs.
8141＋8250 完整实现
```

可优先推进 8130 的 PoC，但不要因此弱化对 8141 对照组的策略实现，也不要将 8250 排除后再宣称 8130 独有多通道能力。

### 13.3 第三阶段：根据条件选择，而不是给抽象 EIP 打总分

| 若验证结果显示…… | 相应决策方向 |
|---|---|
| 现有合约层方案满足安全、体验与成本目标 | 不急于为核心产品修改原生交易协议 |
| Actor 标准化显著减少跨产品接入复杂度，多通道／nonce-free 在直发负载有实测价值 | 8130 的原生集成更有立项依据 |
| 完整 Frame 编排、批准前策略检查及 keyed-nonce 约束更适合账户架构，准入和工具成本可控 | 8141＋8250 的原生集成更有立项依据 |
| 主要瓶颈是热点市场执行、Oracle、排序或证明积压 | 将资源投入对应执行层工作，不用 AA 替代真正优化 |
| 专用模块或 L3 成为终态 | 将账户方案纳入该域完整的认证、重放、费用与验证设计，再决定继承哪些标准 |

这是一组条件式工程建议，不是既成测试结论。

### 13.4 对原稿结论的最终修订

应保留：

> 8130 的账户权限、Canonical Authenticators、赞助与二维 nonce 标准化集成，值得在 Mantle 产品负载中优先验证。

应补充：

> 其价值在链上直发、高频同账户自动化场景中更可能进入关键路径，但仍需解决 Manager 的资产执行权限、通道干扰、Gas 预算、锁定撤权与订单验证。

应替换过强表述：

> 8141 不是“所有签名都在 EVM 验证”、不是“不能保留独立报销”，也不能在忽略 8250 后被概括为“只能串行”；Launchpad 也不能在未定义 Agent 负载时被断定为没有判别力。

**最终建议：将两案都当作原生交易基础，而不是完整 Agent 产品。以同一套账户安全和业务状态要求驱动实现，再用真实负载证明哪些原生能力值得引入 Mantle。**
