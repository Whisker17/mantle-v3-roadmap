### 1.3 恒定乘积不变量 k

```
k = vSOL₀ × vTOK₀
  = 30,000,000,000 lamports × 1,073,000,000,000,000 base units
  = 32,190,000,000,000,000,000,000,000            (raw)
  = 30 × 1.073×10⁹ = 3.219×10¹⁰                   (SOL·token)
```

**关键概念**："virtual reserves" 是**纯记账数字**，池子里并不真的有 30 SOL。它的作用是给曲线一个**非零起始价**并压平初期斜率，解决冷启动问题：如果从真实储备 0 开始，第一枚代币价格为 0，第一个买家会以近乎免费的价格吃掉全部供应。

### 1.4 买入公式

程序内部用 u128 整数运算。给定投入 lamports 数量 `Δs`（**已扣除手续费后真正进入曲线的部分**）：

```
新虚拟 SOL 储备:   vSOL' = vSOL + Δs
新虚拟代币储备:    vTOK' = ⌊ (vSOL × vTOK) / vSOL' ⌋ + 1      ← +1 为向上取整，防舍入套利
获得代币:          Δt    = vTOK − vTOK'
实际上限:          Δt    = min(Δt, realTokenReserves)         ← 曲线售罄即触发毕业
```

反向（程序 `buy` 指令实际签名是"我要买 N 枚代币，最多付 M lamports"）：

```
所需 lamports:     Δs = ⌊ (vSOL × Δt) / (vTOK − Δt) ⌋ + 1
总支出:            Δs_total = Δs × (1 + fee)                  ← 费用加在成本之上，非从中扣除
```

### 1.5 卖出公式

```
曲线返还 lamports: Δs = ⌊ (Δt × vSOL) / (vTOK + Δt) ⌋
到手:              Δs_net = Δs × (1 − fee)                     ← 费用从返还额中扣除
储备更新:          vSOL −= Δs ,  vTOK += Δt
```

### 1.6 现货价格与市值

```
现货价 P = vSOL / vTOK                    (SOL per token)
市值   MC = P × 1,000,000,000             (以总供应计价，pump.fun UI 采用此定义)
```

- **开盘价** = 30 / 1,073,000,000 = `2.795899×10⁻⁸` SOL/token → **开盘市值 27.959 SOL**
- **毕业价** = 115.005359 / 279,900,000 = `4.108802×10⁻⁷` SOL/token → **毕业市值 410.880 SOL**
- **全程涨幅 = 14.6958×**（这是一个**结构性常数**，与 SOL 价格无关）

### 1.7 毕业募资额的严格推导 —— "85 SOL" 从哪来

曲线售罄的定义是 `realTokenReserves = 0`，即 793,100,000 枚全部售出。此时：

```
vTOK_end = 1,073,000,000 − 793,100,000 = 279,900,000
vSOL_end = k / vTOK_end = 32,190,000,000 / 279,900,000 = 115.005359 SOL
真实募得 = vSOL_end − vSOL₀ = 115.005359 − 30 = 85.005359 SOL
```

**本人程序化验算结果**：以整数逐步模拟买入 793,100,000 枚，得 `85.005359 SOL`，k 不变量校验 `1.000000000`。`[链上核实]`

> 所以广为流传的 **"85 SOL 毕业"是精确的**（85.005359），且它**不是一个可调参数**，而是 (30, 1.073B, 793.1M) 三者的唯一解。

5. **协议的收入结构因此高度依赖曲线阶段与刚毕业阶段**（95/93 bps），而非成熟代币（5 bps）。这解释了为什么 pump.fun 的收入与"新币发行量"强相关、与"存量代币市值"弱相关。

### 6.4 基础设施技术细节

#### RPC：为什么公共 RPC 不够用
- 公共 RPC（`api.mainnet-beta.solana.com`）有严格速率限制——**我在本次研究中就多次撞到 `429 Too many requests`**，且不提供 `getProgramAccounts`。
- 抢开盘需要**毫秒级**的新币发现 + 高频状态读取，公共节点在两个维度都不可用：延迟与配额。
- 供应商差异：**Triton ONE**（Yellowstone Geyser 的开发者，最底层）、**Helius**（开发者体验 + MEV Protect + 优先费估算 API）、**QuickNode**、**Shyft**（pump.fun 专用解析 API）。
- dedicated node 成本：月费数百至数千美元量级 `[二手，具体报价未核实]`。

#### gRPC Yellowstone Geyser —— 抢开盘的关键
- **架构**：Geyser 是 Solana 验证者的**插件接口**，允许在验证者进程内直接订阅状态变更，绕过 RPC 层。Yellowstone 是 Triton ONE 开发的 gRPC 实现。
- **订阅类型**：account updates、transactions、slots、blocks、block metadata，均支持按程序 ID / 账户过滤。
- **相比 WebSocket `logsSubscribe` 的优势**：`logsSubscribe` 要等交易被处理并生成日志、经 RPC 层序列化后推送；Geyser 在验证者内部第一时间输出。差异是**数十至数百毫秒**——在抢开盘场景等于生死。
- **托管方**：Helius、Shyft、Chainstack、Triton ONE。

#### Jito
- **Block Engine + bundle**：最多 **5 笔**交易的原子包，全成或全不成（失败则不上链、不消耗）。
- **tip 机制**：8 个 PDA tip 账户；最低 tip 10,000 lamports；Jito 收 5% 手续费。`[二手]`
- **TipRouter 分配**：**94%** 给验证者与质押者、**2.7%** 给 Jito DAO 国库、**0.3%** 给 NCN operator。每 epoch 由 NCN operator 提交 Merkle root，需 66.7% 质押权重共识。`[二手]`
- **规模**：2024 全年处理 >30 亿笔 bundle，累计 **375 万 SOL** tip。日 tip 从 2024-01-11 的 781 SOL 涨到 2024-11-19 的 **60,801 SOL** 峰值。日 bundle 量峰值 2024-12-21 达 **2,440 万笔**。Jito-Solana 客户端验证者质押占比：2024 初 48% → 2025 初 92% → 2026 年中 >95%。`[二手]`
- **ShredStream**：直接订阅 shred 流，进一步压缩感知延迟。
- **BAM（Block Assembly Marketplace）**：2025-07-21 发布，见 §7.4。

#### swQoS（stake-weighted Quality of Service）
- **原理**：验证者的 QUIC 连接容量按**质押权重**分配。总容量中 **80% 预留给按 stake 加权的连接，20% 留给未质押连接**。
- 一个持有网络 x% 质押的验证者，可获得 leader TPU 入口 x% 的保证带宽份额。
- **为什么终端要买 staked RPC**：拥堵时未质押连接的 20% 通道会被海量交易挤爆，交易根本到不了 leader。staked connection 让交易走"预留车道"。
- 这也意味着**交易的"上链权"在结构上是可购买的**——这是 Solana 一个常被忽略的中心化压力点。

#### priority fee 与 compute unit
```
Prioritization Fee = Compute Unit Limit × Compute Unit Price (micro-lamports/CU)
```
- 通过 `SetComputeUnitLimit` + `SetComputeUnitPrice` 两条 ComputeBudget 指令设定。
- 典型交易消耗 200,000–400,000 CU。常见 CU price：低 ~50,000、中 ~300,000+、高 1,000,000+ micro-lamports/CU。`[二手]`
- 估算工具：`getRecentPrioritizationFees` RPC（**可按具体账户查询"这条账户线的行情价"**——这正是 local fee market 的可观测体现）、Helius `getPriorityFeeEstimate`、QuickNode Gas Tracker、Triton Priority Fee Tracker。

#### 低延迟发送服务
Nozomi、Astralane、0slot、Temporal、Paladin P3、bloXroute —— 提供与 leader 的专线/优先转发，绕开公共 TPU 入口。这一层是纯粹的**延迟商品市场**。

### 6.5 一笔 pump.fun 抢开盘交易的完整技术路径

| # | 步骤 | 使用的基础设施 | 延迟预算 |
|---|---|---|---|
| 1 | 感知新币 `CreateV2` 事件 | **Yellowstone gRPC Geyser**（订阅 pump 程序 transactions），非 WebSocket | ~1–20 ms |
| 2 | 解析指令、提取 mint / bonding curve PDA、拉取元数据 | 本地解码（PDA 本地派生，**不发 RPC**） | <1 ms |
| 3 | 风控过滤（dev 持仓、社交、黑名单） | 本地缓存 + 预取 | ~1–5 ms |
| 4 | 构造 `buy` 交易（含 ComputeBudget、滑点、ATA createIdempotent） | 预签名模板 + 缓存 blockhash | ~1 ms |
| 5 | 发送 | **Jito bundle（含 tip）** 或 **staked connection / 低延迟发送服务**，常多路并发冗余发送 | ~5–50 ms |
| 6 | 落块确认 | leader TPU → Banking Stage → slot | 350–400 ms（1 slot） |

**关键工程原则**：
- 步骤 2–4 **绝不能有网络往返**。所有 PDA 本地派生、blockhash 预取、交易模板预构造。任何一次 RPC 调用就输了。
- 步骤 5 通常**多路径并发**（Jito + 多家低延迟 sender 同时发），用冗余换成功率；代价是重复 tip。
- 真正的竞争发生在步骤 1 与 5，且**很大程度由机房物理位置决定**（与 leader co-location）。这是资本密集型竞争，不是算法竞争。

## 7. MEV：Solana sandwich、Jito tips、防夹 RPC 原理

### 7.1 无全局 mempool 的架构含义

- Solana **没有**公开全局 mempool。交易经 **Gulf Stream** 直接转发给当前及即将上任的 leader，通过 **QUIC → TPU** 进入验证者。
- QUIC 提供带认证握手，使验证者可做流控与 swQoS 分级——这本身是"看得见的准入分层"。
- **leader schedule 在每 epoch 开始前即确定并公开**。任何时刻"谁将打包接下来 4 个连续 slot"是已知信息。

**后果（这是理解 Solana MEV 的核心）**：
1. 搜索者可针对具体 leader 建立专线直连，抢先嗅探其交易流；
2. 与该 leader 合谋（或该 leader 自营机器人）在经济上完全可行。

> **全局公开队列消失了，但局部可预测性取代了它。** 这就是"无 mempool"却仍有严重 MEV 的根本原因。

### 7.2 sandwich 的具体实现

Helius 报告的真实案例（2024-12-16，Komeko 代币）`[二手，一手案例数据]`：

| # | 交易 | 内容 |
|---|---|---|
| 1 | 前置 | 攻击者用 **14.63 SOL** 买入 3,290 万枚，把价格推到受害者滑点允许的最差执行价 |
| 2 | 受害者 | 用 0.33 SOL 买入 62.4 万枚，在被推高的价格成交 |
| 3 | 回补 | 攻击者卖出 3,290 万枚换回 **14.65 SOL**，净赚 **0.01678 SOL（≈$3.35）** |

三笔打包为一个 Jito atomic bundle，tip 仅 0.000148 SOL。**注意杠杆比：用 14.63 SOL 的资本、$3.35 的利润——这是一个极低毛利、极高频次、纯基础设施驱动的生意。**

**三种实现路径**：
1. **Jito 曾经的公开 mempool（2022-08 – 2024-03）**：relayer 延迟 200ms 再转发给 leader，这 200ms 窗口本质是"迷你公开 mempool"，接入 Block Engine 的搜索者都能预览全部交易——**当时 sandwich 的主要土壤**。
2. **验证者私下打包 / "sandwich validators"**：验证者运行修改版客户端或私有 relayer，直接观察进入自己 TPU 的交易并插单。Helius 点名 **DeezNode** 运营的验证者（`HM5H6…jdMRA`）：委托质押从 2024-11-13 的 30.79 万 SOL 暴涨至 12-09 的 **80.25 万 SOL**（其中 19.89% 来自 Marinade 的 mSOL 池），形成 **"质押→更多 leader slot→更多 MEV→更高 APY→吸引更多质押"的恶性飞轮**。
3. **同 slot 内交易排序**：leader 对自己打包 slot 内的顺序有最终裁量权。

### 7.3 Jito 2024-03 关闭 mempool

- **原因**：200ms 预览窗口被系统性用于 sandwich。Jito 尝试工程手段过滤，但形容为"猫鼠游戏"无法根本取胜，最终**主动牺牲显著 tip 收入关闭**。`[二手]` Blockworks / The Block
- **直接结果**：sandwich 数量断崖下跌，但**一个月内迅速恢复**。`[二手]` sandwiched.me
- **转移去向**：
  - **私有订单流 / 私有 mempool**：多名验证者曝光收到 "DeezMempool" 提案文档（涉利润分成）
  - **验证者自营 sandwich 机器人**：程序 `vpeNALD89BZ4KxNUFjdLmFXBCwtyqBDQ85ouNoax38b`，Jito 内部分析显示该**单一程序贡献全网近一半 sandwich 攻击量**
  - **"宽夹"（wide/blind sandwich）兴起**：为对抗 `jitodontfront`（用户在交易中加入哨兵账户，告知 Jito bundler 不要把该交易打包进 sandwich bundle），攻击者改为**前后交易分开发送（间隔 50–300ms）而非同 bundle**，宽夹占比出现**近 30 倍增长**
  - **质押市场成为掩护层**：Marinade SAM 是 pay-for-stake 竞价机制。epoch 717 数据：0% 佣金诚实验证者 ~9.4% APY，SAM 中标 APY 达 **13.73%**，前十名竞价高达 **18.27% APY**（被解读为很可能靠 MEV 补贴出价）

### 7.5 BAM（Block Assembly Marketplace）

- 2025-07-21 由 Jito Foundation / Jito Labs 发布 `[二手]`
- **机制**：Solana 版 Proposer-Builder Separation（PBS），把排序职责从验证者剥离到可编程市场层：
  1. **BAM Node（TEE Scheduler）**：核心调度节点运行在**可信执行环境**（TEE，如 AMD SEV-SNP）中，执行前对交易顺序保密，事后产出**密码学 attestation** 证明排序遵循既定规则。这是与旧 Block Engine（不透明、无可验证性）的关键区别。
  2. **BAM Validator**：运行更新版 Jito-Solana（或兼容 Firedancer/Frankendancer 的 "FireBAM"），接收预排序 bundle 并按指示执行、返回证明。
  3. **Plugin**：开发者可编写自定义排序逻辑，支持即时预言机更新、应用控制执行（ACE）等。
- **是否缓解 MEV**：设计目标是用"TEE 保密 + 可验证证明"同时解决隐私与透明两难，理论上能压制"验证者随意查看并插单"。**但**：① TEE 有侧信道攻击历史先例，安全假设从"信任验证者"转移为"信任 TEE 硬件厂商与固件"；② BAM 仍由 Jito 中心化运营发起，是否引入新中心化依赖点，Chorus One 等持保留态度。`[二手]`

### 7.6 防夹 RPC 的原理与局限

**三种机制**：
1. **Jito bundle 原子性**：bundle 内全成或全不成、按指定顺序执行。用户可把 swap 与哨兵指令打包；`jitodontfront` 约定让运行 Jito 客户端的验证者拒绝把该交易插入任何 sandwich bundle 中间。
2. **私有交易通道**：既然攻击者需"看到"交易才能夹，就不让它看到——绕开公开 QUIC/TPU 入口，`sendTransaction` 直发私有 relay，该 relay 只与可信验证者或 Jito Block Engine 建专线。
3. **黑名单式路由**（以 Helius MEV Protect 为例）：持续监控 sandwich 机器人及其获利落地的验证者，标记"统计上高度关联夹单行为"的验证者；开启 `mev-protect=true` 后将交易**避开被标记验证者**转发。另有 Backrun Rebates（`rebate-address=…`）让用户捕获自己交易产生的合法回补套利收益。

**六条局限（为什么"防夹"不是绝对的）**：
1. **黑名单滞后性**：识别恶意验证者依赖历史统计，本质是滞后指标；新验证者可在被拉黑前完成若干轮攻击（sandwiched.me 提到"dormant validator"被唤醒接手作恶）。
2. **⭐ 宽夹无法被 bundle 原子性防御**：一旦攻击者把前后夹单分开、间隔发送而不打包进同一 bundle，"只保护 bundle 内原子性"或"拒绝夹在同一 bundle 里"的机制（如 `jitodontfront`）**完全失效**。这正是宽夹暴增 30 倍的直接原因。
3. **私有 relay 本身可能被攻陷或勾结**：若提供商自己出售订单流，"私有"反而制造出更隐蔽的观测点（Jito 关闭 mempool 后出现 DeezMempool，只是变得不可审计）。
4. **治理悖论**：白名单被视为最后手段——leader 连续分配 4 个 slot，拉黑一名验证者会导致这几个 slot 内交易延迟数秒；更根本的是，**由中心化 RPC 提供商单方面决定"谁是恶意验证者"本身与去中心化精神冲突**，且有误伤风险。
5. **验证者自己就是攻击者时无解**：用户端无法验证 leader 是否老实排序。这是 BAM 试图用 TEE+attestation 解决但尚未成为全网标准的核心痛点。
6. **速度与保护的权衡**：只走 Jito 通道意味着单路径落地，拥堵时降低成交速度。**Helius 报告了一个反直觉现象：很多 Telegram bot 用户即使被提供 MEV Protect 也不开启**——因为更在意抢先成交（meme 交易者滑点容忍度本来就高，对被夹相对不敏感）。

> **结论**：防夹 RPC 的准确定位是**降低被夹概率的风险缓释措施**，而非密码学保证。只要 Solana 保留"leader 对本 slot 内交易顺序有最终裁量权"这一架构特征，sandwich 的经济激励就不会归零。

## 8. 为什么 Solana infra 适合 meme

### 8.1 Local fee market：按 writable account 隔离热点争用 ⭐ 最重要的一条

**机制细节**：
- Solana 交易提交前必须**显式声明**会读写哪些账户（`AccountMeta` 标注 `isWritable`）。
- 优先费 = `CU Limit × CU Price`。
- **关键**：这个竞价**不是网络级单一拍卖**，而是**按每笔交易实际写入的账户集合局部生效**。验证者调度器（Agave 1.18+ 中央调度器，构建 **prio-graph** 依赖图）只在存在**真实写冲突**的账户集合内比较优先费高低；不同账户集合之间价格互不影响。
- 可观测证据：`getRecentPrioritizationFees` **可按具体账户查询"这条账户线的行情价"**。

**与 EVM 全局 gas 拍卖的对比**：

| | Solana | EVM |
|---|---|---|
| 费用市场粒度 | **per writable account** | **全局单一** |
| 热门 mint 的外部性 | 隔离，不传导 | 全链 gas 拍高 |
| 类比 | 每条车道独立收费 | 隔壁着火，全楼加价 |

一个爆火 meme 币抢购在 Solana 上只让**那一个 bonding curve 账户**的优先费飙升；隔壁的借贷协议、稳定币转账、NFT 交易的费用**完全不受影响**。在 EVM 上，同一事件会把整条链的 gas price 拉高，误伤所有无关用户。

**这是 meme launchpad 对链的第一需求，也是 Mantle 当前最大的结构性短板。**

### 8.2 并行执行 Sealevel —— 以及一个必须讲清的关键澄清

**机制**：交易静态声明完整读写账户集合，Sealevel 据此构建冲突图：**无写集交集的交易可在多核完全并行**；写同一账户的交易必须串行。

**对 launchpad 的两面性**：
- ✅ **不同代币间互不阻塞**：代币 A 与代币 B 的 curve 账户是两个独立账户，买卖交易无写集交集，可同时调度到不同核心。理论上成百上千个代币曲线可同时被交易而互不排队。
- ⚠️ **同一代币的 curve 账户本身是串行瓶颈**：bonding curve / AMM pool 的状态（储备、价格）存在**单一账户**里，任何一笔买卖都必须写它。因此针对同一枚爆款币的所有交易，**无论 Sealevel 并行度多高，本质上仍要串行排队**。

> **这个澄清极其重要**，它同时解释了两个看似矛盾的现象：
> - 为什么 Solana 能支撑同时上千个 meme 币交易？→ 因为币与币之间并行。
> - 为什么 Solana 仍有严重的 sandwich / 抢跑问题？→ 因为同一爆款币内部必须串行，"谁先谁后"有巨大价值。
>
> **并行执行解决"不同 meme 币间不排队"，解决不了"同一爆款币内部的排序竞争"——而后者恰恰是 MEV 的全部土壤。**

### 8.3 低费、高吞吐的具体参数

| 参数 | 值 | 备注 |
|---|---|---|
| base fee | **5,000 lamports/签名**（0.000005 SOL） | 50% 销毁、50% 给出块验证者 |
| priority fee 常见区间 | 低 ~50,000 / 中 ~300,000+ / 高 1,000,000+ micro-lamports/CU | 随拥堵波动 |
| 典型交易 CU | 200,000–400,000 | |
| slot time | 长期 **400ms**；2026-08-21 经 **SIMD-0525** 降至 **350ms**；路线图 300→250→200ms | `[二手，2026 数据需二次验证]` |
| 真实用户 TPS（剔除 vote） | 常态 1,500–4,000+，高峰 2,000–5,000+ | 理论上限常引用 65,000（实验室） |
| 区块 CU 容量演进 | 48M → 50M（2025 初）→ **60M（2025-07-22，官方明确为缓解 meme 热潮瓶颈）** → **100M（2026-07-29, SIMD-0286）** | `[二手，100M 需二次验证]` |
| **单账户（hot account）写入上限** | **固定 12M CU** | ⭐ 见下 |

> **⭐ 单账户 12M CU 硬顶**：即便区块总容量从 48M 扩到 100M，**单个热门账户能承载的计算量增长有硬顶**。这从协议层再次印证 §8.2 的论断，并**直接限制了单一 meme 币在极端抢购下的理论 TPS 上限**。对 launchpad 设计的启示：如果曲线状态集中在一个账户，扩容区块对爆款币毫无帮助。

### 8.4 账户模型 / SPL Token / ATA：发币成本

发一个标准代币的网络层强制成本约 **0.01 SOL**（旧 Metaplex 路径）`[二手]`：

| 账户 | 成本 | 作用 |
|---|---|---|
| Mint | ~0.0015 SOL | 供应量、精度、mint/freeze 权限 |
| ATA | ~0.002 SOL | 存放初始供应 |
| Metaplex Metadata | ~0.0056 SOL | 名称/符号/链下 JSON URI |
| 交易费 | <0.00001 SOL | |

**以上均为可退还的 rent-exempt 押金**（关掉账户可取回）。

> **2026 更新（本人链上核实）**：pump.fun 现用 **Token-2022 的 MetadataPointer + TokenMetadata 扩展**，元数据内嵌 mint 账户，**不再创建独立 Metaplex Metadata 账户**——进一步降低成本与账户数。

**对比 EVM**：部署 ERC-20 合约动辄数十至上百美元 gas，**且不可退**。Solana 账户模型把"创建代币"的边际成本压到**几美分级且可退**——这是 pump.fun 式"一键发币"模式能成立的**直接经济基础**。

### 8.5 机器化生态成熟度

- **RPC/bot/钱包可组合性**：Helius、Triton 开放 `getRecentPrioritizationFees`、`sendTransaction` 定制路由、Geyser 插件等，使第三方 bot 能以极低摩擦接入全流程。
- **Jupiter 聚合**：2024-08 引入**动态滑点**——按代币类型（稳定币 vs 高波动 meme）、路由池、市场状况实时计算最优滑点阈值，替代用户手动设置，**直接降低 meme 交易者"滑点设太高"导致的被夹暴露面**。这是一个协议外的"隐形护栏"。
- **钱包一键体验**：Phantom 等已把"买入 / 设滑点 / 优先费估算"整合为一键，配合 Telegram bot 提供"看到新币→点击→秒级成交"。

### 8.6 反例与代价（不能只讲优点）

| 代价 | 具体表现 |
|---|---|
| **状态膨胀** | 验证者需维护全部账户状态以保证低延迟访问；meme 币账户爆炸式增长持续推高存储/内存负担。社区探索 SIMD-0341 等状态压缩，但压缩状态在 CPI 时需解压，带来额外摩擦 |

| **swQoS 的隐含含义** | 交易的"上链权"在结构上可购买 |

## 9. 推论：一条链要支撑 meme launchpad 需要什么（11 条清单）

> 本节为后续 Mantle 建议的直接输入。每条附必要性论证。

| # | 机制需求 | 必要性论证 |
|---|---|---|
| 1 | **账户级/资源级局部费用市场**，而非全局 gas 拍卖 | 防止单一热门币抢购拖垮全链体验、避免"隔壁着火全楼加价"。缺此能力，任何爆量事件都造成全网级拥堵与费用飙升，扼杀普通用户 |
| 2 | **交易显式声明读写集 + 运行时冲突图并行调度**（Sealevel 式） | 实现"不同代币曲线互不阻塞"的技术前提。无显式读写集声明，链只能保守悲观锁或全局串行 |
| 3 | **极低且可预测的固定 base fee** | meme 交易本质是高频小额投机。固定低费是"发币几美分、单笔亚分"这种规模化试错行为成立的经济前提；费用不确定或过高直接抑制散户 |
| 4 | **代币创建的原生低成本标准**（无需部署自定义合约） | Solana 用 SPL Token + ATA + 元数据标准把发币变成几条标准指令、约 0.01 SOL 可退押金，而非部署合约（EVM 数十美元且不可退）。这是"发币民主化"的基础 |
| 5 | **快速、确定性的出块与最终性**（数百毫秒级） | meme 交易者对抢首发高度敏感；秒级以上确认让"新币刚上线抢购"场景丧失意义 |
| 6 | **原子性交易/bundle 能力** | 无论用于套利、防夹还是多步组合，原子执行是复杂 launchpad 交互与任何反 MEV 方案的技术前提 |
| 7 | **成熟第三方基础设施层**（RPC/索引/bot SDK）愿意投入 | Jupiter/Helius/Jito 提供滑点优化、优先费估算、防夹路由等"隐形护栏"。新链若缺这层，即使底层性能达标，UX 也会因缺少"最后一公里"而崩塌 |
| 8 | **钱包/入口的一键化体验**（生态成熟度而非技术指标） | Phantom + TG bot 把"发现→评估→买入"压到几秒。纯链上性能优势若无前端整合，无法转化为实际交易量 |
| 9 | **透明、可审计（或至少可问责）的排序机制 + MEV 治理演化能力** | 排序权被少数验证者/builder 无监督把持会导致用户系统性被夹，最终反噬用户基础。需预留 BAM（TEE+可验证证明）或协议层防夹 AMM 的演进空间，而非假设 MEV 会自然消失 |
| 10 | **足够的区块/账户级计算容量且可迭代提升** | meme 热潮呈脉冲式爆发。需要明确可执行的扩容路径（而非写死硬上限），否则单次热点事件就导致网络级瘫痪。**注意同时需要解决单账户 CU 硬顶问题（§8.3）** |
| 11 | **低成本"试错"环境 + 噪声治理能力** | 低失败成本既是"人人可参与"的普惠来源，也是带宽被噪声挤占的代价（75.7% 失败率极值）。需在"降低试错门槛"与"抑制垃圾交易"（如中央调度器/prio-graph）间做权衡设计，不能只抄低费而不配套反噪声机制 |

**额外三条来自本文独有发现的设计教训**：

12. **LP 锁定是必要不充分条件**（§2.8）：burn LP 消灭了技术性 rug，但风险平移为分布性抛售。真正的持有人保护需要配合发行侧筹码分布约束。
13. **曲线可以照抄，费用分配政治学必须原创**（§4.3）：pump.fun 在 2025-07 被打到 24% 份额不是因为机制差，而是因为费用没有反哺社区。这是 Mantle 最应该学的一课。
14. **不要把曲线状态集中在单一账户**（§8.2 + §8.3）：单账户 12M CU 硬顶意味着爆款币的吞吐无法通过扩容区块解决。若要突破，需要在设计上对热点曲线做状态分片（例如分桶计价 + 定期归并），这是一个尚未被现有 launchpad 解决的开放问题。
